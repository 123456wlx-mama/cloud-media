## 1. 架构总览

单仓库双端：Windows Qt5.12 客户端 + Linux 自研服务端，共享 `common/`。

```
client/ui (Qt 控件/自绘)  ─┐
client/transfer (队列)     ├─ client/netapi/NetWorker (QTcpSocket, 独立网络线程)
client/player (FFmpeg)    ─┘        │
                                    │ 协议 v2 帧（19 字节头 + payload）
                                    ▼
                       server/net (epoll ET Reactor, 单线程 IO)
                                    │ 投递
                                    ▼
                       server/pool (业务线程池) ── 禁止 IO 线程做磁盘/DB/日志
                                    │
                       server/logic (业务 handler/service)
                          │                    │
                  server/db (MySQL DAO)   server/cache (Redis)
                          │
                  data/blobs/aa/bb/{md5}  (内容寻址)
```

## 2. 协议 v2 帧格式（代码实测，非文档措辞）

`kHeaderSize = 19`，`kMaxPayload = 8MB`，`kMagic = 0x434D4456`（"CMDV"）。

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 4 | magic | 0x434D4456 |
| 4 | 1 | version | 与 `kVersion` 严格相等，否则 BadVersion |
| 5 | 2 | type | `MessageType`，未登记类型直接拒绝 |
| 7 | 4 | len | payload 字节数，> 8MB 判 BadLength |
| 11 | 4 | seq | 请求/响应配对 |
| 15 | 4 | crc32 | **覆盖 offset 4..14（11 字节）+ payload**，跳过 CRC 自身 |

> 注意：`docs/specs` 里描述为「魔数+版本+类型+SEQ+LEN+CRC32」，实际线上顺序是 **LEN 在前、SEQ 在后**。CRC 覆盖区间 = version+type+len+seq+payload。这是一处文档与实现的措辞不一致，讲解时要按代码说。

解码顺序：magic → version → len 上限 → 整帧是否到齐 → CRC → type 已知性 → 取出 payload。长度上限校验在 CRC 之前，避免了按畸形 LEN 预分配。

## 4. 存储模型（7 张表）

| 表 | 主键 | 关键字段 | 设计意图 |
|---|---|---|---|
| `t_user` | `u_id` | `u_tel` 唯一、`u_password` CHAR(64)、`u_salt` CHAR(32)、`u_pwd_algo`（1=旧MD5 2=SHA-256）、`u_status`（0正常 1禁用） | 加盐哈希，支持存量算法迁移 |
| `t_file` | `f_id` | `f_md5` **唯一**（`uk_f_md5`）、`f_size`、`f_path`（相对 blob 根 `aa/bb/<md5>`）、`f_ref_count`、`f_state`（0上传中 1就绪 2孤儿 3缺失） | 内容寻址：一份物理文件被多个用户/路径引用；**`f_state` 是 GC 与秒传的安全阀** |
| `t_user_file` | `uf_id` | `u_id`、`uf_parent_id`（0=根）、`f_id`（目录为 NULL）、`uf_name`、`uf_is_dir`、`uf_deleted_at`（**哨兵值 1970 表示未删除**） | 用户视角目录树；软删用时间哨兵而非布尔位，唯一键含 `uf_deleted_at` 以容纳同名重传 |
| `t_chunk` | (`c_task_id`,`c_index`) | `c_offset`、`c_size`、`c_md5`（**分片 MD5**，非 CRC）、`c_state`（0写入中 1完成）、`c_path` | 断点续传与合并对账的唯一依据 |
| `t_transfer_task` | `tr_id` | `tr_task_id` UUID 唯一、`tr_type`（1上传 2转存 3秒传）、`tr_total_size`、`tr_chunk_size`=4194304、`tr_done_chunks`、`tr_offset`（**派生值可重算**）、`tr_status`（0待开始 1进行中 2暂停 3失败 4完成 5取消 6过期）、`tr_expire_at` | 传输状态必须落 MySQL（可重启续传），不能只放 Redis |
| `t_share` | `s_id` | `s_code` CHAR(6)（31 字符表）、`s_user_id`、`s_uf_id`、`s_file_id`（目录为 NULL）、`s_access_code` CHAR(4)、`s_status`（0有效 1取消）、`s_expire_at` | 分享码 + 可选提取码 + 过期时间 |
| `t_play_record` | `p_id` | `p_user_id`、`p_file_id`、`p_position_ms`、`p_duration_ms`、`p_finished` | 播放进度（续播） |

## 5. 五个设计决策（讲解主线）

1. **内容寻址 + 引用计数 + 状态机**：物理文件按 MD5 存 `data/blobs/aa/bb/{md5}`，`t_file` 对 MD5 唯一，`f_ref_count` 在事务内增减，`f_state` 区分"上传中/就绪/孤儿/缺失"四态。带来秒传与去重，代价是删除必须算引用、GC 必须防"仍有引用却被物理删"，秒传必须拒绝 `f_state != 就绪` 的命中。
2. **协议 v2 帧**：19 字节定长头 + CRC32 覆盖头尾，SEQ 做请求响应配对。上传 4MB 分片走 `RawFrame`，CRC 交给业务线程校验，避免 IO 线程算大块 CRC。
3. **状态分层**：MySQL 存传输状态与文件元数据（要能重启续传），Redis 只存会话、秒传索引、分享码、限流计数——越界即设计错误。
4. **边下边播**：客户端把分片写入 `.part`，播放器用自定义 AVIO 读取，且只读"已确认落盘"的字节（`commitReadable` 推进边界），避免读到文件长度已扩但数据未落盘的洞；服务端用令牌桶限速 + sendfile 零拷贝。
5. **线程模型**：Reactor 单线程只做 IO 与协议拆包，业务投递到线程池；IO 线程内禁止磁盘、MySQL、Redis、同步日志——这是全项目最容易违反的纪律。
