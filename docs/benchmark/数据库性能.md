## 优化案例 1：最近上传列表的 filesort

### 查询

```sql
SELECT uf_id, uf_name
  FROM t_user_file
 WHERE u_id = 1 AND uf_deleted_at IS NULL
 ORDER BY uf_created_at DESC
 LIMIT 50;
```

### 优化前

```
key:   idx_recent
rows:  1
Extra: Using index condition; Using filesort
```

原因：`idx_recent (u_id, uf_deleted_at, uf_updated_at)` 的第三列是 `uf_updated_at`，而业务排序键是
`uf_created_at`。索引能定位到扫描区间，但排序仍需额外一趟 filesort。

### 优化

```sql
ALTER TABLE t_user_file ADD KEY idx_recent_created (u_id, uf_deleted_at, uf_created_at);
```

设计要点：**联合索引的列顺序必须与 `WHERE` 等值列 + `ORDER BY` 排序列一致**（最左前缀匹配），
并且排序列方向与索引一致时才能完全消除排序。

### 优化后

```
key:   idx_recent_created
rows:  1
Extra: Using where
```

`Using filesort` 消失，排序由索引顺序直接提供，`LIMIT` 可提前终止扫描。

## 索引设计说明（v2）

| 表 | 索引 | 覆盖场景 |
|---|---|---|
| t_user_file | `uk_user_parent_name (u_id, uf_parent_id, uf_name, uf_deleted_at)` | 同目录下重名判定（软删参与唯一性） |
| t_user_file | `idx_list (u_id, uf_parent_id, uf_deleted_at, uf_name)` | 目录列表分页（等值 + 前缀排序） |
| t_user_file | `idx_recent_created (u_id, uf_deleted_at, uf_created_at)` | 最近上传列表（本次优化新增） |
| t_user_file | `idx_recent (u_id, uf_deleted_at, uf_updated_at)` | 最近修改列表 |
| t_user_file | `idx_file (f_id, u_id)` | 反查引用（删除文件实体前的引用计数校验） |
| t_file | MD5 唯一索引 | 秒传：按 MD5 判定文件实体是否已存在 |
