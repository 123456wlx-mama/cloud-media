## 优化案例 1：最近上传列表的 filesort

### 查询

注意：软删用哨兵值（`uf_deleted_at NOT NULL DEFAULT '1970-01-01 00:00:00.000000'`），
不是 `IS NULL`——这也是本阶段踩过的一个坑，写成 `IS NULL` 会恒返回 0 行。

```sql
SELECT uf_id, uf_name
  FROM t_user_file
 WHERE u_id = 1
   AND uf_deleted_at = '1970-01-01 00:00:00.000000'
 ORDER BY uf_created_at DESC
 LIMIT 50;
```

### 优化前

```
key:   uk_user_parent_name
rows:  1
Extra: Using index condition; Using filesort
```

原因：可用的两个索引 `uk_user_parent_name` / `idx_recent` 的第三列都不是 `uf_created_at`
（`idx_recent` 排的是 `uf_updated_at`），所以只能定位扫描区间，排序仍需额外一趟 filesort。

### 优化

```sql
ALTER TABLE t_user_file ADD KEY idx_recent_created (u_id, uf_deleted_at, uf_created_at);
```

设计要点：**联合索引的列顺序必须与 `WHERE` 等值列 + `ORDER BY` 排序列一致**（最左前缀匹配），
并且排序列方向与索引一致时才能完全消除排序。

### 优化后

```
key:   idx_recent_created
rows:  1
Extra: Using where
```

`Using filesort` 消失，排序由索引顺序直接提供，`LIMIT` 可提前终止扫描。

## 连接池与缓存基准

环境：Ubuntu 16.04 VM，g++ 5.4，Debug 构建，MySQL 5.7.33 / Redis（源码安装），客户端与服务端同机回环。
执行：`CM_TEST_MYSQL=1 CM_TEST_REDIS=1 ./bin/bench_db`

| 基准 | 参数 | 结果 |
|---|---|---|
| MySQL 连接池借还 | 8 线程 × 50 次 = 400 次 | 6 ms，**66,667 ops/s**，errors=0，in_use=0，idle=4，total_conn=4 |
| MySQL 读往返 | 2000 次 `SELECT` | p50 **99 μs** / p99 420 μs，errors=0 |
| MySQL 写往返 | 2000 次 `INSERT`（临时表） | p50 **63 μs** / p99 557 μs，errors=0 |
| Redis SET | 10 万次 | 5,717 ms，**17,492 ops/s**，errors=0 |
| Redis GET | 10 万次 | 5,098 ms，**19,616 ops/s**，errors=0 |

### 结论与解读

1. **连接池借还几乎无开销**：400 次借还在 6ms 内完成（≈15 μs/次），说明池内命中时不产生系统调用；
   `total_conn=4` 稳定在 min 连接数，`in_use=0` 表示无泄漏——池化把建连成本（约 1-2ms）从每次请求里彻底消掉。
2. **MySQL 读 p50 99 μs / 写 p50 63 μs**：写比读快是因为临时表 INSERT 无索引维护；
   p99 420-557 μs 的尾部来自 VM 调度抖动与 InnoDB 刷盘抖动。
3. **Redis 单连接 1.7-2.0 万 QPS 的关键判读**：单连接串行同步命令的吞吐上限 ≈ `1 / RTT`，
   据此反推 `RTT ≈ 1/19616 ≈ 51 μs`（回环往返 + 协议解析），**瓶颈是同步往返次数，不是 Redis 本身**
   （Redis 单实例实际可达 10 万级 QPS）。提升手段：连接池并发（多连接并行）、pipeline 批量发送、
   或改用异步 hiredis API。
4. 本轮基准取的是 Debug 构建的绝对值，仅用于同一环境下的回归对比。
