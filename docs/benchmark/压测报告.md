# cloud-media 压测报告（Phase 7 收官）

> 版本：2026-10-20 ｜ 被测：cloud-media-server 0.1.0（Release）｜ 工具：benchmarks/bencher（协议 v2 直连）

## 0. 适用范围与边界（先看这段）

- **网络环境：局域网 / 本机回环（127.0.0.1）**，客户端与服务端同机，**不含公网带宽、NAT、丢包、跨机房 RTT 因素**。所有吞吐都是"服务端处理能力"上限，不是"用户能拿到的下载速度"。
- **硬件：2 vCPU / 5.9GB RAM / 单块 VMware 虚拟盘**（`/sys/block/sda/queue/rotational=1`，宿主机介质不可见），Ubuntu 16.04.5 + g++ 5.4。
- 因此本报告的绝对值**只能用于同一台机器上的横向/纵向对比**，不能直接当生产容量规划；对外引用时必须带"2C4G 回环"前缀。
- 压测前必须 `service lightdm stop`（桌面合成器 compiz 会抢 0.67 核，P7-5 实测它能让 list 掉 4 倍）。

## 1. 方法

| 项 | 内容 |
|---|---|
| 工具 | `benchmarks/bencher`：每线程一个 epoll、连接分组、单连接单在途；直连协议 v2（LoginRq / UploadInit+Chunk+Complete / DownloadOpen+Range+Done / ListFileRq），不 spawn CLI |
| 请求语义 | **一次请求 = 一次完整文件操作**（10MB = init + 3×4MB chunk + complete） |
| 在途控制 | 全局 `--inflight 64`（4MB 分片 × 64 ≈ 在途 256MB，2C4G 下不限流会 OOM） |
| 采样 | 客户端：每秒一次 CSV 采样 + 每轮汇总（QPS / MB/s / P50·P90·P99·P999 / 失败率 / 错误分布）；服务端：`/proc/<pid>/io` + `/proc/diskstats` + `/proc/<pid>/status` 每秒一次（VM 无 sysstat，等价 pidstat/iostat） |
| 次数 | 每档 warmup 后跑 3 次取中位数；10MB 档 duration 30s / warmup 10s（窗口必须 ≥3× 单请求延迟） |
| 清态协议 | 每轮前 `bench_env.sh wipe` + `chown` + `echo 3 > drop_caches` + 记录 df |
| 隔离 | 独立库 `cloud_media_bench`、独立数据目录、端口 8014，不影响 e2e 的 8004 |
| 限速 | 下载路径已接线：连接级 2MB/s + 用户级 8MB/s（R1）；"裸能力"数据取自接线前 |

## 2. 基线（修正后）

> 本表所有 MB/s = **file_qps × 单请求字节数**。P7-2 初版的 84.7/545.9 是 bencher 计数器虚高，修正过程见 [phase7_bench_before.md §0](phase7_bench_before.md)。

| 档位 | file_qps | 吞吐 | P50 | P99 | 失败率 |
|---|---:|---:|---:|---:|---:|
| upload 10MB c=100 | 4.2 | 42.0 MB/s | 7.72s | 8.68s | 0 |
| upload 10MB c=1000 | 4.1 | 41.0 MB/s | 7.86s | 8.62s | 0 |
| upload 10MB c=3000 | 3.7 | 37.0 MB/s | 7.77s | 8.08s | 0 |
| upload 1MB c=100 | 47.1 | 47.1 MB/s | 1.25s | 1.37s | 0 |
| upload 1MB c=1000 | 46.9 | 46.9 MB/s | 1.23s | 1.39s | 0 |
| download 10MB c=100（裸） | 52.2 | 522 MB/s | 918ms | 1.75s | 0 |
| download 10MB c=1000（裸） | 40.7 | 407 MB/s | 1.32s | 2.17s | 0 |
| list c=1000（60s） | 3765 → **4310** | — | 263ms | 348ms | 0 |
| connect storm c=8000 | — | **1920 conns/s** | 0.94ms | 1.04s | 0 |
| **8000 长连接保持 30s** | 登录 10,013 QPS | — | 99ms | 135ms | 0（conn_fail=0，服务端 RSS **41.7MB**） |

**读法（重要）**：
1. **上传与连接数无关**：c=100/1000/3000 吞吐 42/41/37MB/s，P99 都在 8s 量级 → 瓶颈是磁盘写 + CPU 哈希，不是连接数。
2. **10MB 上传的 P99 是排队时间**，不是单请求慢：64 在途 × 10MB ÷ 42MB/s ≈ 7.6s，与 P50 7.72s 吻合（Little's Law）。
3. **下载是裸能力 522MB/s、CPU 仅 15%**（sendfile），c=1000 掉到 407MB/s 是 1000 条连接的调度开销。
4. **list 4310 QPS**（P7-5 清态复测，比 P7-2 的 3765 高，因为杀掉了 compiz）。
5. **8000 长连接**：0 连接失败、30s 稳定、服务端 RSS 只有 41.7MB（每连接状态很轻）。

优化前 upload 的 CPU 分布：**MD5 41.1% + CRC 28.6% = 69.6%**，磁盘路径仅 13.9%，拷贝 6.8%。即"4 趟全量扫描/字节"（帧 CRC、分片 MD5、merge 整文件 MD5、block CRC sidecar）是最大成本。详见 [phase7_flamegraph.md](phase7_flamegraph.md)。

## 4. 优化项与收益（清态 before/after）

| # | 优化 | before | after | 收益 |
|---|---|---|---:|---|
| 1 | **O7-c** block CRC sidecar 懒化（不再上传后回读整个 blob 算 CRC） | 3.5 file/s / 35.3MB/s / P99 11.59s | 5.0 / 50.3MB/s / P99 9.07s | **+43%** 吞吐，−22% P99（与 O7-a 合并测量） |
| 2 | **O7-a** 收片不再重算分片 MD5（帧 CRC + merge 已双重覆盖） | 同上 | 同上 | 约占上述 43% 中的 12/28 |
| 3 | **O1** merge 直接写 blobs 路径（同目录 rename，消灭 tmp→blob 二次写） | 5.0 / 50.3MB/s / P99 9.07s | **8.7 / 86.7MB/s / P99 6.65s** | **+74%** 吞吐，−27% P99；设备写放大 2.0× → 1.0× |
| 4 | **R1** 下载限速接线（2MB/s 连接级 + 8MB/s 用户级 + 512/8 流数上限 + 3006） | 522MB/s（无限速） | **2.0MB/s 单流稳态；4 流聚合 7.6MB/s** | 限速精确生效，超限回 3006 |
| 5 | **O3** somaxconn/syn_backlog 调优 | 1920 conns/s，P90 1.04s | 1942 conns/s，P99 3.04s（更差） | **无收益，已回退** |

**累计：upload 10MB c=100 从 35.3 → 86.7MB/s（2.46×），P99 从 11.59s → 6.65s（−43%）。**

三条要能讲清楚的反直觉结论：
- **O1 比哈希优化更赚**：把设备写从 2.0× 降到 1.0× 后，磁盘不再是并发上限，P50 从 8.4s 直接掉到 6.1s。
- **O3 无效**：8000 连接全部成功、CPU 仅 3%，P90 的 1 秒来自客户端 TIME_WAIT/端口回收，不是 accept backlog。
- **限速必须用大文件验证**：10MB 文件在 4MB 桶突发窗口内就跑完，看起来 28MB/s；40MB 才看到真实的 2.0MB/s。

## 5. 结论

1. 系统在 2C4G 回环上能做到：**上传 86.7MB/s（10MB 文件 8.7 个/s）、下载裸能力 522MB/s、list 4310 QPS、8000 长连接稳定保持（RSS 42MB）**。
2. 上传是**磁盘写 + 哈希 CPU 双限**：优化前 69.6% 的 CPU 花在 4 趟数据扫描上，砍掉 2 趟 + 消灭 1 次全量写之后吞吐 2.46×。
3. 下载路径零拷贝（sendfile）已经很省：CPU 15%、RSS 不涨；真正的短板是**限速之前完全没接线**（D-5 半成品），现已补齐并验证稳态。
4. 连接层不是瓶颈：8000 连接 3% CPU；connect storm 的 P90 尾延迟来自客户端端口回收，**不要用 EPOLLEXCLUSIVE 去解**。

## 6. 简历话术（可直接引用，括号里是口径）

- "在 2 vCPU/4GB 云主机上，用自研 epoll 压测客户端（协议级直连、支持 login/upload/download/list/connect storm）对自研网盘服务端做基线压测，**上传吞吐从 35.3MB/s 优化到 86.7MB/s（2.46×），P99 从 11.6s 降到 6.7s**。"
- "用 perf + 火焰图定位到上传路径 **69.6% 的 CPU 花在 MD5/CRC 的 4 趟全量扫描**，据此做了 sidecar 懒生成、分片校验去重、merge 直写 blobs 三项优化，**把设备写放大从 2.0× 降到 1.0×**。"
- "补齐下载令牌桶限速（连接级 2MB/s、用户级 8MB/s、全局 512 流）并用 40MB 大文件验证稳态，**单流 2.0MB/s、4 流聚合 7.6MB/s 精确命中配置**。"
- "8000 长连接保持 30s 零失败、服务端 RSS 42MB；connect storm 1920 conns/s，并定位到 P90 尾延迟来自客户端 TIME_WAIT 而非 accept backlog。"

> 引用时必须带上环境前缀（2C4G / 回环 / Release），否则会被追问穿。

## 7. 复现

~~~bash
# VM：环境 + 服务端
sudo bash scripts/sql/bench_grant.sh && bash scripts/bench_env.sh init
bash scripts/bench_env.sh start && source ~/cm_bench_env.sh

# 基线 / 优化后（清态）
bash scripts/perf/clean_state.sh
build-bench/bin/bencher -p 8014 -op upload -c 100 -t 4 -size 10 -duration 30 -warmup 10 -runs 3 --inflight 64

# 限速稳态（40MB 才进稳态）
build-bench/bin/bencher -p 8014 -op download -c 1 -t 1 -size 40 -duration 45 -warmup 8 --setup-files 1 --inflight 1

# 8000 长连接保持 / 建连风暴
build-bench/bin/bencher -p 8014 -op login  -c 8000 -t 4 -duration 30 -warmup 10
build-bench/bin/bencher -p 8014 -op connect -c 8000 -t 4

# 回归
cd build-cov && CM_TEST_MYSQL=1 CM_TEST_MYSQL_USER=cm_test CM_TEST_MYSQL_DB=cloud_media_test \
  CM_TEST_MYSQL_PASSWORD=... CM_TEST_REDIS=1 ctest --output-on-failure   # 43/43
~~~
