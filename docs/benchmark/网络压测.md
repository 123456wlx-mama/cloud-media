# 网络层回声压测报告（Phase 3）

## 环境

| 项 | 值 |
|---|---|
| 被测服务 | `bin/echo_server`（Reactor：epoll ET + EPOLLONESHOT，单事件循环） |
| 压测工具 | `bin/bench_conn`（自研多连接回声压测客户端） |
| 服务器环境 | Ubuntu 16.04 VM，g++ 5.4.0，构建类型 Debug |
| 网络路径 | 客户端与服务端同机，走 127.0.0.1 回环 |
| 启动命令 | `ulimit -n 65535; ./bin/echo_server -p 8004` |
| 压测命令 | `./bin/bench_conn -c 2000 -t 30 -h 127.0.0.1 -p 8004` |

## 结果

| 指标 | 数值 |
|---|---|
| 并发连接 | 2000（connect_failed = 0，conn_success = 100%） |
| 总请求数 | 3,528,041（首轮）/ 3,161,526（审查修复后回归） |
| QPS | **117,145** / 104,963（两轮同为 10 万量级，差异为 VM 噪声） |
| 请求成功率 | 100%（两轮一致） |
| p50 延迟 | **14.9 ms** |
| p99 延迟 | 33.5 ~ 35.6 ms |
| 总流量 | 1,806,356,992 字节（约 1.8 GB） |
| 压测时长 | 30.1 ~ 30.15 s |
| fd 泄漏检查 | 压测前后一致（首轮 9/9；新增预留 fd 后 10/10），零泄漏 |
| CPU | 空闲期 0.0%（写完即关 EPOLLOUT，无空转） |
| 优雅退出 | SIGINT 后 exited_cleanly，日志无报错 |

## 结论

1. **2000 并发连接全量稳定**：建连成功率 100%，请求成功率 100%，fd 数压测前后一致，无连接泄漏。
2. **吞吐约 11.7 万 QPS**：单事件循环（单 Reactor + 事件回调内完成 echo）即可承载，符合设计预期；后续网盘业务接入后，业务处理将由工作线程池承担，IO 线程只做收发。
3. **延迟解读（重要）**：p50 ≈ 15ms 并非处理慢，而是**单事件循环下的排队时延**——2000 条连接各有一个在途请求时，单条请求的等待时间约为 `并发数 / QPS ≈ 2000 / 105000 ≈ 19ms`，与实测 p50 15ms 吻合。真实的服务端处理开销（收包→分发→回写）在微秒级；**降低该指标的正解是减少单连接的并发在途请求数，或演进为多 IO 线程（主从 Reactor）**。p99 ≈ 34ms 的尾部来自 VM 宿主机调度抖动。裸机环境预期显著优于该值。
4. 事件循环无空转：无数据可写时立即关闭 EPOLLOUT，空闲期 CPU 占用 0%。

## 已知限制（改进方向）

- 单 Reactor：多核场景下受限于单事件循环，Phase 4+ 如遇吞吐瓶颈可演进为主从 Reactor（acceptor + 多 IO 线程）。
- 压测在虚拟机回环上进行，绝对值仅用于回归对比，不代表裸机生产性能。
