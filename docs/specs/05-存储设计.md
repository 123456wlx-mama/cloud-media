## 0. 结论速览

| # | 决策 | 一句话理由 |
|---|---|---|
| 1 | 需求列的 6 张表之外，**必须补 t_user_file** | 用户目录、重命名、软删、分享指向的都是「用户看到的一个条目」，内容表存不了这层语义 |
| 2 | t_file 只存**内容 blob**，目录不进 t_file | 旧库把 folder 塞进 t_file，破坏 MD5 唯一性与引用计数；新模型彻底拆开 |
| 3 | 目录树用**邻接表 parent_id**，不用路径字符串、不存深度列 | 避免 utf8mb4 长路径撑爆唯一索引；移动/重命名只改一行，深度与环由服务层按需遍历判断 |
| 4 | 软删用 **uf_deleted_at 哨兵值**，不设 is_deleted 冗余列 | 唯一索引需要把「删除代次」纳入键；NULL 在唯一索引里不互斥，会放过同名活跃文件 |
| 5 | 删除只减引用计数，**不物理删 blob**；引用计数在应用层事务维护，**删除旧触发器** | 触发器不可单测、锁等待放大、与软删冲突；孤儿 blob 由运维脚本回收 |
| 6 | **本库不建外键** | 批量迁移/在线 DDL 会被阻塞；一致性靠事务 + 唯一索引 + 对账 SQL |
| 7 | 连接池内部状态用 **shared_ptr&lt;PoolCore&gt;**，连接持有 core 的强引用 | 退出顺序错时，最后一条连接归还前 core 不会被析构，避免 use-after-free |
| 8 | **关闭 libmysql 自动重连**，由池层重建物理连接 | 自动重连会静默丢失 charset/sql_mode/time_zone/临时表等会话状态 |
| 9 | Redis 连接**同一时刻只属于一个线程**；超时后**直接丢弃**，绝不重用 | redisContext 非线程安全；超时可能残留未读回复，复用会导致协议错位 |
| 10 | Cache-Aside + TTL 抖动 ±10% + 空值缓存 + 进程内 single-flight + Redis 互斥锁 | 穿透/击穿/雪崩分别有对应手段，且不引入新组件 |
| 11 | 鉴权与限流 **fail-closed**（Redis 挂即拒绝服务） | 降级成「人人合法/不限流」比短暂不可用更危险 |
| 12 | 秒传/分享码 **fail-open 到 MySQL**（唯一索引兜底） | 正确性来源是 DB 唯一索引，Redis 只是加速层 |
| 13 | BUILD_STORAGE：Linux 默认 ON、Windows 默认 OFF，Windows 显式 ON 直接 FATAL | libmysqlclient/hiredis 不在 Windows 侧交付，避免半套依赖 |
| 14 | 迁移保留旧库与旧 blob 目录 **30 天只读**，blob 用硬链接重排 | 可回滚、可对账；硬链接不产生双倍磁盘占用 |

## 1. 范围、环境与约定

### 1.1 范围

**做：**

- 表结构 v2：t_user / t_file / t_user_file / t_chunk / t_transfer_task / t_share / t_play_record。
- 旧库到 v2 的字段映射、目录树重建、blob 重排、数据保留与回滚。
- MysqlPool：RAII 连接、预处理语句、事务 RAII、慢查询打点、池参数与超时。
- RedisPool：hiredis 0.13 封装、命令集、重连与超时、RAII 借还。
- 缓存三件套（穿透/击穿/雪崩）与按场景降级表。
- CMake 接入（BUILD_STORAGE、依赖定位、target 划分、测试注册）。

**不做（明确边界）：**

- 不做分库分表、读写分离、主从、CDC、ORM、迁移框架。
- 不做 Redis Cluster / Sentinel；单实例 + 连接池。
- 不缓存文件列表（失效面太大、收益低），只缓存单实体与计数。
- 不做布隆过滤器（数据量小、删除维护成本高，空值缓存足够）。
- 不做定时物理清理回收站；孤儿 blob 与过期分片只提供运维脚本与对账 SQL。
- 不做服务端下载任务表：下载是无状态 Range 读取，进度在客户端 t_local_task。

### 2.2 t_user

| 字段 | 类型 | 空 | 默认 | 说明 |
|---|---|---|---|---|
| u_id | BIGINT UNSIGNED | 否 | AUTO_INCREMENT | 用户 ID，迁移时保留旧值 |
| u_tel | VARCHAR(20) ascii | 否 | — | 手机号/登录名 |
| u_password | CHAR(64) ascii | 否 | — | SHA-256(salt + password) 的 hex；迁移期可存 32 位旧 MD5 |
| u_salt | CHAR(32) ascii | 否 | — | 每用户随机盐；旧账号迁移时生成新盐 |
| u_pwd_algo | TINYINT UNSIGNED | 否 | 2 | 1=旧 MD5（迁移态），2=SHA-256 |
| u_name | VARCHAR(45) | 否 | — | 昵称，允许重名 |
| u_status | TINYINT UNSIGNED | 否 | 0 | 0 正常，1 禁用 |
| u_created_at | DATETIME(6) | 否 | CURRENT_TIMESTAMP(6) | 创建时间 |
| u_updated_at | DATETIME(6) | 否 | CURRENT_TIMESTAMP(6) ON UPDATE | 更新时间 |

索引：

| 名称 | 列 | 类型 | 用途 |
|---|---|---|---|
| PRIMARY | u_id | 聚簇 | 主键 |
| uk_u_tel | u_tel | 唯一 | 登录查询、注册查重 |

设计说明：

- **密码不用 MD5**。旧库是「固定盐 1234 + MD5」，彩虹表可查；v2 用每用户随机盐 + SHA-256。迁移期用 u_pwd_algo=1 兼容，登录成功后立即重算并改写为 algo=2，用户无感。
- u_tel 唯一索引同时承担注册并发查重：不先 SELECT 再 INSERT（有竞态），直接 INSERT 捕获 ER_DUP_ENTRY。
- 不存最后登录时间/头像等展示字段：当前没有需求，避免为想象的功能建列。

### 2.3 t_file（内容 blob）

| 字段 | 类型 | 空 | 默认 | 说明 |
|---|---|---|---|---|
| f_id | BIGINT UNSIGNED | 否 | AUTO_INCREMENT | 文件实体 ID；迁移时保留旧文件 ID |
| f_md5 | CHAR(32) ascii | 否 | — | 内容 MD5，小写 hex |
| f_size | BIGINT UNSIGNED | 否 | — | 字节数 |
| f_path | VARCHAR(128) ascii | 否 | — | 相对 data/blobs 的路径，如 ab/cd/abcdef... |
| f_ref_count | INT UNSIGNED | 否 | 0 | 引用它的未删除 t_user_file 数 |
| f_state | TINYINT UNSIGNED | 否 | 0 | 0 上传中，1 就绪，2 孤儿，3 缺失 |
| f_created_at | DATETIME(6) | 否 | CURRENT_TIMESTAMP(6) | |
| f_updated_at | DATETIME(6) | 否 | CURRENT_TIMESTAMP(6) ON UPDATE | |

索引：

| 名称 | 列 | 类型 | 用途 |
|---|---|---|---|
| PRIMARY | f_id | 聚簇 | 主键、下载/播放按 ID 取元信息 |
| uk_f_md5 | f_md5 | 唯一 | **秒传正确性的唯一来源**；并发去重靠它，不靠 Redis 锁 |
| idx_state_created | (f_state, f_created_at) | 普通 | 扫描上传中/孤儿 blob（运维与对账） |

设计说明：

- **f_path 落库而不是每次由 MD5 计算**。分片目录规则未来可能从 2 级变 3 级；历史文件必须仍能定位。规则变更只影响新写入。
- **目录不是 t_file**。旧库 f_type='folder' 的行迁移到 t_user_file（f_id=NULL, uf_is_dir=1）。这样 t_file 的每一行都有真实 MD5，唯一索引才有意义。
- v2 **不在分片阶段创建 t_file 占位行**：只有全部分片合并、整文件 MD5 校验通过后，才在一个事务里 INSERT t_file（f_ref_count=1）并写 t_user_file。f_state=0 只用于「合并中」的短暂窗口与历史遗留数据，不会长期停留。
- 删除文件只把 f_ref_count 减一；减到 0 置 f_state=2（孤儿），**不删行、不删 blob**。理由：分享、播放记录、审计都可能还引用该 f_id；物理回收交给运维脚本（先确认无引用再 unlink）。
- f_state=3 用于迁移时源文件丢失：元数据保留、下载返回明确错误，不阻断整批迁移。

### 2.4 t_user_file（用户目录节点）

> 这是需求 6 张表之外**必须补**的一张。没有它，「同一个 blob 在 A 用户叫 1.mp4、在 B 用户叫 电影.mp4、在 A 的 /收藏/ 下」这类信息无处存放。

| 字段 | 类型 | 空 | 默认 | 说明 |
|---|---|---|---|---|
| uf_id | BIGINT UNSIGNED | 否 | AUTO_INCREMENT | 节点 ID，分享/转存指向它 |
| u_id | BIGINT UNSIGNED | 否 | — | 所属用户 |
| uf_parent_id | BIGINT UNSIGNED | 否 | 0 | 父节点；0 = 用户根目录（不建根行） |
| f_id | BIGINT UNSIGNED | 是 | NULL | 文件指向 t_file；目录为 NULL |
| uf_name | VARCHAR(255) | 否 | — | 显示名（含扩展名） |
| uf_is_dir | TINYINT UNSIGNED | 否 | 0 | 1 = 目录 |
| uf_deleted_at | DATETIME(6) | 否 | 1970-01-01 00:00:00.000000 | 哨兵值 = 未删除；非哨兵 = 删除时间 |
| uf_created_at | DATETIME(6) | 否 | CURRENT_TIMESTAMP(6) | 旧库 f_uploadtime |
| uf_updated_at | DATETIME(6) | 否 | CURRENT_TIMESTAMP(6) ON UPDATE | 重命名/移动会更新 |

索引：

| 名称 | 列 | 类型 | 用途 |
|---|---|---|---|
| PRIMARY | uf_id | 聚簇 | 主键 |
| uk_user_parent_name | (u_id, uf_parent_id, uf_name, uf_deleted_at) | 唯一 | 同目录下活跃节点不重名；软删后可复用同名 |
| idx_list | (u_id, uf_parent_id, uf_deleted_at, uf_name) | 普通 | 目录列表 + 按名排序 |
| idx_name | (u_id, uf_name) | 普通 | 文件名前缀搜索 |
| idx_recent | (u_id, uf_deleted_at, uf_updated_at) | 普通 | 最近使用 / 回收站按时间 |
| idx_file | (f_id, u_id) | 普通 | 引用计数对账、按 blob 反查用户 |

**为什么用哨兵时间而不是 is_deleted 布尔列**

唯一索引 (u_id, uf_parent_id, uf_name) 在软删后会永久占用名字，用户删掉 a.txt 再传 a.txt 就撞唯一键。把删除代次纳入唯一键即可，但：

- 若用 uf_deleted_at NULL 表示未删：MySQL 唯一索引允许多个 NULL，**两个活跃的同名节点都能插入**，约束失效。
- 因此用 NOT NULL 哨兵 1970-01-01：所有活跃行共享同一值，互相冲突；删除行各取真实时间，互不冲突。

代价是「已删除」判断变成与常量比较，可读性略差；由 DAO 统一封装 kNotDeleted 常量，业务层不手写。

**为什么用邻接表而不是路径字符串**

- 路径字符串进唯一索引：uf_dir(255) + uf_name(255) 在 utf8mb4 下是 2040 字节，再加 u_id/时间会逼近 3072 上限；邻接表只需约 1044 字节。
- 移动/重命名只改一行，不需要 UPDATE ... WHERE uf_dir LIKE '/old/%' 批量改写后代。
- 代价：显示完整路径需要向上走 ≤16 次（有界，可一次查 16 个父节点），或由服务层缓存；这个代价远小于批量改路径。
- **深度不落库**：父链深度、是否超过 16 层、移动时是否成环，都由服务层向上遍历计算（≤16 次指针跳转）。这样移动目录只改被移动节点的一行 parent_id，不需要批量更新后代的深度列。

**目录软删不级联**：删除目录只把该节点置为已删，子节点保持原状。理由是本期没有「恢复」功能，从根遍历时整棵子树天然不可达；级联更新会产生大量行锁与长事务。回收站只展示被删的顶层节点，不展开子树。

### 2.5 t_chunk（上传分片）

| 字段 | 类型 | 空 | 默认 | 说明 |
|---|---|---|---|---|
| c_task_id | CHAR(32) ascii | 否 | — | 对应 t_transfer_task.tr_task_id（UUID hex） |
| c_index | INT UNSIGNED | 否 | — | 分片序号，从 0 开始 |
| c_offset | BIGINT UNSIGNED | 否 | — | 在文件中的字节偏移 |
| c_size | INT UNSIGNED | 否 | — | 本片字节数（末片可小于 4MB） |
| c_md5 | CHAR(32) ascii | 否 | — | 分片 MD5，用于坏片重传 |
| c_state | TINYINT UNSIGNED | 否 | 0 | 0 写入中，1 完成 |
| c_path | VARCHAR(160) ascii | 否 | — | 临时分片相对路径 tmp/<task_id>/<index> |
| c_created_at | DATETIME(6) | 否 | CURRENT_TIMESTAMP(6) | |
| c_updated_at | DATETIME(6) | 否 | CURRENT_TIMESTAMP(6) ON UPDATE | |

索引：

| 名称 | 列 | 类型 | 用途 |
|---|---|---|---|
| PRIMARY | (c_task_id, c_index) | 复合聚簇 | 单任务内分片天然唯一；重复上传同片可 ON DUPLICATE KEY UPDATE 幂等 |
| idx_updated | (c_updated_at) | 普通 | 清理超时任务的残留分片 |

设计说明：

- **复合主键而非自增 ID**：分片只在任务内被访问，(task_id, index) 就是业务主键；顺带获得幂等 upsert 能力。
- 不冗余 c_file_md5：任务表已有；多存一份会产生「两处真相」。
- 完成分片数不在本表做 COUNT 聚合（大文件会有上千行），由 t_transfer_task.tr_done_chunks 计数，事务内 +1。
- 分片文件写完并 fsync 后才把 c_state 置 1（写盘顺序：临时文件 → rename → 更新行）。

### 2.6 t_transfer_task（写侧任务：上传 / 转存 / 秒传）

| tr_updated_at | DATETIME(6) | 否 | CURRENT_TIMESTAMP(6) ON UPDATE | |

索引：

| 名称 | 列 | 类型 | 用途 |
|---|---|---|---|
| PRIMARY | tr_id | 聚簇 | 主键 |
| uk_task_id | tr_task_id | 唯一 | 协议按任务 ID 查询；同时防重复创建 |
| idx_user_type_status | (tr_user_id, tr_type, tr_status, tr_updated_at) | 普通 | 登录后拉未完成任务（对账）；按更新时间排序 |
| idx_expire | (tr_status, tr_expire_at) | 普通 | 过期任务扫描 |

设计说明：

- **只持久化写侧任务**。下载是 Range 无状态读取，服务端不需要任务行；下载续传进度在客户端 SQLite。这样表不会因为「每次下载一行」膨胀。
- 秒传（type=3）通常一步完成（命中 → 插 t_user_file → done），任务行存在的意义是审计与幂等：同一客户端重试不会落两条用户文件（用 uk_user_parent_name 兜底）。
- tr_offset 只是加速字段：续传时以 t_chunk 的完成位图为准重算，避免计数漂移导致跳过坏片。
- 状态机由 Phase 5 的 Service 负责；存储层只提供条件更新（UPDATE ... WHERE tr_status IN (...)）保证并发安全，不在这里写状态机代码。

### 2.9 索引设计与最左前缀

**三条规则：**

1. 等值条件列在前，排序列紧随其后，范围条件列最后。
2. 跳过最左列，后续列无法用于定位（只能全扫或松散索引扫描）。
3. 范围条件之后的列失去排序能力（ORDER BY 会 filesort）。

| 查询 | SQL 形状 | 命中索引 | 最左前缀说明 |
|---|---|---|---|
| 登录 | WHERE u_tel=? | uk_u_tel | 单列唯一，最左即全部 |
| 注册查重 | INSERT 捕获 1062 | uk_u_tel | 不先查后插 |
| 目录列表 | WHERE u_id=? AND uf_parent_id=? AND uf_deleted_at=? ORDER BY uf_name LIMIT ? | idx_list | 三个等值列全匹配，第四列直接提供排序；若去掉 uf_parent_id，只能用 u_id 前缀，且排序失效 |
| 根目录列表 | WHERE u_id=? AND uf_parent_id=0 AND uf_deleted_at=? | idx_list | 根目录是常量 0，同样走完整索引 |
| 文件名前缀搜 | WHERE u_id=? AND uf_name LIKE 'kw%' | idx_name | u_id 等值 + uf_name 范围；%kw% 无法走索引，退化为用户内扫描 |
| 最近使用 | WHERE u_id=? AND uf_deleted_at=? ORDER BY uf_updated_at DESC LIMIT 20 | idx_recent | 前两列等值，第三列排序 |
| 我的分享 | WHERE s_user_id=? AND s_status=0 ORDER BY s_created_at DESC | idx_user_status_created | 两列等值 + 排序；若只按 s_user_id 查，仍能用前缀但需回表过滤 status |
| 未完成任务 | WHERE tr_user_id=? AND tr_type=? AND tr_status IN (0,1,2) ORDER BY tr_updated_at | idx_user_type_status | 前三列定位；IN 跨多个 status 值时允许 filesort（行数 <100，可接受） |
| 过期任务 | WHERE tr_status IN (0,1,2) AND tr_expire_at < NOW(6) | idx_expire | status 在最左且是范围，expire 只能过滤不能定位；这是扫描型查询，低频 |
| 秒传 | WHERE f_md5=? | uk_f_md5 | 单列唯一 |
| 引用对账 | WHERE f_id=? | idx_file | (f_id, u_id) 最左 f_id |
| 播放续播 | WHERE p_user_id=? AND p_file_id=? | uk_user_file | 两列全匹配 |
| 最近播放 | WHERE p_user_id=? ORDER BY p_updated_at DESC | idx_user_updated | 等值 + 排序 |

**索引长度与行格式**：uk_user_parent_name 在 utf8mb4 下约 1044 字节，超过 767 字节的旧限制。必须满足：

- innodb_large_prefix=ON（5.7 默认 ON）
- innodb_file_format=Barracuda（5.7 默认）
- 表显式 ROW_FORMAT=DYNAMIC

若线上是 5.6 或 compact 行格式，该索引会创建失败——这是把 MySQL 锁定为 5.7 的原因之一。

**不为写而过度建索引**：t_user_file 已有 1 个唯一 + 4 个普通索引，上传/删除是低频写、列表是高频读，这个比例可以接受；不再为「按大小排序」等未定需求加索引。

### 2.10 外键策略：本库不建外键

| 理由 | 具体影响 |
|---|---|
| 批量迁移/修复会被阻塞 | 导入顺序必须严格 parents-first；删旧库前要先摘 FK；出问题无法单表重灌 |
| 在线 DDL 受限 | 改父表主键/类型需要重建子表约束；pt-online-schema-change 对 FK 支持差 |
| 高并发下锁放大 | 每次 INSERT t_user_file 都要对 t_file 父行加共享锁，秒传热点 MD5 会成为行锁瓶颈 |
| 软删语义 FK 表达不了 | 删除是改 uf_deleted_at，不是 DELETE；FK 的 CASCADE/RESTRICT 全部用不上 |
| 引用计数是应用层不变量 | f_ref_count 与关系行必须同一事务更新，FK 不会替你维护计数 |
| 分表/归档是既定演进方向 | t_play_record、t_transfer_task 按时间归档时，FK 是纯负担 |

**不用外键 ≠ 不管一致性**，用四道防线：

1. 唯一索引兜住业务唯一性（MD5、分享码、同目录名、用户文件）。
2. 同一事务内更新关系行与引用计数。
3. 所有跨表读取用 JOIN 校验存在性；对不上返回明确错误，不返回半条数据。
4. 每日对账 SQL（见 2.11）与告警；发现孤儿只记录、不自动删。

### 2.11 不变量与对账

| 编号 | 不变量 | 违反后果 |
|---|---|---|
| I1 | t_file.f_ref_count = COUNT(t_user_file WHERE f_id=? AND uf_deleted_at=哨兵) | 计数偏大 → blob 永不回收；偏小 → 误删仍在用的 blob |
| I2 | t_user_file.f_id 非空时必存在于 t_file 且 f_state=1 | 列表出现坏条目 |
| I3 | 父子链无环、深度 ≤16；父节点必须属于同一用户且是目录 | 路径递归死循环 / 跨用户越权 |
| I4 | DONE 任务的 SUM(c_size) = tr_total_size | 合并出截断文件 |
| I5 | 分享指向的节点未删除且未过期 | 分享页 404 或越权 |

对账 SQL（放 scripts/reconcile.sql，只读，不自动修）：

~~~sql
-- I1 引用计数
SELECT f.f_id, f.f_ref_count,
       (SELECT COUNT(*) FROM t_user_file u
         WHERE u.f_id = f.f_id
           AND u.uf_deleted_at = '1970-01-01 00:00:00.000000') AS real_cnt
  FROM t_file f
 HAVING f.f_ref_count <> real_cnt;

-- I2 悬空引用
SELECT u.uf_id, u.f_id
  FROM t_user_file u
  LEFT JOIN t_file f ON f.f_id = u.f_id
 WHERE u.f_id IS NOT NULL
   AND (f.f_id IS NULL OR f.f_state <> 1);

-- I3 父链异常（跨用户 / 父节点不是目录）
SELECT c.uf_id, c.u_id, c.uf_parent_id
  FROM t_user_file c
  JOIN t_user_file p ON p.uf_id = c.uf_parent_id
 WHERE c.uf_parent_id <> 0
   AND (p.u_id <> c.u_id OR p.uf_is_dir <> 1);

-- I4 分片汇总
SELECT t.tr_task_id, t.tr_total_size, SUM(c.c_size) AS sum_size
  FROM t_transfer_task t
  JOIN t_chunk c ON c.c_task_id = t.tr_task_id AND c.c_state = 1
 WHERE t.tr_status = 4
 GROUP BY t.tr_task_id, t.tr_total_size
HAVING SUM(c.c_size) <> t.tr_total_size;
~~~

### 3.1 旧结构的问题（决定映射方式）

### 3.3 目录树重建算法

输入：legacy.t_user_file 全部行（含 file 与 folder）。

1. 对每个用户，收集所有 f_dir，按 / 切段并去重，得到「需要存在的目录路径」集合（包含只出现在 f_dir 里、但没有对应 folder 行的中间目录）。
2. 按段数从少到多排序（保证父先于子）。对每条路径逐段查/建节点：
   - SELECT uf_id FROM t_user_file WHERE u_id=? AND uf_parent_id=? AND uf_name=? AND uf_deleted_at=哨兵；
   - 不存在则 INSERT（uf_is_dir=1, f_id=NULL）。
   - 用内存 map 缓存 (u_id, 完整路径) → uf_id，避免 N 次查询。
3. 处理 folder 行：按 (u_id, f_dir + f_name + '/') 找到步骤 2 建的节点，回填 uf_created_at = f_uploadtime；找不到说明旧数据缺行，补建。
4. 处理 file 行：按 (u_id, f_dir) 找父节点，插入 uf_name, f_id, uf_is_dir=0；同名冲突加 (2)、(3) 并写入冲突报告。
5. 任何路径段数 > 16 的路径：照常迁移（不丢数据），但记 WARN，且新版本禁止再创建超过 16 层。
6. 全量插入完成后执行一次 I3 对账，确认无跨用户父节点、父节点均为目录。环由「按段数从少到多、自顶向下」的构建顺序保证。

复杂度：O(节点数 × 平均深度)，深度上限 16；10 万节点量级可在一次迁移窗口内完成，按 1000 行/批提交，避免长事务。

### 3.4 blob 重排

旧布局按用户目录存放，同一个 MD5 可能有多份物理文件；v2 是全服一份。

1. 按 f_md5 分组，每组选一个源文件（优先 f_state=1、f_id 最小、文件存在）。
2. 目标路径 data/blobs/aa/bb/md5；目录不存在则创建（运维脚本，不在服务进程里做）。
3. 优先 link() 硬链接（同一文件系统，零额外空间）；跨文件系统退化为复制。
4. 校验：目标文件大小 = f_size；迁移时抽检 10% 的 MD5，其余由后台任务补全。
5. 同一 MD5 的其余副本不立即删除，留在旧目录，随旧目录 30 天后一起清理。
6. 源文件缺失：f_state=3，写异常报告，不阻断批次。

空间预估：迁移前检查 df，若无法硬链接，需要 ≥ 旧数据总大小 × 1.1 的空闲空间；脚本先输出预估再执行。

### 3.5 分享迁移

- s_link 是 bigint，可能丢失前导 0：迁移时左补 0 到 9 位；不足 9 位且首位为 0 的，重新生成。
- s_linkPassword 左补 0 到 4 位；0 或 NULL 视为无提取码。
- 旧分享没有过期时间。**迁移假设：统一设为「迁移时刻 + 7 天」**，并在迁移报告中列出数量；产品若要求永久分享，改这一个常量即可。
- s_uf_id 取该行对应的用户文件节点；s_file_id 取该行的 f_id（目录分享为 NULL）。
- 重复 s_code：保留最早一条，其余重新生成并记录映射表（旧码 → 新码），供客服查询。

### 3.6 数据保留与回滚

| 阶段 | 动作 | 保留期 |
|---|---|---|
| 0 备份 | mysqldump --single-transaction --routines --triggers NetDisk > NetDisk_YYYYMMDD.sql；在 staging 恢复验证一次 | 永久（离线归档） |
| 1 冻结 | 停旧服务写入，记录 MAX(u_id)、MAX(f_id)、行数 | 迁移窗口内 |
| 2 建库 | 新建 cloud_media（与旧库同实例或新实例），执行 schema_v2 | — |
| 3 迁移 | 按 user → file → 目录树 → 节点 → share 顺序；每 1000 行提交 | — |
| 4 blob | 硬链接/复制到 data/blobs，写 f_path | — |
| 5 对账 | 跑 2.11 与 3.7 的校验 | — |
| 6 切换 | 改 server.ini 指向新库，启动 v2 服务 | — |
| 7 观察 | 旧库改名 NetDisk_legacy_YYYYMMDD，建只读账号；旧 blob 目录改名 data/legacy-YYYYMMDD | **30 天** |
| 8 清理 | 删除旧库与旧目录（硬链接已共享空间，只释放目录项） | 30 天后 |

**回滚**：旧库与旧二进制在 30 天内保持可用；回滚 = 停 v2 → 改回配置 → 启动旧服务。代价是切换后新写入的数据丢失（停机迁移，可接受）；因此迁移窗口内禁止新写入。

**不可回滚点**：旧 blob 目录被删除之后。所以第 8 步必须人工确认，不进自动化脚本。

### 3.7 迁移校验清单

~~~sql
-- 1 用户数
SELECT (SELECT COUNT(*) FROM NetDisk_legacy.t_user) AS old_cnt,
       (SELECT COUNT(*) FROM cloud_media.t_user)   AS new_cnt;

-- 2 去重后的文件实体数
SELECT (SELECT COUNT(DISTINCT f_MD5) FROM NetDisk_legacy.t_file WHERE f_type='file') AS old_blobs,
       (SELECT COUNT(*) FROM cloud_media.t_file) AS new_blobs;

-- 3 用户文件关系数（只算文件）
SELECT (SELECT COUNT(*) FROM NetDisk_legacy.t_user_file uf
          JOIN NetDisk_legacy.t_file f ON f.f_id=uf.f_id AND f.f_type='file') AS old_links,
       (SELECT COUNT(*) FROM cloud_media.t_user_file WHERE f_id IS NOT NULL) AS new_links;

-- 4 逻辑总容量（按关系累加，应与旧库一致）
SELECT (SELECT SUM(f.f_size) FROM NetDisk_legacy.t_user_file uf
          JOIN NetDisk_legacy.t_file f ON f.f_id=uf.f_id AND f.f_type='file') AS old_bytes,
       (SELECT SUM(f.f_size) FROM cloud_media.t_user_file uf
          JOIN cloud_media.t_file f ON f.f_id=uf.f_id) AS new_bytes;

-- 5 分享数
SELECT (SELECT COUNT(*) FROM NetDisk_legacy.t_user_file WHERE s_link IS NOT NULL) AS old_shares,
       (SELECT COUNT(*) FROM cloud_media.t_share WHERE s_status=0) AS new_shares;

-- 6 孤儿/悬空
SELECT COUNT(*) FROM cloud_media.t_user_file u
  LEFT JOIN cloud_media.t_file f ON f.f_id=u.f_id
 WHERE u.f_id IS NOT NULL AND f.f_id IS NULL;
~~~

外加三项非 SQL 校验：

1. 随机抽 100 个 f_id，按 f_path 打开文件、重算 MD5、比对。
2. 随机抽 20 个用户，登录后目录树节点数与旧 f_dir/f_name 去重数一致。
3. 随机抽 10 个旧分享码，验证能打开、提取码正确、文件名一致。

### 3.8 明确不迁移的内容

| 内容 | 处理 | 原因 |
|---|---|---|
| 旧服务端内存传输 map | 丢弃 | 进程退出即失效，无持久化价值 |
| 旧客户端 SQLite（t_upload/t_download） | 不迁移 | v1 表结构与 v2 不兼容；客户端首次登录按服务端任务列表重建 |
| user_file_info 视图 | 不建 | 见 3.2 |
| 两个触发器 | 不建 | 见 3.2 |
| f_path 绝对路径 | 不保留 | 换机即失效 |
| 旧分享历史（已取消/已过期） | 不迁移 | 旧库没有状态字段，无法区分 |

## 4. MysqlPool

### 4.1 所有权与类关系

~~~text
MysqlPool (facade, shared_ptr)
  └─ shared_ptr<PoolCore>        // 队列、互斥量、条件变量、计数、配置
       ├─ idle: deque<unique_ptr<MYSQL, MysqlCloser>>
       └─ cv, mutex, stopping

MysqlConn (move-only, 由 acquire 返回 unique_ptr)
  ├─ shared_ptr<PoolCore> core_  // 强引用：保证归还时 core 还活着
  ├─ unique_ptr<MYSQL, MysqlCloser> conn_
  ├─ last_active_at_, broken_, in_tx_
  └─ ~MysqlConn() { core_->give_back(std::move(conn_)); }
~~~

关键点：连接持有 core 的 **shared_ptr**（不是 weak_ptr）。退出时即使 MysqlPool 已经析构，core 仍活到最后一个连接归还；归还时看到 stopping=true 就直接关闭物理连接，然后 core 自然析构。这样不会出现「线程还在用连接池，池已析构」的段错误（04 文档已把这条列为退出顺序风险）。

不使用裸 new/delete：std::unique_ptr<MYSQL, MysqlCloser>，deleter 调 mysql_close；PoolCore 由 **std::make_shared<PoolCore>(...)** 创建（make_shared 是 C++11；项目禁用的是 C++14 的 make_unique，不是 make_shared）。

### 4.2 借还与 RAII

~~~cpp
class MysqlPool {
public:
    static std::shared_ptr<MysqlPool> create(const MysqlOptions& opt, std::string* err);

    // 失败返回 nullptr；超时/不可用通过 last_error() 区分
    std::unique_ptr<MysqlConn> acquire();
    std::unique_ptr<MysqlConn> acquire(std::chrono::milliseconds timeout);

    PoolStats stats() const;
    std::string describe() const;   // 不含密码
    void shutdown();
};

class MysqlConn {
public:
    ~MysqlConn();                                   // 归还，不 close
    MysqlConn(const MysqlConn&) = delete;
    MysqlConn& operator=(const MysqlConn&) = delete;

    MYSQL* raw();
    bool ping();
    bool valid() const;
    std::unique_ptr<PreparedStatement> prepare(const std::string& sql);
    bool begin();
    bool commit();
    bool rollback();
    bool in_transaction() const;
    uint64_t conn_id() const;                       // 仅用于日志

~~~

使用形态：

~~~cpp
std::unique_ptr<MysqlConn> conn = pool->acquire();
if (!conn) {
    return reply_error(ErrorCode::DbPoolTimeout, seq);
}
std::unique_ptr<PreparedStatement> st = conn->prepare(
    "SELECT f_id, f_size, f_path FROM t_file WHERE f_md5=?");
st->bindString(0, md5);
if (!st->execute() || !st->fetch()) {
    return reply_error(ErrorCode::DbQueryFailed, seq);

~~~

约束：

- acquire() **只允许在业务线程调用**。Debug 构建下用 EventLoop::isInLoopThread() 断言，防止有人在 IO 线程里拿连接做查询（04 文档的硬约束）。
- 返回的 MysqlConn 不可跨线程传递；谁借谁还。
- MysqlConn 析构不抛异常；归还失败只记日志。

### 4.3 连接有效性检测与重连

建连参数：

| 选项 | 值 | 说明 |
|---|---|---|
| MYSQL_OPT_CONNECT_TIMEOUT | 3s | 建连超时 |
| MYSQL_OPT_READ_TIMEOUT | 5s | 读超时 |
| MYSQL_OPT_WRITE_TIMEOUT | 5s | 写超时 |
| MYSQL_OPT_RECONNECT | **0** | 关闭自动重连 |
| MYSQL_SET_CHARSET_NAME | utf8mb4 | 握手字符集 |
| CLIENT_MULTI_STATEMENTS | **不启用** | 防注入放大；一次只允许一条语句 |

**为什么关闭自动重连**：libmysql 的自动重连只重建 TCP，不恢复会话状态——charset、sql_mode、time_zone、autocommit、用户变量、临时表全部丢失，且应用完全无感。经典事故是「重连后字符集回到 latin1，中文全部乱码」。因此由池层显式重建，并在新连接上重放会话初始化。

借出前检测：

1. 从 idle 取连接。
2. 若 now - last_active_at > 30s，执行 mysql_ping。
3. ping 失败或 mysql_errno 属于连接级错误 → mysql_close，从池中移除，尝试新建。
4. 新建失败连续 3 次 → 打开熔断（5s 内直接失败），避免每个请求都等 3s 建连超时。
5. 借出成功时刷新 last_active_at。

会话初始化（每条新建物理连接执行一次）：

~~~sql
SET NAMES utf8mb4;
SET SESSION time_zone = '+00:00';
SET SESSION sql_mode = 'STRICT_TRANS_TABLES,NO_ZERO_DATE,ERROR_FOR_DIVISION_BY_ZERO,NO_ENGINE_SUBSTITUTION';
SET SESSION autocommit = 1;
SET SESSION innodb_lock_wait_timeout = 5;
SET SESSION max_execution_time = 2000;   -- 仅对只读 SELECT 生效
~~~

max_lifetime（默认 30 分钟）：到期连接主动关闭重建，避免被 MySQL wait_timeout 或中间代理静默掐断后才发现。

错误分类：

| 错误 | 处理 |
|---|---|
| CR_SERVER_GONE_ERROR / CR_SERVER_LOST / CR_CONN_HOST_ERROR | 标记 broken，丢弃；**只对只读查询**允许上层重试一次 |
| ER_LOCK_DEADLOCK (1213) / ER_LOCK_WAIT_TIMEOUT (1205) | 连接仍可用；由 Service 重跑整个事务（最多 2 次），池不重试 |
| ER_DUP_ENTRY (1062) | 业务错误（秒传命中、分享码冲突、重名），映射为具体 ErrorCode |
| 其他 SQL 错误 | 记 ERROR（含 SQL 占位符与 errno），返回 DbQueryFailed，不重试 |

写操作**绝不自动重试**：无法判断 MySQL 是「没收到」还是「执行了但回包丢了」，重试可能产生重复行。

### 4.4 PreparedStatement

~~~cpp
class PreparedStatement {
public:
    ~PreparedStatement();                        // mysql_stmt_close
    void bindInt(int idx, int64_t v);
    void bindUInt(int idx, uint64_t v);
    void bindString(int idx, const std::string& v);
    void bindNull(int idx);
    bool execute();                              // mysql_stmt_execute
    bool fetch();                                // true=有行；false=结束或错误
    bool isNull(int idx) const;
    int64_t getInt(int idx) const;
    std::string getString(int idx) const;
    uint64_t affected_rows() const;
    uint64_t insert_id() const;
    const std::string& sql() const;              // 占位符形式，不含参数
};
~~~

实现约束（都是踩过的坑）：

1. **两段式绑定**：先把所有参数值放进 std::vector<std::string> 并 reserve(n)，再一次性填 MYSQL_BIND 数组。禁止边 push_back 边 bind——vector 扩容会让 MYSQL_BIND::buffer 变成悬垂指针（与环境规则里「string 取址后 resize 失效」是同一类 UB）。
2. MYSQL_BIND 数组、长度数组、is_null 数组由 statement 持有，生命周期覆盖 execute/fetch。
3. 结果默认 mysql_stmt_store_result 缓冲（所有列表查询都有 LIMIT ≤200）；不做服务器端游标，避免长事务占连接。
4. 每条 SQL 都走 prepare，**不做字符串拼接**。SQL 文本天然不含参数值，慢查询日志因此天然脱敏。
5. 不做 statement 缓存（v2）。本地 prepare 成本约 0.1ms；若 Phase 7 压测显示占比高，再在连接内加 LRU。

### 4.5 Transaction RAII

~~~cpp
class Transaction {
public:
    explicit Transaction(MysqlConn& conn);
    ~Transaction();                 // !committed_ -> ROLLBACK，吞异常只记日志
    bool valid() const;             // BEGIN 是否成功；嵌套时 false
    bool commit();                  // COMMIT 成功后 committed_=true
    bool rollback();
    ErrorCode last_error() const;
    Transaction(const Transaction&) = delete;
    Transaction& operator=(const Transaction&) = delete;
};
~~~

语义：

- 构造执行 BEGIN；valid()==false 时不发任何语句（例如连接已 broken）。
- 析构时若未 commit() 也未 rollback() → 执行 ROLLBACK。**析构不抛异常**；回滚失败只记 ERROR 并把连接标记 broken（连接可能处于未知事务状态，不能回池复用）。
- 成功 commit() 后析构不再发语句。
- **禁止嵌套**：Transaction 构造时检查 conn.in_transaction()，为真则 valid()=false、last_error()=ErrTxNested。需要部分回滚时显式用 SAVEPOINT，不靠嵌套对象。
- 事务内禁止执行 DDL（隐式提交会破坏语义）；DDL 只出现在迁移脚本。

事务边界（Phase 5 会用到，这里先定死）：

| 操作 | 事务内语句 |
|---|---|
| 秒传落库 | INSERT t_file ... ON DUPLICATE KEY UPDATE f_ref_count=f_ref_count+1 → INSERT t_user_file |
| 上传完成 | UPDATE t_file SET f_state=1 → INSERT t_user_file → UPDATE t_transfer_task SET tr_status=4 |
| 删除文件 | UPDATE t_user_file SET uf_deleted_at=NOW(6) → UPDATE t_file SET f_ref_count=f_ref_count-1（条件 >0） |
| 转存 | 读源 f_id → 增引用计数 → 插新 t_user_file → 写 t_transfer_task |

### 4.6 慢查询打点

- 计时用 std::chrono::steady_clock，包住 mysql_stmt_execute + 结果读取（fetch 全部行），不是只算 execute。
- 阈值 slow_query_ms 默认 200ms，可配置。
- 超过阈值 → WARN 日志：trace_id, conn_id, cost_ms, rows, affected, in_tx, sql（SQL 是占位符形式，无参数）。
- 聚合计数：slow_query_total、slow_query_max_ms，通过 stats() 暴露。
- 不在池层采样绑定参数；需要排查具体值时，由业务在 Debug 日志里显式记录**非敏感**字段（如 file_id），密码/token 永远不记。
- MySQL 侧同时开 slow_query_log，阈值 1s，作为第二道证据（池层 200ms 用于发现「还没慢到 MySQL 阈值但已经拖慢接口」的查询）。

### 4.7 池参数与获取超时

| 参数 | 默认 | 取值理由 |
|---|---|---|
| min_size | 2 | 启动预热，避免首请求建连抖动；2C4G 上足够 |
| max_size | 8（上限 32） | 经验公式 max_size ≈ 业务线程数 + IO 线程数；每个业务线程同一时刻最多持 1 条连接，超过就是排队而非并行 |
| idle_timeout | 60s | 空闲超过 1 分钟且总数 > min_size 时关闭 |
| acquire_timeout | 500ms | 超过 500ms 说明池已饱和，快速失败优于继续排队拖高 P99 |
| max_lifetime | 30min | 规避 wait_timeout / 代理空闲断开 |
| validation_interval | 30s | 空闲超过该值才 ping，避免每次借出都多一次 RTT |
| shrink_interval | 10s | 后台收缩线程周期 |

**获取超时的处理（按顺序）：**

1. wait_for(acquire_timeout) 等 idle 或 stopping。
2. 超时且池未停止 → 返回 nullptr，acquire_timeout_total++，WARN 日志限流（每 1s 最多一条），内容只含池计数。
3. 上层映射为 ErrorCode::DbPoolTimeout（可重试），回 ERROR_RS；**不原地重试、不 sleep 重试**，避免请求线程堆积。
4. 若同时观察到「连续建连失败 ≥3」，直接返回 DbUnavailable 并打开熔断 5s；熔断期间 acquire 立即失败，不做无意义的 500ms 等待。
5. 半开：5s 后放一个探测请求建连，成功则关闭熔断，失败则重新计时。

acquire() 不抛异常、不阻塞超过 acquire_timeout；这是保证「存储层抖动不会把 Reactor/业务线程池拖死」的底线。

### 4.8 生命周期与关闭顺序

~~~text
ServerApp::stop()
  1. 停 accept，等待在途请求结束（04 的优雅退出）
  2. 业务线程池 join            // 此后不会再有新 acquire
  3. mysql_pool->shutdown()      // stopping=true; cv.notify_all()
  4. 等待 in_use 归零，最多 5s   // 连接归还时看到 stopping 直接 close
  5. 关闭 idle 队列中的所有物理连接
  6. 最后一个 shared_ptr<PoolCore> 释放（可能由归还的连接触发）
~~~

禁止：在仍有查询执行时析构 pool；在信号处理函数里调用 shutdown（只允许置原子标志 + self-pipe，04 已规定）。

### 4.9 安全：密码不进日志与 describe()

| 位置 | 规则 |
|---|---|
| MysqlOptions | 有 password 字段，仅在 mysql_real_connect 使用 |
| MysqlPool::describe() | 只输出 host/port/db/user/pool 计数，**永不输出 password** |
| ServerConfig::describe() | 敏感字段统一替换为 *** |
| 启动日志 | mysql connected host=... port=... db=... user=...，无 DSN、无密码 |
| 错误日志 | 只记 mysql_errno/mysql_error，不拼接连接串 |
| 慢查询 | 只记占位符 SQL，不记参数 |
| 单测 | 断言 describe() 与 ServerConfig::describe() 的输出不含密码明文 |

## 5. RedisPool

### 5.1 hiredis 0.13 的硬约束

| 约束 | 影响 | 对策 |
|---|---|---|
| redisContext **非线程安全** | 多线程共用一个连接会交错读写、解析错位 | 借出期间连接归单线程独占；归还前不得有其他线程持有 |
| 0.13 **没有 redisReconnect**（0.14 才有） | 断线不能原地重连 | redisFree 后 redisConnectWithTimeout 重建，并重放 AUTH/SELECT |
| 命令超时后可能残留未读回复 | 复用会导致后续命令读到上一条的回复 | 任何 IO 超时/连接错误 → 标记 broken，**丢弃不复用** |
| redisCommand 是 printf 风格 | 拼字符串有注入与格式串风险 | 统一 redisCommandArgv，键与参数分开传 |
| redisReply 需手动 freeReplyObject | 泄漏高发 | RAII ReplyPtr |

### 5.2 结构与 RAII

~~~text
RedisPool (facade)
  └─ shared_ptr<RedisCore>
       ├─ idle: deque<unique_ptr<redisContext, RedisCloser>>
       └─ mutex / cv / stopping / stats

RedisConn (move-only)
  ├─ shared_ptr<RedisCore> core_
  ├─ unique_ptr<redisContext, RedisCloser>
  ├─ broken_
  └─ ~RedisConn() { core_->give_back(std::move(ctx_)); }
~~~

与 MysqlPool 同构的 core 强引用方案，解决退出顺序问题。RedisCloser 调 redisFree。

              const std::vector<std::string>& keys,
              const std::vector<std::string>& args,
              RedisReply* reply);              // RedisReply 内部持有 redisReply*
    bool ping();
    bool healthy() const;
};
~~~

get 用 Lookup 而不是 bool：必须把「键不存在」与「Redis 出错」分开，否则会把一次故障当成缓存未命中，进而把请求全打到 MySQL——这正是击穿雪崩的起点。

### 5.3 命令封装规则

| 规则 | 说明 |
|---|---|
| 全部用 redisCommandArgv | 不做 "GET " + key 拼接；键里出现空格/二进制也不会错 |
| 二进制安全 | 值用 (const char*, size_t) 传，不依赖 strlen |
| 单条命令单次往返 | v2 不做 pipeline（Phase 7 若需要再加；pipeline 会拉长连接占用时间） |
| 禁止阻塞命令 | 池化连接上禁止 BLPOP/BRPOP/SUBSCRIBE；会永久占住连接 |
| 大 value 上限 | 单 value ≤ 64KB；文件内容绝不进 Redis |
| AUTH/SELECT | 建连后立即执行；失败则关闭该连接，不进入池 |
| 错误分层 | ctx->err = 连接级（丢弃连接）；reply->type == ERROR = 命令级（连接可复用，返回错误） |
| WRONGTYPE | 说明键的 schema 冲突：记 ERROR、DEL 坏键、本次按未命中处理（可自愈） |

### 5.4 超时、重连与错误分类

| 项 | 值 | 说明 |
|---|---|---|
| connect_timeout | 200ms | 本机/内网 Redis，200ms 足够；超时说明故障 |
| command_timeout | 300ms | 通过 redisSetTimeout 设置 SO_RCVTIMEO/SO_SNDTIMEO |
| acquire_timeout | 200ms | 池耗尽时快速失败 |
| idle_timeout | 60s | 空闲连接回收（保留 min_size） |
| health_interval | 30s | 空闲超过 30s 的连接借出前 PING |

重连流程（无 redisReconnect）：

1. 命令返回连接级错误或 IO 超时 → broken_=true，归还时销毁，不入 idle。
2. 下一次 acquire 发现 idle 为空 → 新建连接（redisConnectWithTimeout + AUTH + SELECT）。
3. 连续 3 次建连失败 → 熔断 5s，快速返回 RedisUnavailable。
4. 恢复后先 PING 探测，成功再放量。

**为什么超时后不能复用**：hiredis 是请求-回复流水线协议。读超时发生时，服务端的回复可能还在 socket 缓冲区里；此时再发 GET，读到的会是上一条命令的回复。轻则数据错乱，重则把 A 用户的值返回给 B 用户。这是必须「超时即弃」的原因。

### 5.5 池参数

| 参数 | 默认 | 理由 |
|---|---|---|
| min_size | 2 | 预热；会话与热点键读取 |
| max_size | 8 | Redis 单线程处理命令，连接数超过核数收益递减；8 足够覆盖业务线程的并发阻塞 |
| acquire_timeout | 200ms | 比 MySQL 更短：缓存是加速层，等不到就应该走降级路径 |
| idle_timeout | 60s | 与 MySQL 一致 |

### 5.6 eval 与原子性

限流与「比较并删除锁」必须原子，用 Lua：

~~~lua
-- 固定窗口计数：INCR + 首次设置过期
local v = redis.call('INCR', KEYS[1])
if v == 1 then
  redis.call('PEXPIRE', KEYS[1], ARGV[1])
end
return v
~~~

~~~lua
-- 释放锁：只删自己的锁
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
end
return 0
~~~

规则：

- 脚本作为常量字符串放在代码里，**不拼接任何用户输入**；用户输入只通过 KEYS/ARGV 传。
- eval 的 keys 数量必须正确（集群模式下还要求同槽；本期单实例，但接口按 keys/args 分离设计，便于以后迁移）。
- 脚本执行时间必须短（<1ms），禁止在 Lua 里循环大集合。

## 6. 缓存设计

### 6.1 Key 规范与 TTL

格式：cm:{ver}:{domain}:{id}，全小写，冒号分隔，不含空格。ver 用于整体失效（结构变更时 +1）。

| Key | 内容 | 基础 TTL | 写/失效时机 |
|---|---|---|---|
| cm:v1:sess:{token} | Hash：uid、client_id、login_at | 30min 滑动 | 登录写；登出/改密删；剩余 <20min 时续期 |
| cm:v1:usr:{uid} | 用户基本信息（不含密码） | 10min | 改名/禁用时删 |
| cm:v1:file:md5:{md5} | f_id | 60min | 上传完成写；blob 删除时删 |
| cm:v1:file:id:{fid} | size/path/state | 10min | 状态变更时删 |
| cm:v1:share:{code} | 分享元信息（含文件名、过期时间） | 5min | 创建写；取消/改名/删除时删 |
| cm:v1:share:miss:{code} | 固定串 1 | 60s | 查不到时写（空值缓存） |
| cm:v1:up:bitmap:{task} | 已完成分片位图 | 24h | 分片完成时 SETBIT；任务结束删 |
| cm:v1:rl:ip:{ip}:{win} | 计数 | 窗口长度 | INCR + 首次 PEXPIRE |
| cm:v1:lock:rebuild:{key} | 锁持有者 token | 3s | 重建缓存时 SET NX PX |
| cm:v1:dl:ticket:{token} | fid/uid/exp | 5min | 签发下载直链时写 |

**不缓存目录列表**：一次上传/删除/重命名/移动会影响多个列表键，失效面大、一致性问题多；列表查询本身走索引，单用户量级下 <5ms。这是刻意不做，不是遗漏。

### 6.2 Cache-Aside 读写路径

读：

~~~mermaid
flowchart TD
    A[读请求] --> B{GET key}
    B -->|Hit| C[反序列化返回]
    B -->|Miss| D{本地 single-flight}
    D -->|已有加载者| E[等待 ≤200ms]
    E -->|完成| C
    E -->|超时| F[读 DB]
    D -->|我是加载者| G{Redis SET NX 锁}
    G -->|拿到| H[二次 GET 双检]
    H -->|Hit| C
    H -->|Miss| I[查 DB]
    I -->|存在| J[SET 带抖动 TTL]
    I -->|不存在| K[SET 空值标记 60s]
    J --> L[释放锁 Lua compare-del]
    K --> L
    G -->|没拿到| M[睡 20ms 重试 ≤3 次]
    M -->|仍失败| I
~~~

写（更新/删除）：

1. 先提交 DB 事务。
2. 事务提交后 DEL 缓存；失败重试 1 次，再失败记 WARN，靠 TTL 兜底。
3. **删除而不是更新缓存**：并发读可能把旧值写回；删除让下一次读重新加载，窗口更小。
4. 对强一致要求高的键（分享状态、用户禁用）追加「延迟双删」：提交后立即删 + 500ms 后异步再删一次。

**为什么不用先删缓存再写 DB**：写 DB 失败会留下空缓存 + 旧数据；先提交再删，失败最多是短时间旧值，且 TTL 可控。

### 6.3 缓存穿透

| 手段 | 做法 |
|---|---|
| 参数校验前置 | md5 必须 32 位 hex、分享码必须 9 位数字、id 必须正整数；不合法直接拒绝，不查缓存也不查 DB |
| 空值缓存 | 查不到写 cm:v1:share:miss:{code}=1，TTL 60s；读路径把它当 Miss 返回，不再打 DB |
| 短 TTL | 空值只挡 60s，避免「后来创建了但缓存仍说没有」的窗口过长 |
| 限流 | 分享码查询按 IP 限流（5 次/分钟失败后锁定 10 分钟），防止枚举 9 位码 |

**不使用布隆过滤器**：数据量小（分享码 10 万级），删除需要计数布隆或重建，维护成本高于收益；空值缓存 + 限流已经覆盖主要风险。

### 6.4 缓存击穿

热点键过期瞬间，大量请求同时回源。

两层 single-flight：

1. **进程内**：std::unordered_map<std::string, std::shared_ptr<RebuildSlot>> + mutex。第一个线程创建 slot 并加载，其余线程在 slot 的 condition_variable 上等（最多 200ms）；加载完成广播。避免同进程内 N 个线程查同一条 DB。
2. **跨进程**：SET cm:v1:lock:rebuild:{key} <token> NX PX 3000。
   - 拿到锁：二次 GET 双检（可能别人刚填好）→ 查 DB → 回填 → Lua compare-del 释放。
   - 没拿到：sleep 20ms + 抖动重试，最多 3 次（总等待 ≤100ms）；仍失败则**直接查 DB** 并打点 cache_rebuild_fallback_total。

为什么最后允许直接查 DB：锁的作用是削峰，不是正确性依赖。让请求在 100ms 后失败，比让它多打一次 DB 更糟（可用性优先）。真正防止打穿的是入口限流 + 连接池上限。

锁的 TTL 必须大于最慢查询（3s > 200ms 慢查询阈值）；持锁进程崩溃后锁自动过期，不会永久死锁。

### 6.5 缓存雪崩

| 手段 | 做法 |
|---|---|
| TTL 抖动 ±10% | ttl = base × (1000 + rand(-100,100)) / 1000，避免同一批键同时过期 |
| 不批量预热 | 本期不做启动预热；需要时按 key 逐个加随机延迟，禁止 for 循环同一秒写几万个键 |
| 降级路径明确 | Redis 整体挂掉时按第 7 节分场景处理，不把所有请求直接转给 MySQL |
| 熔断 | Redis 连续失败 3 次 → 5s 内快速失败，避免每请求 300ms 超时拖死业务线程 |
| 内存策略 | maxmemory 512mb + volatile-lru（只淘汰带 TTL 的键）；禁用 allkeys-lru，避免把无 TTL 的锁/计数键淘汰后语义错乱 |

### 6.6 一致性边界

| 事件 | 需要删除的键 | 说明 |
|---|---|---|
| 上传完成 | file:md5:{md5}、file:id:{fid} | 新 blob 可被秒传 |
| 删除文件 | share:{code}（若有）、file:id:{fid} | 分享失效；f_id 元信息可保留到 TTL |
| 重命名/移动 | share:{code} | 分享页展示名来自节点 |
| 取消分享 | share:{code} | |
| 用户改名/禁用 | usr:{uid}、sess:*（禁用时按 uid 索引删） | 禁用需要立刻踢下线；本期可接受 30min 内自然过期，若要强踢需维护 uid→token 集合 |
| 播放进度 | 不缓存 | 直接写 MySQL，读时按需查 |

**一致性等级**：最终一致，窗口 ≤ TTL（最长 10 分钟）。项目不引入 CDC/消息队列，这是明确取舍；对「取消分享立即生效」这类强需求，用删除 + 延迟双删保证秒级。

## 7. 降级策略

### 7.1 总表

| # | 场景 | 依赖 | 故障表现 | 降级动作 | 用户可见 |
|---|---|---|---|---|---|
| 1 | 秒传 MD5 查询 | Redis | 连接失败/超时 | 直接查 t_file.uk_f_md5（超时 300ms） | 功能正常，稍慢 |
| 2 | 分享码校验 | Redis | 连接失败/超时 | 直接查 t_share.uk_s_code | 功能正常，稍慢 |
| 3 | 会话 token 鉴权 | Redis | 连接失败/超时 | **拒绝服务**，返回 ERR_AUTH_UNAVAILABLE | 503「请稍后重试」 |
| 4 | 单 IP 限流 | Redis | 连接失败/超时 | **拒绝服务**，返回 ERR_RATE_LIMIT_UNAVAILABLE | 503 |
| 5 | 下载直链校验 | Redis | 连接失败/超时 | 拒绝新签发；已签发 token 校验失败 → 拒绝下载 | 403/503 |
| 6 | 上传分片位图 | Redis | 缓存不可用 | 查 t_chunk 重算（WHERE c_task_id=? AND c_state=1） | 续传稍慢 |
| 7 | 缓存重建锁 | Redis | 锁命令失败 | 直接读 DB + 本地 single-flight | 无感 |
| 8 | 任意写操作 | MySQL | 连接失败/超时 | 失败，不降级 | 503 |
| 9 | 任意读操作 | MySQL | 连接失败/超时 | 失败（无只读副本） | 503 |
| 10 | 连接池耗尽 | MySQL | acquire 超时 | 快速失败 + Retry-After: 1 | 503 |

### 7.2 逐条理由

**1. 秒传 MD5 查询：可降级到 MySQL。**
正确性来源是 t_file.uk_f_md5 唯一索引，不是 Redis。Redis 只是把一次主键查询提前到内存。降级后 QPS 会打到 MySQL，但秒传是低频操作（用户点上传时一次），且必须带限流；DB 扛得住。

**注意**：MySQL 超时不能当「未命中」。未命中意味着要新建 blob 并插 t_file，误判会多存一份内容（虽然唯一索引会拦住，但会返回错误）。超时一律返回 DbBusy，让客户端重试。

**2. 分享码校验：可降级到 MySQL。**
分享是读多写少，uk_s_code 是唯一索引点查，单条 <1ms。风险是热点分享被刷导致 DB 压力，因此降级期间同时启用 IP 限流；限流本身若也不可用，见第 4 条。

**3. 会话 token 鉴权：不可降级，拒绝服务。**
三个原因：

- **不能 fail-open**：缓存挂了就放行，等于任何人裸奔；鉴权是安全边界，不是性能优化。
- **没有第二数据源**：会话只存 Redis，MySQL 没有 session 表。要降级就得新增一张表 + 双写，等于把缓存变成「又一个数据库」，复杂度和故障面都变大。
- **DB 会被打穿**：每个请求都查鉴权表，QPS 放大 10 倍以上，MySQL 会先于 Redis 挂掉，故障从「登录不可用」扩大为「全站不可用」。

正确做法是快速失败 + 告警 + 让 Redis 尽快恢复（哨兵/重启），而不是静默降级。

**4. 单 IP 限流：不可降级，拒绝服务。**
限流失效 = 攻击面完全打开，尤其登录、分享码枚举、上传接口。降级到「进程内令牌桶」看似可用，但在多实例/多进程下每个实例各有一份配额，实际配额被放大 N 倍；且本项目的限流计数是安全能力，不是体验优化。宁可 503，也不放开。

**5. 下载直链：不可降级。**
直链 token 是「一次性授权凭证」，Redis 存 token→(uid,fid,exp) 映射。Redis 挂时无法判断 token 是否被撤销/是否属于该用户；此时放行等于允许越权下载任意 blob。拒绝是唯一安全选择。已建立的 TCP 下载连接不受影响（token 在握手时已校验），只影响新请求。

**6. 上传分片位图：可降级。**
t_chunk 是权威数据，Redis 位图只是把「哪些片已完成」一次读出来。降级后 ContinueUpload 多一次索引查询（(c_task_id,c_index) 聚簇，很快），用户体验是续传响应慢几十毫秒，可接受。

**7. 缓存重建锁：可降级。**
锁用于削峰，不参与正确性。拿不到锁直接查 DB，最坏是多几条并发查询；配合连接池上限与入口限流，不会雪崩。

**8/9. MySQL 故障：不降级。**
单实例、无只读副本、无本地缓存可当数据源。此时写全部失败、读也失败，返回 503 并告警；不做「假降级」（例如返回空列表），那会让用户以为文件丢了。

**10. 连接池耗尽：快速失败。**
排队只会把延迟从 500ms 放大到数秒，并占满业务线程。返回 503 + Retry-After: 1 让客户端退避，是更负责任的做法。

### 7.3 超时预算与熔断

| 层 | 预算 | 说明 |
|---|---|---|
| Redis connect | 200ms | 内网 |
| Redis command | 300ms | 含 GET/SET/EVAL |
| MySQL acquire | 500ms | 含建连失败重试 |
| MySQL 单条查询 | 2000ms | max_execution_time（只读） |
| MySQL 锁等待 | 5s | innodb_lock_wait_timeout |
| 单请求存储总预算 | ≤800ms（P99 目标） | 超过即视为设计问题，不是调参问题 |

熔断：每个依赖独立计数，连续失败 3 次 → OPEN 5s → HALF_OPEN 放 1 个探测 → 成功 CLOSE / 失败重新 OPEN。OPEN 期间直接返回 Unavailable，不产生网络等待。

### 7.4 错误码

在 common/base/error_code.h 的存储段新增（具体数值在实施时分配，避免与协议/业务段冲突）：

| 名称 | 语义 | 可重试 |
|---|---|---|
| DbUnavailable | MySQL 不可达/熔断 | 是（退避后） |
| DbPoolTimeout | 连接池耗尽 | 是 |
| DbQueryFailed | SQL 执行失败 | 否 |
| DbTxConflict | 死锁/锁等待超时 | 是（事务重跑） |
| RedisUnavailable | Redis 不可达/熔断 | 是（退避后） |
| CacheRebuildFailed | 回填失败 | 否（下次读再试） |
| AuthUnavailable | 鉴权依赖不可用 | 是 |
| RateLimitUnavailable | 限流依赖不可用 | 是 |

错误响应只回通用文案（「服务繁忙，请稍后重试」），不把 SQL、主机名、连接串回给客户端。

## 8. CMake 接入

### 8.1 选项

在 cmake/options.cmake 追加：

~~~cmake
if(WIN32)
    set(_cm_default_storage OFF)
else()
    set(_cm_default_storage ON)
endif()

option(BUILD_STORAGE "Build MySQL/Redis storage layer (Linux only)" ${_cm_default_storage})
option(ENABLE_DB_INTEGRATION_TESTS "Run storage tests against real MySQL/Redis" OFF)

if(BUILD_STORAGE AND WIN32)
    message(FATAL_ERROR
        "BUILD_STORAGE is Linux-only: libmysqlclient and hiredis are not bundled on Windows.")
endif()

if(BUILD_SERVER AND NOT BUILD_STORAGE)
    message(WARNING
        "BUILD_SERVER=ON with BUILD_STORAGE=OFF: server will run without persistence.")
endif()

if(BUILD_STORAGE AND NOT BUILD_SERVER)
    message(WARNING
        "BUILD_STORAGE=ON requires BUILD_SERVER=ON; cm_storage will not be built.")
endif()
~~~

默认值理由：Linux 是服务端目标平台，存储层是 Phase 4 之后的默认能力；Windows 只构建客户端，thirdparty 里没有 mysqlclient/hiredis 的 32 位库，强行 ON 只会得到一堆链接错误，不如直接 FATAL 并说明原因。

### 8.2 依赖定位（兼容 cmake 3.5，不联网）

**顺序**：mysql_config 只作为 HINT，最终以 find_path / find_library 为准。理由：mysql_config --libs 的输出包含 -L/-l/-Wl 混合参数，在 CMake 里解析容易出错；HINT 足够定位，链接由 imported target 统一表达。

~~~cmake
function(cm_find_mysql)
    if(TARGET cm::mysql)
        return()
    endif()

    set(_mysql_include_hint "")
    set(_mysql_library_hint "")

    find_program(MYSQL_CONFIG_EXECUTABLE NAMES mysql_config mariadb_config)
    if(MYSQL_CONFIG_EXECUTABLE)
        execute_process(
            COMMAND ${MYSQL_CONFIG_EXECUTABLE} --include
            OUTPUT_VARIABLE _mysql_include_flags
            OUTPUT_STRIP_TRAILING_WHITESPACE
            ERROR_QUIET)
        string(REPLACE "-I" "" _mysql_include_flags "${_mysql_include_flags}")
        separate_arguments(_mysql_include_hint UNIX_COMMAND "${_mysql_include_flags}")

        execute_process(
            COMMAND ${MYSQL_CONFIG_EXECUTABLE} --libs
            OUTPUT_VARIABLE _mysql_libs
            OUTPUT_STRIP_TRAILING_WHITESPACE
            ERROR_QUIET)
        string(REGEX MATCHALL "-L[^ ]+" _mysql_lib_dirs "${_mysql_libs}")
        string(REPLACE "-L" "" _mysql_library_hint "${_mysql_lib_dirs}")
    endif()

    find_path(MYSQL_INCLUDE_DIR
        NAMES mysql.h
        HINTS ${_mysql_include_hint}
        PATH_SUFFIXES mysql mariadb)
    find_library(MYSQL_LIBRARY
        NAMES mysqlclient mariadb
        HINTS ${_mysql_library_hint})

    if(NOT MYSQL_INCLUDE_DIR OR NOT MYSQL_LIBRARY)
        message(FATAL_ERROR
            "libmysqlclient not found. Install it (Ubuntu: apt-get install libmysqlclient-dev) "
            "or set MYSQL_INCLUDE_DIR / MYSQL_LIBRARY explicitly.")
    endif()

    add_library(cm::mysql UNKNOWN IMPORTED)
    set_target_properties(cm::mysql PROPERTIES
        IMPORTED_LOCATION "${MYSQL_LIBRARY}"
        INTERFACE_INCLUDE_DIRECTORIES "${MYSQL_INCLUDE_DIR}")
endfunction()
~~~

~~~cmake
function(cm_find_hiredis)
    if(TARGET cm::hiredis)
        return()
    endif()

    find_path(HIREDIS_INC NAMES hiredis/hiredis.h)
    find_library(HIREDIS_LIB NAMES hiredis)

    if(NOT HIREDIS_INC OR NOT HIREDIS_LIB)
        message(FATAL_ERROR
            "hiredis not found. Install it (Ubuntu: apt-get install libhiredis-dev) "
            "or set HIREDIS_INC / HIREDIS_LIB explicitly.")
    endif()

    add_library(cm::hiredis UNKNOWN IMPORTED)
    set_target_properties(cm::hiredis PROPERTIES
        IMPORTED_LOCATION "${HIREDIS_LIB}"
        INTERFACE_INCLUDE_DIRECTORIES "${HIREDIS_INC}")
endfunction()
~~~

注意：

- UNKNOWN IMPORTED 在 3.5 可用；不用 3.6 才支持的 IMPORTED_TARGET（pkg_check_modules(... IMPORTED_TARGET)）。
- 不使用 FetchContent、ExternalProject、include(GoogleTest)、gtest_discover_tests、target_link_options、add_compile_definitions。
- 若系统只有 libmysqlclient.a（静态库），需要把 mysql_config --libs 里的 -lssl -lcrypto -lz -ldl -lpthread 一并挂到 INTERFACE_LINK_LIBRARIES；优先使用发行版共享库，避免这层复杂度。

## 9. 风险与未决

### 9.1 风险

| 风险 | 影响 | 对策 |
|---|---|---|
| 唯一索引约 1044 字节依赖 large_prefix | 5.6/compact 行格式建表失败 | 锁定 MySQL 5.7 + DYNAMIC；建表脚本显式声明；启动自检 @@innodb_large_prefix |
| 无外键导致孤儿数据 | 列表出现坏条目、blob 泄漏 | 事务边界固定 + 每日对账 SQL + 告警；不自动删 |
| 软删唯一键的同微秒冲突 | 删除同目录两个同名节点极低概率失败 | 捕获 1062 后将 uf_deleted_at +1µs 重试 |
| 迁移期间硬链接不可用 | 需要双倍磁盘 | 迁移前 df 预估；空间不足则分批复制并延长窗口 |
| 旧密码是 MD5 | 迁移后仍弱 | 登录成功即升级；30 天内未登录账号强制重置 |
| 连接池参数拍脑袋 | 高并发下排队 | Phase 7 用压测校准；采集 waiters/acquire_timeout |
| Redis 单实例 | 宕机即鉴权不可用 | 明确 fail-closed；后续可加 Sentinel，不改接口 |
| hiredis 0.13 无 reconnect | 断线重建有开销 | 池层重建 + 熔断；不在请求路径反复重试 |

### 9.2 未决（不阻塞 Phase 4 实施）

1. 分享默认有效期 7 天是否合适；旧分享迁移统一 +7 天需产品确认。
2. 是否支持目录分享（影响 s_file_id 语义与转存展开逻辑）。
3. MySQL 是否直接上 8.0（可用 CTE/窗口函数/DESC 索引；但与 16.04 默认源不符）。
4. 密码算法是否升级到 bcrypt/Argon2（需引入第三方库，与「不联网」约束冲突）。
5. 是否需要文件版本历史（当前不做；若做需新增 t_file_version，t_user_file 指向版本而非内容）。
6. 会话强踢（禁用用户立即下线）是否必须；当前依赖 TTL，最长 30 分钟。
