## 0. 结论速览

| # | 决策 | 一句话理由 |
|---|---|---|
| 1 | 10000~10029 保持旧语义，**启用 10011/10024 两个废弃槽位**，新增消息从 **10030** 起 | 30 个旧槽位已全部占用；强制升级 v2 后旧语义无流量，复用比新开号段更省映射成本 |
| 2 | 分享码改为 **6 位、31 字符表**（去掉 0/O/1/I/L），不再用 9 位数字 | 口头/手输友好；31^6≈8.9 亿，配合限流足以抗枚举 |
| 3 | 上传分片固定 **4MB**，分片与下载块同尺寸；续传以 **t_chunk 位图**为唯一事实，tr_offset 只是派生值 | 一套块尺寸贯穿上传、下载、CRC sidecar，避免边界换算 |
| 4 | 同一 task 的并发控制用 **InnoDB 行锁**，不用 Redis 锁 | 单实例、DB 是事实源、崩溃自动释放；Redis 锁只增加 TTL/续租/脑裂故障面 |
| 5 | 合并选主用 **条件 UPDATE（status 1→7）**，不用锁对象 | 一条 SQL 完成选举，affected_rows=1 者合并，天然幂等 |
| 6 | 下载采用 **4MB 块对齐 Range**，不做任意字节 Range | 与上传块、CRC sidecar 对齐；续传粒度 4MB，换来零拷贝与可验证 CRC |
| 7 | 下载零拷贝用 **sendfile + 上传期块 CRC + crc32Combine**；sidecar 缺失时回退“IO 池缓冲读 + 流式 CRC” | 02 要求 CRC 覆盖 11 字节头 + payload，sendfile 又不能读 payload；combine 是唯一同时满足两者的办法 |
| 8 | 下载限速用 **每连接令牌桶 + 每用户总配额**，令牌不足用定时器延迟，不 sleep | 不在 IO 线程阻塞；慢客户端只占自己的连接 |
| 9 | 秒传命中仍要落 **t_user_file** 并 ref_count+1；Redis 只省掉 blob 查找 | “秒传”省的是上传字节，不是数据库关系 |
| 10 | 分享访问 **只读**，不计引用计数；只有转存/新增节点才 ref_count+1 | 计数语义是“有多少未删除的用户节点指向 blob” |
| 11 | 彻底删除后 **24h 宽限 + 对账 + 分批 unlink**，自动回收 blob 与 .crc | 用户要求可回收，05 的“纯运维脚本”无法闭环；宽限避免误删与并发读 |
| 12 | 列表分页一律 **游标（keyset）**，禁止 OFFSET；排序键末尾必须带 uf_id | 大偏移会线性扫描；同秒多行靠主键做稳定 tie-break |
| 13 | 大帧（4MB 上传）CRC **移到业务线程校验**，IO 线程只解析帧头并移交 payload | 避免 4MB CRC 在 Reactor 线程造成 3~8ms 全连接停摆 |
| 14 | 新增 upload_cli / download_cli 作为 Phase 5 验收工具，客户端 UI 仍留到 Phase 8 | 业务正确性先用命令行与集成测试锁死，避免 UI 干扰定位 |

## 1. 范围、假设与对既有文档的修订

### 1.1 范围

**做：**

- 协议：上传初始化/分片/确认/完成、秒传预检、续传查询、下载打开/取块/完成、分享创建/列表/访问/取消、播放上报、回收站列表/恢复/彻底删除、文件列表分页。
- 上传：4MB 分片、分片 MD5、整文件 MD5、合并、秒传、断点续传、过期清理。
- 下载：块对齐 Range、4 连接并发（客户端）、sendfile、令牌桶、断点续传。
- 分享：6 位分享码、1 天/7 天/永久、可选 4 位提取码。
- 回收站：软删、恢复、彻底删除、引用计数归零后的 blob 回收。
- 分页、缓存降级表、端到端 CLI 与测试方案。

**不做（明确边界）：**

- 不做多端同步、转存到我的网盘（t_transfer_task.tr_type=2 留到后续）、目录打包下载、zip。
- 不做多清晰度转码、HLS（Phase 9）。
- 不做回收站保留期策略（只有手动彻底删除）；不做定时清空回收站。
- 不做断点续传的字节级粒度（块对齐，最坏重传 4MB）。
- 不做跨连接会话恢复：断线后客户端重新登录；下载并发连接共享同一 ticket。
- 不做分享码自定义、二维码、提取码修改。

10000~10029 共 30 个槽位在 message_type.h 中已全部占用，其中 10011（DownloadFolderRq）与 10024（FolderHeaderRq）在 02 中被标记废弃。Phase 5 需要的新消息超过剩余槽位，因此：

| 处理 | 类型号 | 原语义 | 新语义 | 理由 |

| 复用 | 10011 | DownloadFolderRq（废弃） | **DownloadDataRs（S→C，原始块）** | 下载数据没有独立响应槽位；旧语义已无流量 |
| 复用 | 10024 | FolderHeaderRq（废弃） | **QuickUploadRs（S→C）** | 10017 只有 RS 没有 RQ，正好配对 |
| 新增 | 10030~10043 | — | 上传完成、播放上报、回收站、下载完成、分享取消 | 仍在 02 定义的 10000~10999 业务段内 |

被复用的两个类型号**不再返回 ERR_DEPRECATED**；9007 保留给未来真正退役的类型。旧客户端因强制升级 v2 + HELLO 校验无法连入，复用不会造成线上歧义；但日志/回放工具必须按 v2 类型表解释，不能按旧 packdef.h。

### 1.3 与 02 / 05 的冲突与裁决

#### 冲突 1：分享码 6 位 vs 9 位数字

需求要求“6 位、避开易混淆字符”，但 sql/schema_v2.sql 是 s_code CHAR(9)，CacheKey::share/shareMiss 也硬编码 size()==9 && isdigit。

**裁决：采用 6 位 31 字符表**，字符集 23456789ABCDEFGHJKMNPQRSTUVWXYZ（去掉 0/O/1/I/L）。需要配套改动：

- s_code 改为 CHAR(6) CHARACTER SET ascii，唯一索引不变。
- CacheKey::share/shareMiss 继续复用（函数名与 cm:v1:share: 前缀不变），只把“9 位数字”校验改为“6 位字符表 + 大写归一”。
- 分享码在 URL/界面展示时统一大写，输入允许小写与空格（服务端归一化）。

**候选对比：**

| 方案 | 空间 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| 9 位数字（现状） | 10^9 | 实现零改动 | 手输/口述长，9 位仍可能念错 | 否 |
| 6 位数字 | 10^6 | 短 | 10 万分享时碰撞概率高；枚举 100 QPS 约 2.8 小时 | 否 |
| **6 位 31 字符** | 8.87×10^8 | 短、无易混字符、空间足够 | 需改 DDL 与 CacheKey 校验 | **采用** |
| 7 位 31 字符 | 2.75×10^10 | 更安全 | 超出“6 位”要求 | 备选 |

碰撞估算：10 万有效分享，生日期望碰撞 n²/(2N) ≈ 5.6 次（生命周期累计），单次插入碰撞概率约 1.1×10⁻⁴；INSERT 捕获 1062 后重试，最多 5 次。枚举估算：31^6≈8.87 亿，100 QPS 全空间约 102 天，叠加“5 次/分钟”限流后不可行。

#### 冲突 2：sendfile 零拷贝 vs 帧 CRC 覆盖 payload

02 规定 CRC32 覆盖 VERSION+TYPE+LEN+SEQ 共 11 字节 + payload（环境规则中的硬规则）。sendfile 只把页缓存直接送进 socket，不经过用户态，无法计算 payload CRC。

**裁决：上传合并时按 4MB 块计算并落 sidecar CRC，下载时用 crc32Combine 把“11 字节头 CRC”和“块 CRC”合成整帧 CRC，再 sendfile。** sidecar 缺失（迁移旧 blob）时回退缓冲读路径。

| 方案 | 零拷贝 | 符合 CRC 规则 | 代价 | 结论 |
|---|---|---|---|---|
| 缓冲读 4MB + 流式 CRC + send | 否 | 是 | IO 池 memcpy/CRC，内存峰值高 | 回退路径 |
| **sendfile + 块 CRC + combine** | 是 | 是 | 新增 .crc sidecar、combine 需单测 | **默认路径** |
| bulk 帧不校验 payload | 是 | 否 | 破坏协议硬规则 | 禁止 |
| 改 CRC 只覆盖帧头 | 是 | 否 | 同上 | 禁止 |

crc32Combine(crc1, crc2, len2) 与 zlib 的 crc32_combine 等价，返回 CRC(A||B)；必须用 crc32(header11||payload) 的直接计算做对照测试。

#### 冲突 3：05 的“不物理删 blob” vs 回收站彻底删除

05 的结论是“删除只减引用计数，不物理删 blob，孤儿由运维脚本回收”。Phase 5 要求“彻底删除 + 磁盘回收”，纯运维脚本无法闭环。

**裁决：保留软删 + 宽限，但增加自动孤儿回收**：

1. 软删/彻底删除只把 f_ref_count 减到 0，置 f_state=2，不立即 unlink。
2. 每日 03:00 的 GC 任务在 24h 宽限后，重新校验无活跃节点、无有效分享，才 unlink blob 与 .crc，最后删 t_file 行。
3. 保留 scripts/reconcile.sql 作为第二道对账；GC 失败只告警，不自动重试删除。

这比“立即 unlink”安全（避免分享/播放/并发下载持有引用），也比“永不回收”符合产品预期。

#### 冲突 4：目录软删不级联 vs 彻底删除目录

05 明确目录软删不级联（避免长事务与大量行锁）。本设计保留该结论：

- 删除目录只改该节点 uf_deleted_at；子节点原状保留，从根遍历不可达。
- 回收站展示该目录节点；恢复后子树重新可达。
- 彻底删除目录时按子树批量物理删除（每批 200 行），活跃子节点视为删除并递减引用计数；节点数超过 10000 返回 TooManyNodes。

## 2. 错误码与映射

### 2.1 三层错误

| 层 | 载体 | 范围 | 连接动作 |
|---|---|---|---|
| 协议层 | ERROR_RS（11002），code=9xxx | 帧头、CRC、版本、握手、未知类型 | 回包后关闭 |
| 业务层 | **业务 RS 的 u32 code 字段** | 参数、权限、状态、存储依赖 | 保持连接 |
| 数据面 | ERROR_RS（仅 10013 取块失败） | 取块请求没有结构化 RS | 保持连接 |

**为什么业务错误不统一走 ERROR_RS**：上传完成失败要带“坏分片下标列表”，限流要带“建议重试时间”，ERROR_RS 只有 code + message，无法结构化表达；业务 RS 自带 code 可以一次往返说清。

### 2.3 4001~4008 的映射

这 8 个码是“存储依赖”错误，**不暴露 SQL/主机/连接串**，只作为 RS.code 返回：

| 码 | 名称 | 出现接口 | 客户端可见 | 重试 | 服务端动作 |
|---|---|---|---|---|---|
| 4001 | DbUnavailable | 所有读写 | 是 | 1s 后 | 熔断期间快速失败 |
| 4002 | DbPoolTimeout | 所有读写 | 是 | 1s 后 | acquire 500ms 超时 |
| 4003 | DbQueryFailed | 所有读写 | 是 | 否 | 记 ERROR（占位符 SQL） |
| 4004 | DbTxConflict | 上传完成、删除、恢复 | 是 | 立即 | 服务端已自动重跑 2 次 |
| 4005 | RedisUnavailable | 秒传、分享、ticket | 是 | 1s 后 | 按第 10 节决定 fail-open/closed |
| 4006 | CacheRebuildFailed | 内部 | **否** | — | 只记日志，不回给客户端 |
| 4007 | AuthUnavailable | 所有需登录接口 | 是 | 1s 后 | 鉴权 fail-closed |
| 4008 | RateLimitUnavailable | 限流相关接口 | 是 | 1s 后 | 限流 fail-closed |

规则：

- 4006 永远不进入 wire；缓存回填失败由 TTL 兜底。
- 4001/4002/4005/4007/4008 的“可重试”是**客户端退避重试**，服务端不在请求路径 sleep 重试。
- 写操作遇到 4004 只重跑事务，不重发网络请求；客户端看到 4004 说明服务端两次都冲突，立即重试一次即可。

### 2.4 9xxx 的映射

| 码 | 名称 | 触发 | 是否回 ERROR_RS | 连接 |
|---|---|---|---|---|
| 9001 | BadFrame | MAGIC 错、帧结构非法 | 能解析 SEQ 时回 | 关闭 |
| 9002 | Version | VERSION≠2 | 是 | 关闭 |
| 9003 | UnknownType | 不在类型表 | 是 | 关闭 |
| 9004 | PayloadTooLarge | LEN>8MB、字符串>64KB | 是 | 关闭 |
| 9005 | Crc | 帧 CRC 不符 | 是（不带 payload） | 关闭 |
| 9006 | HandshakeRequired | HELLO 前发业务消息 | 是 | 关闭 |
| 9007 | Deprecated | 预留（Phase 5 无类型使用） | 是 | 关闭 |
| 9008 | Timeout | 90s 空闲、合并等待超时 | 可选 | 关闭 |

**边界**：4xxx 是“请求级”，9xxx 是“连接级”。一个请求失败但连接仍可用时，绝不发 9xxx；一个帧已经坏了，也绝不发业务 RS。

## 4. 消息字段

### 4.0 编码约定

- 整数一律大端；string = u32 长度 + UTF-8 字节；bytes = u32 长度 + 原始字节（serialize.h 的 writeBytes）。
- 每个业务 RS 的第一个字段固定为 u32 code（0=成功）。
- 新增字段只追加到末尾；接收方用 Reader::remaining() 判断是否存在，旧字段顺序不变。
- 时间统一 Unix epoch 毫秒（u64）；DB 内部用 UTC DATETIME(6)。
- file_md5 固定 32 位小写 hex；task_id 固定 32 位小写 hex（UUID 去横线）。
- 单帧 payload ≤8MB；单字符串 ≤64KB。分片数据 4MB+40B 左右，安全。

## 5. 上传

### 5.1 状态机

~~~mermaid
stateDiagram-v2
    [*] --> Pending: UploadInit
    Pending --> Uploading: 第一个分片
    Uploading --> Uploading: 分片/重放
    Uploading --> Merging: Complete 选主成功
    Merging --> Done: 合并+落库成功
    Merging --> Uploading: 坏片/整文件MD5错(保留分片)
    Merging --> Failed: 磁盘满/DB 重试耗尽
    Merging --> Paused: 服务重启恢复
    Pending --> Paused: 服务重启
    Uploading --> Paused: 服务重启
    Pending --> Cancelled: 主动取消
    Uploading --> Cancelled: 主动取消
    Paused --> Cancelled: 主动取消
    Pending --> Expired: 超过 expire_at
    Uploading --> Expired: 超过 expire_at
    Paused --> Expired: 超过 expire_at
    Failed --> [*]
    Done --> [*]
    Cancelled --> [*]
    Expired --> [*]
~~~

| 状态 | 含义 | 允许的请求 |
|---|---|---|
| 0 Pending | 已初始化，未收到分片 | Chunk、Continue、Complete（会因缺片失败）、Cancel |
| 1 Uploading | 至少一片完成，未齐 | Chunk、Continue、Complete、Cancel |
| 2 Paused | 重启/客户端暂停 | Chunk、Continue、Complete、Cancel |
| 3 Failed | 不可恢复失败 | 只读查询；重新 init 新任务 |
| 4 Done | 完成 | Complete 幂等返回、查询 |
| 5 Cancelled | 取消 | 查询 |
| 6 Expired | 过期 | 查询；重新 init |
| 7 Merging | 合并中（新增） | 只读；Complete 返回 3005 重试 |

### 5.2 初始化与秒传

**初始化流程（10004）**：

1. 参数校验：file_md5 32 hex、total_size>0、file_name 非空且≤255 字节、parent_id 是本人目录或 0。
2. req_id 幂等缓存查询 → 命中回放。
3. 秒传查找：
   - cm:v1:file:md5:{md5} 命中 → 得到 f_id；
   - 未命中 → SELECT f_id,size,f_state FROM t_file WHERE f_md5=?（uk_f_md5）；命中回填 Redis，TTL 60 分钟 ±10%；
   - 只有 f_state=1 且 f_size=total_size 才算命中；否则按未命中处理。
4. 命中分支（事务）：
   - 先查同目录同名且同 f_id 的活跃节点 → 存在则直接返回（重试幂等）；
   - 否则插入 t_user_file，名称冲突自动 (2)…(99)；
   - UPDATE t_file SET f_ref_count=f_ref_count+1 WHERE f_id=?；
   - 返回 result=1, uf_id, file_name。
5. 未命中分支：计算 total_chunks=ceil(size/chunk_size)，插入 t_transfer_task（status=0，expire=now+24h），返回 task_id。
6. 写 req 结果缓存（10 分钟），释放短锁。

**为什么秒传命中还要写库**：t_file 是内容实体，t_user_file 才是“用户看到的文件”。只回 file_id 会让用户在列表里看不到文件。Redis 命中只省掉“找 blob”，不省“建立用户关系”。

**为什么 Redis 只是加速**：正确性由 uk_f_md5 唯一索引保证。Redis 挂了走 MySQL；MySQL 也挂才返回 4001/4002。缓存回填失败只记日志（4006 不外泄）。

### 5.3 分片写入

**线程路径**：

~~~text
IO 线程：decodeBulk 解析 10006 帧头（不校验 CRC，不拷贝大 payload）
   └─ 移交 RawFrame（payload 用 move）到业务池
业务池：verifyFrameCrc(header11 + payload)
   ├─ 失败 → 回 9005 + 请求 loop 关闭连接
   ├─ 校验 task/status/index/offset/size/md5
   ├─ 写 tmp/<task_id>/<index>.bin.tmp.<seq> → fsync → rename
   └─ DB 事务：SELECT task FOR UPDATE → upsert chunk → 计数 → 提交
IO 线程：回 10007（done_chunks / next_hint）
~~~

- 写盘在业务池（04 §2.3 允许“分片落盘”），合并才走 IO 池。
- 临时文件名带随机后缀，避免同一 index 的并发写互相覆盖；rename 原子生效。
- fsync 分片后再写 DB；DB 提交成功才回 ack。崩溃时可能出现“文件在、DB 无”的孤儿分片，过期清理按任务目录整删。
- 每连接最多 2 个在途分片任务；超过则 pauseRead()，ack 发出后 resumeRead()。防止一个客户端把业务池队列塞满。

**分片大小边界**：

| 条件 | 期望 |
|---|---|
| index < total-1 | data_len == chunk_size |
| index == total-1 | data_len == total_size - index*chunk_size，且 >0 |
| total_size % chunk_size == 0 | 没有短末片，total_chunks 正好整除 |

### 5.4 大帧与 CRC 的线程边界

02 的 Codec::decode 在 IO 线程完成“拆帧 + CRC”。4MB 的查表 CRC 约 3~8ms，这期间同一 loop 的所有连接停摆，违反 04 的硬约束。

**Phase 5 增加两条窄接口**（P0-2）：

~~~cpp
struct RawFrame {
    std::uint16_t type;
    std::uint32_t seq;
    std::uint32_t len;
    std::uint32_t expectedCrc;
    std::string header11;   // VERSION..SEQ 共 11 字节
    std::string payload;    // 已从 Buffer 移出
};

DecodeStatus decodeBulk(Buffer& in, RawFrame* out);  // 只校验 MAGIC/VER/LEN，不校验 CRC
bool verifyFrameCrc(const RawFrame& frame);          // 业务线程调用
~~~

规则：

1. 只有 10006（上传分片）走 decodeBulk；其余类型仍走 decode，保持 Phase 2 的单测语义。
2. 业务线程在解析任何字段前必须 verifyFrameCrc；失败回 9005 并关闭连接，**不得投递业务**。
3. rawFrame.payload 用 std::move 从 Buffer 取出，避免 4MB 再拷贝一次。
4. 单测：同一帧分别走 decode 与 decodeBulk+verify，CRC 结果必须一致；坏 CRC 必须在业务入口被拦住。

### 5.5 合并

**选主**：

~~~sql
UPDATE t_transfer_task
   SET tr_status = 7, tr_updated_at = NOW(6)
 WHERE tr_task_id = ? AND tr_user_id = ?
   AND tr_status IN (0, 1);
~~~

affected_rows=1 的请求负责合并；=0 时读状态：4→幂等返回，7→3005 重试，6→3007，3/5→3005。

**合并前校验**：

- tr_done_chunks == tr_total_chunks；
- SELECT SUM(c_size) FROM t_chunk WHERE c_task_id=? AND c_state=1 等于 tr_total_size；
- 缺片则回 3002，并带前 32 个缺失下标。

**合并步骤（IO 池，单任务串行）**：

1. 打开 tmp/<task_id>/merged.bin.tmp（O_CREAT|O_TRUNC）。
2. 按 index 升序逐片读：1MB 缓冲；边读边做三件事：
   - 更新整文件 MD5（cm::Md5）；
   - 更新当前 4MB 块的 CRC（cm::Crc32），块满即写入 sidecar 内存数组；
   - 写入 merged 文件。
3. 每片读前 stat 校验 size，读中校验该片 MD5；不符则记录 bad_index，**中止合并**。
4. 全部通过后：fsync(merged)；比较整文件 MD5 与 tr_file_md5。
5. 写 sidecar（<md5>.crc）到临时路径并 fsync；blob 目标路径 data/blobs/aa/bb/<md5>。
6. 若目标 blob 已存在：校验大小一致后删除 merged（同内容，保留已有 inode，避免影响正在读的下载）；否则 rename(merged, blob) 并 fsync 目录。
7. DB 事务（见 5.6）。
8. 删除 t_chunk 行与任务临时目录。

**坏片处理**：删除 bad_index 对应的行与文件，tr_done_chunks -= bad_count，tr_offset 减去这些片的大小（减法前校验不小于被减量，否则置 0 并告警，防止无符号下溢），status 改回 1，回 3002 + 下标列表；客户端只重传坏片。

**整文件 MD5 不符**：说明客户端在分片之间改了源文件。status=3，返回 3003，删除任务临时目录与分片（避免继续浪费磁盘）；客户端必须重新 init。

**并发合并上限**：全局同时最多 2 个合并任务（IO 池固定 4 线程，留 2 个给下载回退路径与 GC）；其余任务在队列等待，Complete 请求保持连接但不阻塞 loop（业务池等待，超 30s 回 1006）。

### 5.6 合并落库事务

顺序固定，全部在一个事务内：

1. INSERT INTO t_file(f_md5,f_size,f_path,f_ref_count,f_state) VALUES(?,?,?,1,1) ON DUPLICATE KEY UPDATE f_ref_count=f_ref_count+1, f_state=1, f_updated_at=NOW(6)；
2. SELECT f_id FROM t_file WHERE f_md5=?；
3. 插入 t_user_file：
   - 名称冲突时在事务内重试 (2)…(99)（1062 是语句级回滚，事务仍可继续）；
   - 若同目录已有同名且同 f_id 的活跃节点（客户端重试），直接复用，不重复插入；
4. UPDATE t_transfer_task SET tr_status=4, tr_offset=tr_total_size, tr_done_chunks=tr_total_chunks WHERE tr_task_id=?；
5. 提交后：SET cm:v1:file:md5:{md5} = f_id（失败只记日志）。

**崩溃窗口与幂等**：

| 崩溃点 | 现象 | 恢复 |
|---|---|---|
| rename 后、事务前 | 任务 7，blob 存在 | 重启把 7 改 2；重试 Complete 时发现 blob 存在且 MD5 正确，跳过 rename，直接落库 |
| 事务中 | 回滚，任务 7 | 同上 |
| 提交后、删分片前 | 任务 4，分片残留 | 过期清理/孤儿清理按任务目录删除 |

**同名文件**：flags bit0=1（默认）时自动改名（name (2).ext），不返回 1003 给用户；flags bit0=0 时冲突返回 1003。自动改名与主流网盘一致，也避免“上传成功但用户找不到”的困惑。

**改名 99 次仍失败**：事务回滚（包括 f_ref_count 的 +1）；若本次是新建 blob（不是复用已存在 blob），由 IO 池 unlink 该 blob 与本次生成的 sidecar，避免留下“磁盘有文件、DB 无行”的孤儿。若 blob 原本就存在，绝不能删。

### 5.7 断点续传

**唯一事实源**：t_chunk 的 (c_task_id,c_index,c_state)。tr_done_chunks 是计数缓存，tr_offset 是字节总和缓存；两者都可以由 t_chunk 重算。

**续传流程**：

1. 客户端持久化 task_id（客户端 SQLite / CLI 状态文件）。
2. 重连后发 10028：服务端查任务状态与过期时间。
3. 服务端 SELECT c_index FROM t_chunk WHERE c_task_id=? AND c_state=1，构造位图；done_chunks=bits set count；done_bytes=SUM(c_size)。
4. 若计数缓存与重算值不一致：以重算值为准，并 UPDATE t_transfer_task 修正（记录 WARN，说明此前有崩溃窗口）。
5. 客户端只发位图中为 0 的片；服务端对已完成的片仍会幂等接受（duplicate=1），防止客户端位图过期。

**服务端重启恢复**：

启动顺序（在 listen 之前）：

1. DB 池就绪；
2. UPDATE t_transfer_task SET tr_status=2 WHERE tr_status=7（合并中断，回到暂停）；
3. IO 池清理 tmp/*/merged.bin.tmp* 与超过 1h 的 *.tmp.*；
4. 启动 expiry tick（每 5 分钟）；
5. listen。

不把 status=1 改成 2：status=1 表示“有未完成分片”，与“当前是否有连接”无关；客户端随时可以续传。

**过期清理**：

- tr_expire_at：init 时 NOW()+24h；每片成功后续期到 LEAST(tr_created_at+7d, NOW()+24h)，避免一次写盘不续期导致大文件传不完。
- 扫描 SQL：WHERE tr_status IN (0,1,2) AND tr_expire_at < NOW(6) ORDER BY tr_expire_at LIMIT 200（命中 idx_expire）。
- 对每个任务：UPDATE ... SET tr_status=6 WHERE tr_task_id=? AND tr_status IN (0,1,2)（条件更新防止和正在上传的请求打架）；然后 DELETE FROM t_chunk WHERE c_task_id=?（每批 500）；最后由 IO 池删任务目录。
- 顺序必须是“先置 6，再删行，再删文件”：置 6 后所有写请求都会被 3007 拒绝；即使删文件失败，任务目录也会被下一次扫描的“孤儿 tmp”规则清掉。

**周期与批量取舍**：

| 参数 | 取值 | 理由 |
|---|---|---|
| 扫描周期 | 5 分钟 | 过期不是实时需求；5 分钟对用户无感，对 DB 压力可忽略 |
| 单批任务数 | 200 | 200 次条件更新 + 200 个目录删除约 100~300ms；1000 会拉长事务/IO 抖动 |
| 分片删除批 | 500 行/事务 | 25k 片的超大任务分 50 批，避免长事务 |
| 单轮时间上限 | 2s | 超时留到下一轮，不阻塞 tick 线程 |

### 5.8 重复分片、乱序与并发锁

**重复分片**：靠 (c_task_id,c_index) 主键 + c_md5 比对，见 4.2。重复 ack 不增加计数。

**乱序**：允许任意顺序。done_chunks 只数“已完成片数”，不要求连续；next_hint 只是优化提示。合并前用 done_chunks==total + SUM(c_size)==total_size 双条件，防止“计数对但内容缺”。

**并发同一 task 的锁粒度：选行锁，不选 Redis 锁。**

| 方案 | 粒度 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| Redis 分布式锁 | task_id | 跨进程/跨机可用 | TTL、续租、崩溃残留、Redis 故障即不能上传；单实例无收益 | 否 |
| **InnoDB 行锁** | SELECT ... FOR UPDATE 锁 t_transfer_task 一行 | 事实源一致、提交/断连自动释放、无额外组件 | 仅单实例有效 | **采用** |
| 全局互斥量 | 进程级 | 最简单 | 所有上传串行，吞吐归零 | 否 |
| 无锁 + 最终校验 | — | 最快 | 计数漂移、重复落库 | 否 |

具体规则：

- 事务内锁顺序固定：**任务行 → 分片行**，禁止反向，避免死锁。
- 事务内不做文件 IO：先写盘，再开事务；事务只做校验 + upsert + 计数，目标 <20ms。
- 合并选主不用锁对象，用 5.5 的条件 UPDATE；affected_rows 就是选主结果。
- 同一用户对同一 task 的并发请求本来就应串行（客户端单连接上传）；行锁的竞争只发生在“重试 + 原请求”重叠的短暂窗口。

### 5.9 上传失败矩阵

| 失败 | 检测点 | code | 任务状态 | 分片 | 客户端动作 |
|---|---|---|---|---|---|
| 分片 MD5 错 | 收到分片时 | 3003 | 不变 | 不写 | 重传该片 |
| offset/长度错 | 收到分片时 | 1001 | 不变 | 不写 | 修正后重传 |
| 任务过期 | 收到分片时 | 3007 | 6 | 清理 | 重新 init |
| 未传完就 complete | 合并前 | 3002 + 缺片表 | 1 | 保留 | 补片 |
| 合并读片失败（文件缺失） | 合并中 | 3002 + bad list | 1 | 删坏片行 | 重传坏片 |
| 分片内容坏（MD5 不符） | 合并中 | 3002 + bad list | 1 | 删坏片行 | 重传坏片 |
| 整文件 MD5 不符 | 合并后 | 3003 | 3 | 清理 | 重新 init |
| 磁盘满 | rename/merge | 1005 | 3 | 清理 | 释放空间后重试 |
| DB 不可用 | 任意 | 4001/4002 | 不变 | 保留 | 退避重试 |
| 死锁 | 事务提交 | 4004 | 不变 | 保留 | 立即重试 |
| 服务重启 | — | — | 7→2 | 保留 | 续传 |

## 6. 下载

### 6.1 打开与票据

**10010 打开流程**：

1. 鉴权：连接已登录（session 绑定 uid）。
2. 若带 share_ticket：校验 Redis cm:v1:share:ticket:{token}，得到 owner_uid/f_id/share_code；否则按 uf_id 查 t_user_file，校验 u_id=当前用户 且 uf_deleted_at=哨兵。
3. 取 t_file：f_state=1，否则 3001。
4. stat blob（业务池，允许阻塞）：大小与 f_size 一致，否则 3001 + 告警。
5. 生成 ticket：32 字节随机 → 64 hex；Redis SET cm:v1:dl:ticket:{token} = "uid|fid|exp|flags" PX 300000。写失败 → 4005/4007，**拒绝**（票据是授权凭证）。
6. 返回元信息与 block_count。

**票据语义**：

- 5 分钟 TTL，**每次成功取块滑动续期**（PEXPIRE），单张票最长 2 小时（value 里写 hard_exp，到点不再续）。
- 不绑定单连接：4 个并发连接共享一张票；但每次取块都校验 ticket.uid == session.uid 且 ticket.fid == req.f_id。
- 票据丢失/Redis 故障 → 拒绝新取块；已建立的在途 sendfile 不受影响（数据已经在内核里）。
- 单张票硬上限 2 小时：超长下载（如 100GB）在到期前重新发 10010（start_block=当前缺失块）换新票，已下载块不重传。

### 6.2 块对齐 Range

| 项 | 取值 | 说明 |
|---|---|---|
| block_size | 4MB（4194304） | 与上传分片一致 |
| block_count | ceil(size/block_size) | |
| 单次请求 | 1 块 | 不做多块聚合，避免单连接长时间占用 |
| 末块 | size - (block_count-1)*block_size | 1~4MB |
| 续传粒度 | 1 块 | 最坏重下 4MB，换 CRC/零拷贝一致性 |

**客户端落盘**：4 个连接各自请求不同的 block_index，QFile::seek(block_index*block_size) + write()；块全部完成后整文件 MD5 校验。.part 旁边维护块位图（客户端 SQLite/CLI 状态文件）。

**为什么不做任意字节 Range**：任意 offset/length 会让“上传期块 CRC”无法复用，只能回退到缓冲读+CRC，失去零拷贝；4MB 粒度对续传体验几乎无差别。

### 6.3 零拷贝与 CRC 的实现

**sidecar 格式**（data/blobs/aa/bb/<md5>.crc）：

~~~text
offset 0   magic "CMBC1" (5B)
offset 5   version u8 = 1
offset 6   block_size u32 BE
offset 10  block_count u32 BE
offset 14  crc[block_count] u32 BE   // 0 表示未知，需要懒计算
~~~

- 上传合并时顺带生成，零额外读盘。
- 旧 blob 没有 sidecar：首次取块时由 IO 池读该块、计算 CRC、pwrite 到 sidecar 对应槽位，然后走**缓冲发送**；后续同块走 sendfile。
- CRC=0 视为未知（CRC 真为 0 时只会导致重复计算，不影响正确性）。

**取块发送流程**：

1. 业务池校验 ticket/f_id/block_index，open(blob, O_RDONLY)；fstat 校验大小。
2. 计算 offset/len；查 sidecar 的 blockCrc。
3. runInLoop 到连接所属 IO 线程：
   - 若 blockCrc 已知：构造 19 字节帧头（LEN=len，SEQ=请求 SEQ，CRC=crc32Combine(crc32(header11), blockCrc, len)），先 send(header)；header 未发完时它留在 outputBuffer，sendFile 必须等 outputBuffer 写空后再启动，保证 TCP 字节序（帧头在前）；
   - 若未知：投 IO 池读块 + 计算 CRC，回 loop 用普通 send(frame)（缓冲路径）。
4. sendFile 每轮最多 1MB，避免饿死同 loop 的其他连接；EAGAIN 时登记剩余区间并 enableWriting，不占用线程。
5. 完成/失败都关闭 fd（RAII），失败通过 forceClose 或 ERROR_RS 通知。

**为什么 combine 是安全的**：CRC(A||B) = combine(CRC(A), CRC(B), len(B)) 是 CRC32 的线性性质；A 是 11 字节头，B 是块数据。单测必须覆盖：

- len(B)=0/1/4MB-1/4MB；
- 随机 payload 直接算 vs combine 算，结果一致；
- 已知向量 "123456789" → 0xCBF43926。

**缓冲回退路径的并发上限**：同时最多 16 个回退块（16×4MB=64MB 峰值）；超过则排队，避免 512 个下载流各分配 4MB。

### 6.4 令牌桶与慢客户端

**两级令牌桶**：

| 级别 | 容量 | 默认速率 | 说明 |
|---|---|---|---|
| 每连接 | 4MB | 2MB/s | 4 连接合计 8MB/s |
| 每用户 | 16MB | 8MB/s | 防止用户开更多连接绕过 |

- 发送前按 len 扣令牌；不足则计算等待时间 need/rate，用 TimerQueue::runAfter 延迟，**不 sleep、不忙等**。
- 等待 >2s（例如管理员把速率配成 0）→ 回 3006，客户端退避。
- 令牌桶状态在连接对象内（每连接）与用户级 map（每用户，带互斥）；用户级 map 按 uid 懒创建，登出/超时清理。

**慢客户端**：

| 风险 | 对策 |
|---|---|
| 对端不收，sendfile 一直 EAGAIN | 只保留 1 个在途块；注册 EPOLLOUT；30s 无字节进展 → forceClose |
| 单连接长期占满 loop | 每轮 sendfile ≤1MB；同 loop 其他连接的事件优先处理 |
| 大量慢连接占 fd/内存 | 全局 512 个活跃下载流、每用户 8 个；超限 3006 |
| 磁盘读阻塞 loop | posix_fadvise(WILLNEED) 由 IO 池预取下一块；监控 loop 延迟，P99>5ms 时把该连接切到缓冲路径（IO 池读） |
| 4MB×512 内存 | sendfile 路径零用户态缓冲；回退路径限 16 个并发 |

**并发连接数上限**：

- 每文件 4 个（客户端默认；服务端不强制，但超过 4 个不增加吞吐）。
- 每用户 8 个下载连接（含分享下载）。
- 全局 512 个活跃下载流（可配）；超出返回 3006。
- fd 预算：512 流 × 1 fd + 连接 fd；2C4G 的 ulimit -n 建议 ≥65535。

### 6.5 断点续传

1. 客户端保留 .part + 块位图 + 首次 10012 返回的 size/md5/block_size。
2. 重连后先发 10027，拿到远端 size/md5/block_size/block_count；任一不一致 → 删 .part 重下。
3. 一致则只请求位图中缺失的块；服务端无状态，不记录下载进度。
4. 每块到达后客户端校验帧 CRC（Codec 自动做），再落盘并置位图；全部完成后算整文件 MD5。
5. 校验通过发 10040；失败则删 .part 重下（或只重下可疑块，Phase 7 再做）。

**为什么服务端不记下载任务**：下载是 Range 读，无状态；记任务会让 t_transfer_task 因每次下载膨胀，收益只是“服务端知道进度”，而客户端本来就知道。

### 6.6 下载失败矩阵

| 失败 | 检测点 | code | 连接 | 客户端动作 |
|---|---|---|---|---|
| ticket 过期 | 取块 | 1004（ERROR_RS） | 保持 | 重新 10010 取票 |
| ticket 不属于该用户 | 取块 | 1004 | 保持 | 重新登录/取票 |
| f_id 与 ticket 不符 | 取块 | 1004 | 保持 | 修正请求 |
| 块越界 | 取块 | 1001 | 保持 | 修正 block_index |
| blob 缺失 | 打开/取块 | 3001 | 保持 | 提示文件损坏 |
| 限流等待 >2s | 取块 | 3006 | 保持 | 1s 后重试 |
| Redis 不可用（票据/限流） | 打开/取块 | 4005/4007/4008 | 保持 | 退避；不接受 fail-open |
| 磁盘读失败 | sendfile | 3001 + forceClose | 关闭 | 重连重试 |
| 客户端 30s 不读 | 发送无进展 | — | forceClose | 重连续传 |
| 整文件 MD5 不符 | 10040 | 3003（仅告警） | 保持 | 删 .part 重下 |

## 7. 分享

### 7.1 码、有效期与提取码

| 项 | 设计 | 理由 |
|---|---|---|
| 分享码 | 6 位，字符表 23456789ABCDEFGHJKMNPQRSTUVWXYZ | 无 0/O/1/I/L；31^6≈8.9 亿 |
| 存储 | CHAR(6) ascii，统一大写 | 唯一索引、缓存键稳定 |
| 有效期 | 永久 / 1 天 / 7 天 | 产品三档；永久用 9999-12-31 哨兵，wire 用 0 |
| 提取码 | 可选 4 位数字，明文存 | 空间只有 10^4，哈希无意义；防护靠锁定+限流 |
| 默认 | 7 天，无提取码 | 与主流网盘一致 |

**永久分享的 DB 表示**：s_expire_at='9999-12-31 23:59:59.999999'；不用 NULL（唯一索引/比较都更麻烦），wire 层映射为 0。

### 7.2 创建、访问、取消

**创建（10018）**：

1. 校验 uf_id 属于当前用户且未删除；目录也允许分享（本期只展示元信息，不展开）。
2. expire_policy 映射：0→9999 哨兵，1→now+1d，2→now+7d。
3. req_id 幂等缓存命中 → 返回同一 code。
4. 生成分享码：std::mt19937 + 拒绝采样保证均匀；INSERT 捕获 1062 重试 ≤5 次。
5. 生成 4 位提取码（若 access_mode=1）：1000~9999，避免 0000 这种弱码。
6. INSERT t_share(...)；s_file_id 文件分享填 f_id，目录为 NULL。
7. 写 cm:v1:share:{code}（TTL 5min±10%），写 req 结果缓存 10min。

**访问（10022）**：

1. 归一化 code（大写、去空格）。
2. cm:v1:share:{code} 命中 → 得到元信息；未命中 → SELECT ... WHERE s_code=?（uk_s_code），命中回填；未命中写 cm:v1:share:miss:{code}=1（60s）。
3. 校验 s_status=0 且 s_expire_at > NOW(6)；否则 2003。
4. 若 s_access_code 非空：
   - Redis 计数 cm:v1:share:fail:{code}:{ip}，5 次/10 分钟锁定；
   - 比较提取码；错误 → 2004，正确 → DEL 计数；
   - Redis 不可用 → 4008（**fail-closed**，否则提取码可无限爆破）。
5. 生成 share_ticket（10 分钟，绑定 uid+code+fid），返回元信息。

**取消（10042）**：UPDATE t_share SET s_status=1 WHERE s_code=? AND s_user_id=?；已取消返回 already=1；DEL cm:v1:share:{code}。

### 7.3 引用计数

**分享访问不增加 f_ref_count**。计数定义是“有多少个未删除的 t_user_file 指向该 blob”：

- 创建分享：只新增 t_share 行，不新增节点 → 不加计数。
- 访问/下载：只读 → 不加计数。
- 取消分享：不删节点 → 不减计数。
- 删除被分享的节点：节点软删 → 减计数；分享随即失效（缓存失效 + 访问时校验节点）。
- 转存（本期不做）：新增 t_user_file → 加计数。

**为什么**：如果把“访问”也算引用，热门分享会让 blob 永远无法回收；而且访问是无状态读，没有“访问结束”的可靠信号（断线、崩溃），计数会泄漏。

### 7.4 分享缓存与降级

| 场景 | Redis 键 | TTL | Redis 挂 |
|---|---|---|---|
| 分享元信息 | cm:v1:share:{code} | 5min ±10% | 回源 MySQL（fail-open） |
| 不存在 | cm:v1:share:miss:{code} | 60s | 不写，直接查 MySQL |
| 提取码失败计数 | cm:v1:share:fail:{code}:{ip} | 10min | **fail-closed**，返回 4008 |
| 创建幂等 | cm:v1:share:req:{uid}:{req_id} | 10min | 退化为可能重复创建 |
| 分享票据 | cm:v1:share:ticket:{token} | 10min | 无法访问分享下载 → 4005 |
| 下载票据 | cm:v1:dl:ticket:{token} | 5min 滑动 | fail-closed |

**失效时机**：取消分享、重命名节点、移动节点、删除节点、分享过期被扫描到。重命名/移动会让缓存里的 file_name 过期，必须 DEL。

**CacheKey 复用边界**：继续使用 CacheKey::share / shareMiss 的函数与键前缀，仅调整长度/字符校验；不新增 share 专用 key，避免两套命名。

### 7.5 枚举与爆破防护

| 攻击 | 防护 |
|---|---|
| 遍历 6 位码 | 每 IP 分享访问 30 次/分钟（Redis 固定窗口），超限 3006；全局 3006 计数 |
| 爆破 4 位提取码 | 每 (code, IP) 5 次/10 分钟锁定；锁定期间直接 2004（不查 DB） |
| 短时间大量创建 | 每用户 20 次/小时；3006 |
| 缓存穿透 | 空值缓存 60s + 参数格式前置校验（6 位字符表） |
| 日志泄露 | 分享码可记（非秘密）；提取码、ticket 禁止进日志 |

## 8. 回收站与磁盘回收

### 8.1 软删、恢复、彻底删除

| 操作 | DB | 引用计数 | 磁盘 |
|---|---|---|---|
| 删除（10025） | uf_deleted_at=NOW(6) | 文件节点 -1；到 0 置 f_state=2 | 不动 |
| 恢复（10036） | uf_deleted_at=哨兵，修正 parent/name | 文件节点 +1；f_state=2→1 | 不动 |
| 彻底删除（10038） | 物理 DELETE 节点/子树 | **不再减**（软删时已减） | 到 0 的 blob 交给 GC |
| 孤儿 GC（定时） | DELETE t_file | 已为 0 | unlink blob + .crc |

**为什么彻底删除不再减计数**：软删已经减过；再减会变成无符号下溢（f_ref_count>0 条件只能防一次，不能防逻辑错误）。测试必须覆盖“删除→恢复→再删除→彻底删除”的计数轨迹。

**唯一例外**：彻底删除目录时，子树里“从未软删过”的活跃文件节点要在这一批事务里补减一次；已软删的节点不再减。实现时按 `uf_deleted_at` 是否为哨兵区分，不能统一减。

### 8.2 目录子树的处理

- 软删目录不级联（05 决策）；子节点保留原 parent_id，从根不可达。
- 回收站列表只展示“被删除的节点”，不展开子树；用户看到的是他删除的那个目录。
- 恢复目录：只恢复该节点；子节点本来就还在，自动重新可达。若子节点在删除期间被单独恢复过，它已不在该目录下（parent_id 不变但 deleted_at=哨兵，从根可见），这属于允许的边界。
- 彻底删除目录：
  1. BFS 收集所有后代（按 parent_id 查，深度 ≤16）；
  2. 节点数 >10000 → 3008；
  3. 按深度倒序，每 200 行一个事务：活跃文件节点减计数（到 0 置孤儿）、DELETE 行；
  4. 最后删根节点；
  5. 每批事务内同时 UPDATE t_share SET s_status=1 WHERE s_uf_id IN (...)，避免分享指向已删节点。
- 崩溃恢复：根节点最后删，重跑时会跳过已删行，天然幂等。

### 8.3 引用计数归零与 blob 回收

**触发点**：软删/彻底删除事务里，f_ref_count 减到 0 时置 f_state=2。**不在请求线程 unlink**（可能正在被下载/播放）。

**GC 任务（TimerQueue，每日 03:00）**：

~~~sql
SELECT f_id, f_path, f_size
  FROM t_file f
 WHERE f_state = 2
   AND f_updated_at < NOW(6) - INTERVAL 24 HOUR
   AND NOT EXISTS (SELECT 1 FROM t_user_file u
                    WHERE u.f_id=f.f_id
                      AND u.uf_deleted_at='1970-01-01 00:00:00.000000')
   AND NOT EXISTS (SELECT 1 FROM t_share s
                    WHERE s.s_file_id=f.f_id AND s.s_status=0)
 ORDER BY f_updated_at
 LIMIT 100;
~~~

每个候选：

1. 事务内再次 SELECT ... FOR UPDATE 校验 f_ref_count=0 AND f_state=2；
2. 投 IO 池 unlink(blob)、unlink(blob.crc)；ENOENT 视为成功；
3. unlink 成功后 DELETE FROM t_file WHERE f_id=? AND f_ref_count=0；
4. 失败（EACCES/EPERM/EIO）→ 记 ERROR、保留行、下轮重试。

**播放记录不 pin blob**：t_play_record.p_file_id 是历史进度，不是引用；GC 后残留记录由同一任务按月清理（DELETE p FROM t_play_record p LEFT JOIN t_file f ON f.f_id=p.p_file_id WHERE f.f_id IS NULL LIMIT 500）。

**周期与批量取舍**：

| 参数 | 取值 | 理由 |
|---|---|---|
| 周期 | 每日 03:00 | 低峰；用户删除后 24h 内仍可由运维手工恢复 |
| 单轮行数 | 100 | unlink 是磁盘元数据操作，100 个约 10~50ms；1000 个会形成 IO 峰值 |
| 单轮字节上限 | 2GB | 防止一次删掉大量大文件拖垮磁盘；超限留到下一轮 |
| 宽限 | 24h | 给误删/审计留窗口，也避开“刚删就 GC 导致下载失败” |

### 8.4 TimerQueue 定时任务总表

| 任务 | 周期 | 批量 | 失败处理 |
|---|---|---|---|
| 上传任务过期 | 5min | 200 任务/轮 | 记 WARN，下轮重试 |
| 上传 tmp 孤儿清理 | 30min | 200 目录/轮 | 记 WARN |
| 分享过期扫描 | 每日 03:10 | 1000 行/轮 | 记 WARN |
| 孤儿 blob GC | 每日 03:00 | 100 行 / 2GB | 记 ERROR，保留行 |
| 播放记录清理 | 每月 1 日 04:00 | 500 行/轮 | 记 WARN |
| 心跳 tick | 1s | 全连接扫描 | Phase 3 已有 |

所有任务都在 **TimerQueue 所在 loop 线程**触发，但实际 DB/磁盘工作投业务池/IO 池；回调本身只做“取一批 ID + 投递”，禁止在 loop 里跑 SQL 或 unlink。

## 9. 文件列表分页

### 9.1 游标键

| 列表 | 排序 | 游标 | 索引 |
|---|---|---|---|
| 目录（名称） | uf_name ASC, uf_id ASC | (last_name, last_id) | idx_list (u_id, uf_parent_id, uf_deleted_at, uf_name) + PK |
| 目录（最近上传） | uf_created_at DESC, uf_id DESC | (last_created_ms, last_id) | idx_recent_created (u_id, uf_deleted_at, uf_created_at) + PK |
| 目录（最近修改） | uf_updated_at DESC, uf_id DESC | (last_updated_ms, last_id) | idx_recent (u_id, uf_deleted_at, uf_updated_at) + PK |
| 回收站 | uf_deleted_at DESC, uf_id DESC | (last_deleted_ms, last_id) | idx_deleted (u_id, uf_deleted_at) + PK |
| 我的分享 | s_created_at DESC, s_id DESC | (last_created_ms, last_id) | idx_user_status_created |

**禁止 OFFSET**：LIMIT 100000,50 要扫 10 万行；游标是索引 seek，代价与页深无关。

### 9.2 SQL 形状

**名称升序**：

~~~sql
SELECT uf_id, f_id, uf_name, uf_is_dir, uf_created_at, uf_updated_at
  FROM t_user_file
 WHERE u_id = ?
   AND uf_parent_id = ?
   AND uf_deleted_at = '1970-01-01 00:00:00.000000'
   AND (uf_name, uf_id) > (?, ?)
 ORDER BY uf_name, uf_id
 LIMIT ?;
~~~

**创建时间降序**：

~~~sql
... AND (uf_created_at, uf_id) < (?, ?)
 ORDER BY uf_created_at DESC, uf_id DESC
 LIMIT ?;
~~~

**回收站**：

~~~sql
... AND uf_deleted_at > '1970-01-01 00:00:00.000000'
    AND (uf_deleted_at, uf_id) < (?, ?)
 ORDER BY uf_deleted_at DESC, uf_id DESC
 LIMIT ?;
~~~

LIMIT 取 n+1，多出来的一行只用于 has_more=1，不返回给客户端。

### 9.3 同一秒（甚至同一微秒）多行的稳定性

- 时间列是 DATETIME(6)，微秒精度；批量插入仍可能同微秒。
- 所有时间排序都以 (time, uf_id) 二元组做游标，SQL 用行构造器比较；uf_id 是自增主键，唯一且单调。
- idx_* 二级索引末尾隐含主键，(u_id, ..., time, uf_id) 的字典序与 SQL 的 ORDER BY time DESC, id DESC 完全一致，因此不会出现“翻页重复/漏行”。
- 名称排序同理：活跃节点同名被唯一索引禁止，但回收站里同名很常见，仍用 uf_id tie-break。
- 并发插入/删除：keyset 只保证“当前页之后”的稳定，不保证快照隔离；新插入且排序在游标之前的行不会出现在本次翻页中，刷新后可见——这是可接受语义，不需要事务快照。

### 9.4 total_count

- 仅首页（cursor 为空）返回；使用 SELECT COUNT(*) 命中同一索引，max_execution_time=200ms。
- 超过 10000 时不再精确统计：SELECT COUNT(*) FROM (SELECT 1 FROM ... LIMIT 10001) t；结果 10001 → 返回 total_count=10000 + has_more 语义由客户端忽略（仅用于“约 1 万项”展示）。
- 超时/失败 → total_count=0xFFFFFFFFFFFFFFFF（未知），不阻断列表。
- 非首页返回 0，客户端保留首页的值。

## 10. 缓存与降级总表

### 10.1 接口 × 缓存键 × TTL × 降级

| 接口 | Redis 用途 / 键 | TTL | Redis 不可用 |
|---|---|---|---|
| 登录/鉴权（所有接口前置） | cm:v1:sess:{token} | 30min 滑动 | **fail-closed 4007** |
| UploadInit（秒传查找） | cm:v1:file:md5:{md5} | 60min ±10% | 回源 uk_f_md5，可用 |
| UploadInit（幂等） | cm:v1:up:req:{uid}:{req_id} | 10min | 退化为可能重复 init；不损坏数据 |
| UploadChunk | 无 | — | — |
| ContinueUpload | 无（位图以 t_chunk 为准） | — | — |
| UploadComplete | 写 file:md5（回填） | 60min | 跳过回填，下次读回源 |
| QuickUpload | file:md5:{md5} | 60min | 回源 MySQL |
| DownloadOpen | cm:v1:dl:ticket:{token} | 5min 滑动，硬上限 2h | **fail-closed 4005/4007** |
| DownloadStat | 无 | — | — |
| DownloadRange | ticket 校验 | 同上 | **fail-closed** |
| DownloadDone | cm:v1:dl:done:{uid}:{ticket} 去重 | 10min | 跳过去重，重复计数可接受 |
| ShareCreate（幂等） | cm:v1:share:req:{uid}:{req_id} | 10min | 可能重复创建，不损坏数据 |

| ShareOpen | cm:v1:share:{code} / share:miss:{code} | 5min ±10% / 60s | 回源 MySQL，可用（fail-open） |

| ShareCancel | 删 share:{code} | — | 删除失败靠 TTL 兜底 |
| Delete/Restore/Purge | 删 share:{code}（若有） | — | 删除失败靠 TTL 兜底 |
| RecycleList | 无 | — | — |
| ListFile | 无（刻意不缓存列表） | — | — |
| PlayReport | 无 | — | — |
| 分享/创建/登录限流 | cm:v1:rl:ip:{ip}:{window} | 窗口长度 | **fail-closed 4008** |

### 10.2 为什么这些不能降级

| 场景 | 不能降级的理由 |
|---|---|
| 会话鉴权 | 没有第二数据源（MySQL 无 session 表）；fail-open 等于任何人可访问 |
| 下载/分享票据 | 票据是授权凭证；Redis 挂时无法判断是否撤销/是否属于该用户，放行 = 越权 |
| 提取码锁定 | 计数失效 = 4 位码可无限爆破；宁可暂时不可用 |
| IP/用户限流 | 限流失效 = 枚举/刷接口无成本；多实例下进程内计数还会放大配额 |

**能降级的共同特征**：Redis 里存的是 MySQL 已有数据的副本（秒传索引、分享元信息），且失败方向是“变慢”而不是“放行”。

### 10.3 缓存一致性

| 事件 | 动作 |
|---|---|
| 上传完成 | SET file:md5:{md5}=f_id；DEL file:id:{fid}（若有） |
| 秒传落库 | 同上 |
| 删除节点 | DEL share:{code}（该节点所有有效分享） |
| 重命名/移动 | DEL share:{code}（显示名变了） |
| 取消分享 | DEL share:{code}，不写 miss |
| 过期分享 | DEL share:{code}，写 share:miss 60s |
| GC 删 blob | DEL file:md5:{md5}、DEL file:id:{fid} |

删除而不是更新：并发读可能把旧值写回；DEL 让下一次读重新加载，窗口更小。强需求（取消分享立即生效）用“提交后 DEL + 500ms 后异步再 DEL 一次”。

## 11. 端到端测试方案

### 11.1 工具与位置

### 11.2 upload_cli

~~~text
upload_cli --host 127.0.0.1 --port 8004
           --user 13800000000 --password ***
           --file ~/cm_testdata/test_50m.bin
           --remote /test_50m.bin
           -c 4194304          # 分片大小；服务端固定 4MB，非 4MB 会提示并取 4MB
           -r                  # 续传：先登录，再按 --task-id 或 --state 查询位图
           --md5               # 结束后本地算 MD5，与服务端返回比对
           --state ./up.state  # 持久化 task_id/已发片/本地 MD5
           --stop-after-chunks 6   # 测试用：发完 6 片后 _exit(9)，模拟硬杀
           --keep-task         # 失败不取消任务
~~~

流程：

1. 登录 → 拿 token/会话。
2. 有 --state 且 -r：读 task_id，发 10028；否则发 10004。
3. 若 result=1（秒传）→ 打印 INSTANT_HIT=1，结束。
4. 逐片读文件（4MB），算分片 MD5，发 10006；收到 10007 后打印 CHUNK_OK=index。
5. --stop-after-chunks N 达到后直接 _exit(9)（不 flush、不取消任务），模拟进程被杀。
6. 全片完成 → 10030；打印 FILE_ID/UF_ID/NAME/MD5_OK。
7. 退出码：0 成功；2 参数错；3 服务端业务错；4 校验失败；9 模拟杀进程。

### 11.3 download_cli

~~~text
download_cli --host 127.0.0.1 --port 8004
             --user ... --password ...
             --uf-id 12345          # 或 --share-code ABC234 --access-code 1234
             --out ./test_50m.bin
             -c 4194304             # 块大小，必须与服务端一致
             -j 4                   # 并发连接数，默认 4
             -r                     # 续传：读 .part + .part.state
             --md5 25e317773f308e446cc84c503a6d1f85
             --stop-after-blocks 6  # 测试用：下完 6 块后 _exit(9)
             --rate 1048576         # 客户端读速率（测试慢客户端），0=不限
~~~

流程：

1. 登录；10010 打开，拿 ticket/size/block_count。
2. 读 .part.state（size/md5/block_size/bitmap）；与 10027 返回比对；不一致删 .part 重来。
3. 起 -j 个连接（或复用同一连接串行发 10013），按块号取缺失块；每块校验帧 CRC，seek(block*block_size) 写入。
4. 每块完成更新 .part.state（先写临时文件再 rename，避免半写）。
5. --stop-after-blocks N → _exit(9)。
6. 全部完成 → 算 MD5；与 --md5 或 10012 返回值比对；发 10040。

.part.state 文本格式（测试工具私有）：

~~~text
version=1
f_id=123
size=52428800
md5=25e317773f308e446cc84c503a6d1f85
block_size=4194304
blocks=13
bitmap=3f0100
~~~

## 13. 风险与未决

### 13.1 风险

| 风险 | 影响 | 对策 |
|---|---|---|
| crc32Combine 实现错误 | 下载全量 BadCrc | 直接计算 vs combine 的随机对照单测；sidecar 缺失回退缓冲路径 |
| sidecar 与 blob 不一致 | 下载坏块 | 上传时同一遍流生成；GC 同时删两个文件；不一致时重算并覆盖 |
| 4MB CRC 在业务池堆积 | 上传吞吐下降 | 业务池 ≥4 线程；每连接 2 个在途片；超时回 1006 |
| 合并占满 IO 池 | 下载回退路径排队 | 合并并发上限 2；下载回退并发上限 16 |
| 行锁等待 | 同 task 重试变慢 | 事务 <20ms、锁顺序固定、文件 IO 在事务外 |
| 自动改名 99 次冲突 | 上传失败 | 概率极低；返回 1003 并提示重命名 |
| GC 误删 | 用户文件丢失 | 24h 宽限 + 三重 re-check + 只删 f_ref_count=0 |
| 大目录 purge 长事务 | 锁表 | 200 行/事务、10000 节点上限、失败可重跑 |
| Redis 挂 | 鉴权/票据/限流不可用 | 明确 fail-closed；能降级的走 MySQL；演练脚本覆盖 |
| 客户端 4 连接共享 ticket | 票据过期中断 | 每次取块滑动续期；硬上限 2h；过期重开 |
| 时钟回拨 | 过期/分享 TTL 异常 | DB 用 NOW(6) UTC；服务端不信任客户端时间 |
| 迁移旧 blob 无 sidecar | 首次下载变慢 | 懒计算 + 缓存；只影响首块 |

### 13.2 未决（不阻塞 Phase 5 开工）

1. 单用户配额（总容量/文件数）是否本期启用；当前只做磁盘 NoSpace。
2. 分享目录是否允许“在线播放其中的视频”（需要展开子树 + 逐个授权）。
3. 上传完成后的“最近上传”列表是否要强一致（当前靠 uf_created_at，秒传节点用当前时间）。
4. 下载限速默认值（2MB/s/连接、8MB/s/用户）是否按线上带宽调整。
5. 是否把 tr_offset 改名 tr_done_bytes（语义更准，但需要改 05 文档与 DAO 字段）。
6. 孤儿 GC 是否要支持“手工立即回收单个 f_id”（运维接口，非用户接口）。

## 14. Phase 5 实现回填（2026-10-19，状态 Done）

### 14.1 鉴权差异（与 §10.1 第一行）

- 实现是**连接级 uid**：登录成功（10002/10003）后把 uid 写入连接状态，后续请求直接读该 uid；
  没有 cm:v1:sess:{token}，也没有 30min 滑动会话。
- 因此 **Redis 不可用时登录仍然成功**，与 §10.1 写的 fail-closed 4007 不同；这是已确认的偏差，本期不实现 token 会话。
- 其余 Redis 故障行为按 §10.1 执行：下载 ticket fail-closed（4005/4007）、提取码 fail-closed（4008）、
  秒传回源 MySQL、列表不依赖缓存。

### 14.2 Handler 注册（S-1/S-2 收口）

- 已注册：10018/10020/10022/10042（分享）与 10025/10034/10036/10038（回收站）。
- 10022 为游客接口，不要求 uid；提取码失败计数的作用域是连接 IP（去掉端口）。
- 10010 支持 ufId 与 shareTicket 二选一：share_ticket 从 Redis 读 ownerUid|fid|code 后签下载 ticket；
  Redis 挂/键缺失/解析失败一律 fail-closed，不回退 ufId。
