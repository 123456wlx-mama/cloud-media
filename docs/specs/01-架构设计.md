## 0. 结论摘要

1. **单仓库四层**：common（基础/日志/配置/协议）→ protocol（v2 编解码）→ server_core / client 各模块 → 两个可执行程序。
2. **依赖方向单向**：common 不依赖 Qt/FFmpeg/socket；protocol 不依赖 Qt；server 不依赖 Qt；client 不依赖 server 头文件；UI 不直接接触 FFmpeg。
3. **服务端只跑 Linux**：Reactor + epoll(ET/ONESHOT) + 非阻塞 + 线程池；任何阻塞 IO 不得出现在 IO 线程。
4. **客户端只跑 Windows**：Qt 5.12.11 MinGW32；网络层保留 INetMediator 抽象，底层由 WinSock 换成 QTcpSocket。
5. **协议强制升级 v2**：魔数 + 版本 + 类型 + 序号 + 长度 + CRC32；旧客户端不兼容，保留类型号段映射表供对照。
6. **文件存储改为内容寻址**：全服一份 blob（按 MD5 分片目录），用户目录只是关系表；修掉旧工程“同一文件按用户重复存”的缺陷。
7. **传输状态落 MySQL**：t_transfer_task / t_chunk 持久化；Redis 只做会话、秒传索引、分享码、限流缓存。
8. **播放只做原画**：边下边播（读 .part 水位）+ 基础 HLS（FFmpeg Remux，不重编码）；不做 720P/多码率。

## 2. Legacy 依赖分析

### 2.0 方法与限制

- 尝试对 TCPKernel.h 执行 LSP documentSymbol，环境返回 **LSP server not available**（qmake 工程无 compile_commands，C++ LSP 未启动）。
- 因此改用**静态符号分析**：grep 符号定义/引用 + 逐文件读头文件与调用链，结论均给出文件与行号，可复核。
- 分析范围：server/linux-epoll（7 个 cpp，约 1840 行）、client/NetDesk（4 个核心 cpp，约 2420 行）、MediaPlayer（5 个 cpp，约 1400 行）。


## 3. 目标架构

### 3.1 分层原则

1. **基础层无业务**：common 只放日志、配置、错误码、Buffer、MD5/CRC32、时间工具。
2. **协议层无 Qt**：protocol 只依赖 std，服务端与客户端共用同一份编解码。
3. **服务端无 Qt**：server 只依赖 common/protocol/系统库；媒体模块额外依赖 FFmpeg。
4. **客户端无 server 头**：client 只依赖 common/protocol；通过协议通信，不共享业务类。
5. **播放器不暴露 FFmpeg 类型**：PlayerCore 用 pimpl，UI 只看到毫秒、状态、帧回调。
6. **UI 不做 IO**：所有网络/文件/数据库操作在 netapi/transfer/store，UI 只订阅信号。

### 3.2 模块依赖图

~~~mermaid
graph TD
    common[cm_common<br/>base/log/config] --> protocol[cm_protocol<br/>v2 codec/messages]
    protocol --> server_core[cm_server_core<br/>net/pool/db/cache/logic/media]
    protocol --> client_net[cm_client_net<br/>QTcpSocket + dispatcher]
    common --> player_core[cm_player_core<br/>demux/decode/render]
    server_core --> server_app[cloud-media-server]
    client_net --> client_ui[cm_client_ui]
    client_store[cm_client_store<br/>SQLite task cache] --> client_ui
    player_core --> client_ui
    client_ui --> client_app[cloud-media-client]
~~~

禁止出现的边：server → Qt；common → Qt/FFmpeg；protocol → Qt；client → server；ui → FFmpeg。

### 3.3 运行时视图

~~~text
[Windows 客户端]
  UI 线程 ── 信号槽 ── 网络线程（QTcpSocket）── TCP ──┐
     │                                              │
     ├─ 传输线程池（上传/下载，最多4连接/文件）        │
     ├─ SQLite 写线程（WAL，单写者）                  │
     └─ 播放线程组（demux/video/audio）               │
                                                    ▼
[Linux 服务端]
  main EventLoop（accept + 定时器）
     └─ N 个 IO EventLoop（每线程一个 epoll）
          └─ 线程池（业务处理 / 文件合并 / HLS 切片）
               ├─ MySQL 连接池
               ├─ Redis 连接池
               └─ 本地磁盘 data/blobs、data/hls
~~~

## 6. 关键契约（只定边界，不写实现）

### 6.1 common

| 组件 | 契约 |
|---|---|
| Logger | 单例；TRACE~FATAL；双缓冲 + 后台线程；按大小/日期滚动；格式含 traceId；析构 flush；可运行时关闭 |
| Buffer | 可增长字节缓冲；readable/writable 指针；peek/retrieve；不依赖 Qt |
| ErrorCode | enum class；to_string；协议错误码与文案分离 |
| Config | ini 解析；服务端/客户端各自的强类型结构；启动时校验必填项 |
| Md5/Crc32 | 流式与一次性接口；不依赖 OpenSSL |

### 6.2 protocol v2

帧格式（网络字节序）：

| 字段 | 长度 | 说明 |
|---|---|---|
| MAGIC | 4B | 0x434D4456（"CMDV"） |
| VERSION | 1B | 固定 2 |
| TYPE | 2B | 10000~10999 业务；11000~11999 控制；12000+ 预留 |
| SEQ | 4B | 请求/响应关联；推送为 0 |
| LEN | 4B | payload 长度，上限 8MB |
| CRC32 | 4B | 覆盖 VERSION..PAYLOAD |
| PAYLOAD | LEN | 字段逐个序列化，禁止 memcpy 整个结构体 |

规则：
- 首帧必须是 HELLO（携带版本与客户端标识）；版本不符返回 ERR_VERSION 并断开。
- **兼容策略：强制升级**。服务端不实现 v1 解码；legacy 类型号只保留映射表（packdef.h → type_map）供阅读与迁移对照。理由：单仓库同步升级、双协议维护成本高于收益。
- 分片上传的 payload = 固定头 + 原始字节；单帧不超过 4MB + 头。
- 所有字符串长度前缀 + UTF-8；禁止依赖结构体对齐。

### 6.3 server/net

| 组件 | 契约 |
|---|---|
| EventLoop | 一线程一 loop；run/stop；定时任务投递；跨线程用 wakeup fd |
| EpollPoller | ET + EPOLLONESHOT；读必须读到 EAGAIN；事件回调后按需 re-arm |
| TcpConnection | shared_ptr + enable_shared_from_this；持有 fd、输入 Buffer、输出队列、状态；禁止在 IO 线程做磁盘/DB 阻塞调用 |
| 发送 | 业务线程只 append 到输出队列并唤醒；IO 线程写；处理部分写；高水位暂停读 |
| 文件发送 | sendfile 零拷贝；单次不超过 256KB；EAGAIN 时登记剩余区间，等 EPOLLOUT |
| TimerQueue | 最小堆；心跳、空闲踢除、任务超时 |
| 优雅退出 | 停 accept → 关连接 → 停 loop → join 线程 → flush 日志 |

### 6.4 server 存储与业务

| 组件 | 契约 |
|---|---|
| MysqlPool | RAII 借还；预处理语句；重连；事务封装；慢查询日志 |
| RedisPool | hiredis 封装；get/set/expire/hset/incr/eval；超时与重连 |
| 文件存储 | data/blobs/{md5[0:2]}/{md5[2:4]}/{md5}；t_file 对 f_md5 唯一；引用计数在事务内维护，不用触发器 |
| 上传 | 4MB 分片；分片幂等；合并走线程池；整文件 MD5 校验；失败只重传坏片 |
| 下载 | 单文件 Range(offset,len)；4 连接由客户端发起；服务端令牌桶限速；直链 token 存 Redis TTL |
| 分享 | share_code 9 位数字；access_code 4 位；默认 7 天；转存复用秒传关联逻辑 |
| 回收站 | 只置 is_deleted=1；查询默认过滤；不物理清理 |
| 搜索 | 文件名 LIKE；分页；不做全文/ES |
| 播放 | 直链（边下边播）+ HLS（Remux）；播放进度写 t_play_record（单端） |

### 6.5 client 网络/传输/本地库

| 组件 | 契约 |
|---|---|
| INetMediator | 保持抽象；QtTcpMediator 用 QTcpSocket；网络线程独立，信号排队到 UI |
| PacketDispatcher | TYPE → handler 的 std::function 表；未知类型记日志并丢弃 |
| TransferManager | 任务状态机 pending/running/paused/failed/done；下载单文件 4 连接；批量队列有限并发（默认 2 个文件）；暂停用条件变量，禁止忙等 |
| LocalTaskStore | SQLite WAL；单写线程；表 t_local_task/t_local_file_cache/t_play_record_local；登录后与服务端对账 |
| UI | 只读 Model；进度信号节流（≥100ms）；不直接持有 socket/文件句柄 |

### 6.6 player

| 组件 | 契约 |
|---|---|
| PlayerCore | pimpl；open(file/url)、play/pause/stop、seek(ms)、setRate(0.5~2.0)、setVolume；状态回调；不暴露 FFmpeg 类型 |
| 线程 | demux、video decode、audio output 三线程；PacketQueue 用 std::mutex/condition_variable |
| 时钟 | audio_clock 为主；视频按 PTS 同步；seek 清队列 + flush 解码器 |
| ProgressiveIO | 自定义 AVIOContext 读 .part；超过已下载水位则等待（5s 超时→缓冲事件）；下载线程更新水位 |
| HLS | avformat 直接打开 m3u8；只允许已生成分片区间 seek；不自定义 IO |
| 渲染 | IVideoRenderer：GL 实现直接上传 YUV 纹理；QPainter 实现兜底；不逐帧 QImage 拷贝 |
| 倍速 | 音频重采样/时间伸缩 + 视频同步；仅客户端，不影响服务端 |

### 6.7 media（服务端 HLS）

- HlsRemuxer：输入 blob 路径，输出 data/hls/{md5}/index.m3u8 + seg-%05d.ts。
- 命令等价：ffmpeg -i input -c copy -f hls -hls_time 10 -hls_list_size 0。
- **只 Remux，不重编码**；只有原画一档；不做 720P/多码率。
- 幂等：manifest 已存在直接返回 ready；同一 md5 加锁，避免重复切片。
- 并发保护：全局最多 1~2 个切片任务，其余排队；返回 202 + task_id。
- 不引入定时清理任务；HLS 产物由运维手工清理（与 05 的“不做定时物理清理”一致）。

## 8. 架构决策记录（ADR）

| 编号 | 决策 | 理由 | 放弃的方案 |
|---|---|---|---|
| D1 | 单仓库 + legacy/ 只读归档 | 统一后端叙事；旧工程可对照回滚 | 原地增量改造（目录混乱） |
| D2 | 协议强制升级 v2，不做 v1 解码 | 单仓库同步升级；避免双协议维护 | 双协议并存、号段兼容 |
| D3 | 内容寻址 blob + 应用层引用计数 | 跨用户真正去重；软删不与触发器冲突 | 保留每用户路径 + 触发器删文件 |
| D4 | 传输状态落 MySQL，Redis 只做缓存/锁 | 重启可恢复；状态可审计 | 继续用内存 map |
| D5 | 一 IO 线程一 EventLoop；业务走线程池 | 避免单 loop 成瓶颈；阻塞操作隔离 | 单 Reactor 全包 |
| D6 | 客户端 QTcpSocket + 独立网络线程 | 去掉 Windows 专用 WinSock/HANDLE；跨平台 | 保留裸 socket + 接收线程 |
| D7 | PlayerCore pimpl + 渲染接口 | UI 不背 FFmpeg 头；渲染可替换 | 继续 VideoPlayer 直接发 QImage |
| D8 | HLS 只 Remux、只原画 | 服务器算力有限；符合 05 冻结口径 | 多清晰度重编码 |
| D9 | 回收站只软删，不做清理任务 | 避免分布式调度复杂度 | 保留期 + 定时物理删除 |
| D10 | common/protocol 零 Qt/FFmpeg | 服务端/客户端共用；可单测 | 公共层直接用 QString |

## 9. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 协议 v2 与旧客户端不兼容 | 旧客户端无法连接 | 明确强制升级；legacy 仅归档；发布说明写清 |
| FFmpeg 4.2 API 迁移成本 | Phase 9 超期 | 先做 PlayerCore 适配层；send/receive API 小步替换 |
| 32 位 FFmpeg/SDL 与 Qt 套件不匹配 | 链接失败/运行崩溃 | Phase 9 统一评估 32/64 位；thirdparty 与 Qt 同 ABI |
| HLS Remux 并发占 CPU/磁盘 | 播放卡顿 | 全局并发上限 1~2；manifest 幂等；产物缓存 |
| SQLite 多线程写冲突 | 任务状态损坏 | WAL + 单写线程 + 事务；UI 只读 |
| MySQL 触发器移除后的引用计数 | 删除逻辑出错 | 应用层事务维护 ref_count；迁移脚本对账 |
| Windows/Linux 路径分隔符 | 文件找不到 | 统一用配置根目录 + std::string 拼接；禁止硬编码 /home |
| CI 无 Qt/FFmpeg 环境 | 客户端无法自动构建 | 先 CI 只跑 common/protocol/server；客户端本地构建 + 手工回归 |
