## 0. 架构分层与依赖红线

~~~text
┌──────────────────────────── ui/（只认识 Qt 与 QImage）────────────────────────────┐
│  PlayerPane                                                                     │
│   ├─ 控制条：播放/暂停、进度 seek、音量、全屏                                     │
│   ├─ 浮层：缓冲转圈（>1.5s 才显示）、失败态 + "用系统播放器打开"                    │
│   └─ VideoSurface*（接口）                                                       │
│        ├─ GlVideoSurface      QOpenGLWidget + 纹理（默认）                        │
│        └─ PainterVideoSurface QWidget + QPainter（无 GL / 远程桌面回退）           │
└───────────────▲──────────────────────────────────────────────▲──────────────────┘
                │ Qt 信号（queued）：frameReady(QImage)          │ setImage(QImage)
                │ positionChanged/stateChanged/bufferingChanged  │
┌───────────────┴──────────────────────────────────────────────┴──────────────────┐
│  player/PlayerCore（PIMPL，头文件只有 Qt 类型；唯一允许 include libav*/SDL 的层）   │
│   ├─ GrowingFileIO   可增长文件的 AVIOContext（边下边播的"等块"）                  │
│   ├─ PacketQueue     包队列（std::mutex + condition_variable）                    │
│   ├─ Impl 线程        demux / video decode / SDL audio callback                   │
│   └─ libav* + SDL（只用到 SDL 的音频子系统，不建窗口、不做渲染）                    │
└─────────────────────────────────────────────────────────────────────────────────┘
~~~

| 层 | 允许依赖 | 禁止 |
|---|---|---|
| `client/player/` | libav*、SDL（仅 audio）、QtCore/QtGui | QtWidgets、依赖 `ui/` |
| `client/ui/` | Qt、`player/PlayerCore.h`、`QImage` | 任何 `libav*`/`SDL` 头文件 |
| `common/` | 纯 C++11 + STL | 任何 Qt 符号 |

**为什么让 PlayerCore 抛 QImage 而不是 AVFrame**（§5 展开）：

1. 红线：AVFrame 一进 `ui/`，`ui` 就必须 include `libavutil/frame.h`，依赖方向立刻破。
2. 生命周期：AVFrame 是解码器复用的对象，跨线程传递要定义"谁 unref、什么时候 unref"；
   QImage 是隐式共享值语义，跨线程 queued 信号自动拷贝引用，不存在悬垂。
3. 可替换性：渲染后端（GL/Painter/未来的硬解纹理）只需要"像素"，不需要"解码器上下文"。

代价是每帧一次 RGB 转换 + 一次 copy：640×360 RGBA ≈ 900KB，25fps ≈ 22MB/s，可接受。
4K/60 场景下这笔开销会明显，届时的扩展点是给 `VideoSurface` 增加"硬解纹理"重载，
而不是把 AVFrame 漏到 `ui/`。

## 1. 线程模型

**3 个 worker + GUI**，职责严格分离：

| 线程 | 职责 | 碰什么 | 不能做什么 |
|---|---|---|---|
| demux（1 个） | `av_read_frame`，按 stream_index 分发到 videoQ/audioQ；执行 seek；EOF 后等待 seek/close | `AVFormatContext`、两个队列 | 不解码、不渲染、不睡长觉（除了等新数据） |
| video（1 个） | 从 videoQ 取包 → 解码 → 按 pts 与主时钟差节流 → sws 转 RGBA → 发 `frameReady` | `AVCodecContext(video)`、SwsContext | 不阻塞 demux；等待同步时也要能被 quit/seek 打断 |
| audio（SDL 回调，1 个） | 从 audioQ 取包 → 解码 → swr 转 S16 → 混音量 → 推进音频时钟 | `AVCodecContext(audio)`、SwrContext、PCM 缓冲 | **绝不阻塞**（回调卡住 = 爆音），所以只做非阻塞 `get` |
| GUI | 控件、QTimer(200ms) 刷新进度/状态、发命令 | PlayerCore 的原子标志 | 不碰解码器、不做磁盘/网络等待 |

~~~text
            ┌───────────────┐  put(AVPacket)   ┌──────────────┐
 av_read_frame │  demux 线程   │ ───────────────► │ videoQ（锁） │ ──► video 线程 ──► QImage ──信号──► GUI
            │  (seek 也在这) │ ───────────────► │ audioQ（锁） │ ──► SDL 回调（不阻塞）
            └───────────────┘                  └──────────────┘
                    ▲                                                   │
                    │ seekReq/target（原子）                             │ 音频时钟（原子）
                    └──────────────── GUI: seek() ◄─────────────────────┘
~~~

**为什么不是 1 个线程**：如果 demux 和 video 共用线程，视频按 pts 等待（可能几百 ms）时 demux 停摆，
audioQ 立刻抽干 → 爆音。**为什么不是 4 个**：音频解码放在回调里已经是最短路径（44.1kHz/1024 样本
≈ 23ms 一次），再多一个线程只会多一次 PCM 拷贝和同步点。

线程间通信只有四种手段：

| 手段 | 用在哪 | 备注 |
|---|---|---|
| 队列 + mutex/cond | videoQ / audioQ | `PacketQueue::put/get/flush/abort`，`av_packet_move_ref` 转移所有权 |
| mutex | `audioMutex`：音频解码、seek 时 flush 解码器/清 PCM 缓冲 | 只有 demux（seek）和音频回调会拿 |
| 原子量 | paused / quit / seekReq / seekTargetMs / seekGen / seekDropMs / audioClockMs / positionMs | 单值状态，不用锁 |
| Qt 信号（queued） | frameReady / frameSync / positionChanged / stateChanged / bufferingChanged / ended | worker 直接 emit，Qt 排队到 GUI 线程 |

> **已知限制（明确记录）**：队列目前没有按字节数反压。本地文件小（几十 MB）时 demux 会很快把
> 包都读进内存；大文件会持续增长。后续若做长片/4K，应改成"队列超过 N MB 时 put 阻塞"，
> 并在 seek/close 时唤醒。这条不影响现有 20~40MB 场景，但面试被问"内存会不会爆"要如实说。

## 2. 音画同步方案

### 2.1 为什么音频做主时钟

- 声卡的消费速率由硬件决定（44.1kHz 时钟晶振），**软件改不了**。音频快了慢了就是爆音/卡顿，
  没有"等一等"的余地。
- 视频相反：晚 40ms 人眼几乎无感，丢一帧也无感。所以让视频去追音频，是最便宜的方案。
- 反过来（视频主时钟、音频去追）需要重采样/变调或丢样本，音质立刻可闻，工程上得不偿失。

### 2.2 音频时钟怎么算

```text
clock = framePts + consumedSamples / 44100 * 1000   (ms)
```

- `framePts`：解码出这一帧时记录的 pts（毫秒）。**不是解码时刻**，是这帧第一个样本的播放时刻。
- `consumedSamples`：SDL 回调把这帧 PCM 交给声卡时累计的样本数（S16 立体声，2 字节/声道）。
- 只增不减：`if (newClock > clock) clock = newClock`。seek 时由 doSeek 直接设定新基准，
  旧帧在 seek 屏障处被丢弃，不会把时钟拉回去。

这样时钟是"**已经交给声卡的时间**"，比"解码到哪了"更接近耳朵听到的位置，误差上限是
SDL 设备缓冲（1024 样本 ≈ 23ms）。

### 2.3 视频怎么节流

每解码出一帧，拿 `pts` 与主时钟比：

| 差值 `diff = pts - clock` | 动作 | 常量 |
|---|---|---|
| `diff <= 8ms` | 直接渲染 | `kSyncSlopMs = 8` |
| `8ms < diff <= 2000ms` | 每 5ms 睡一次，直到追上（最多 400 次） | — |
| `diff > 2000ms` | 判定时钟异常，直接渲染（避免整段卡死） | — |
| `diff < -120ms`（视频落后） | **丢帧**，不渲染也不更新进度 | `kVideoDropMs = 120` |

**为什么落后要丢帧而不是慢放**：慢放会让视频永远追不上音频（音频不会等你），越拖越多，
最后音画差几秒。丢帧是唯一能"局部牺牲画面、保住同步"的手段。120ms 的选择：约 3 帧（25fps），
低于它就等（人眼看不出 3 帧内的滞后），高于它继续等只会累积。

8ms 的容差是为了避免"每帧都 sleep 一次"：帧间隔 40ms，若要求 diff<=0 才渲染，几乎每帧都要睡。

### 2.4 无音频轨

`audioDev == 0 || !audioClockValid` 时退回系统时钟：

```text
clock = anchorPts + (now - anchorWallMs)
```

- 锚点**只在"确认要渲染的帧"交付前设置**（bug #3 的教训：不能拿 seek 前的旧帧当锚点）。
- seek 后 `wallStarted=false`，下一帧重新锚定；暂停恢复时用当前 position 重新锚定。
- 纯视频回归：20 次 seek 后最大漂移 16ms（见 phase-9.md）。

### 2.5 怎么证明它同步

`PlayerCore::frameSync(videoPts, clock)` 每渲染一帧发一次，回归程序统计 `|videoPts-clock|`
的最大值/当前值。这是**可量化**的证据，不是"看起来不卡"：

| 场景 | 修复前 | 修复后 |
|---|---|---|
| seek 风暴（20 次） | 50303ms | **109ms**（≤ 120ms 丢帧阈值） |
| 暂停→恢复 | — | 12~20ms |
| 纯视频 seek 风暴 | 54841ms | 8~40ms |

> 测量口径：`frameSync` 里的时钟必须在**渲染前**采样。渲染含 sws + QImage 拷贝（毫秒级），
> 若渲染后再读时钟，期间正好发生 seek，就会把"旧帧 + 新时钟"记成 50s 漂移（假象）。
> 这一条本身也是回归里抓出来的：真 bug 修完后偶发一次 50s，定位为测量时序而非同步错误。

## 3. seek 时序与防花屏

### 3.1 一次 seek 的完整顺序

~~~text
GUI: seek(ms)
  └─ seekTargetMs = ms; seekReq = true; positionMs = ms      ← 只让 UI 跟手，不动时钟

demux 线程下一轮循环:
  1. av_seek_frame(fmt, -1, ts, AVSEEK_FLAG_BACKWARD)        ← 退到目标前的关键帧
  2. videoQ.flush(); audioQ.flush()                          ← 丢掉旧包
  3. lock(audioMutex):
       avcodec_flush_buffers(video); avcodec_flush_buffers(audio)
       audioBufSize = audioBufIndex = 0                       ← 丢掉已解码未播的 PCM
     unlock
  4. ++seekGen                                                ← 旧包解出的帧作废
  5. clock = target; audioFramePts = target; consumed = 0     ← 时钟基准在这里重置
  6. seekDropMs = target                                      ← 早于目标 20ms 的帧丢弃
~~~

顺序不能换：

- **flush 必须在重置时钟之前**：否则旧包还能解出旧帧，新时钟已经生效 → 画面在 55s、时钟在 4.8s。
- **时钟不能在 GUI 线程重置**（bug #1）：GUI 只是"提请求"，demux 什么时候真正 seek 完不确定；
  提前改时钟，等待期间交付的每一帧都是错的。
- **音频缓冲要在 audioMutex 里清**：回调线程正在解码/拷贝时清，要么读到一半的数据，要么丢锁。

### 3.2 双屏障各防什么

| 屏障 | 判据 | 防的是 | 不做的后果 |
|---|---|---|---|
| `seekGen`（代数） | 包入队时的代数 ≠ 当前代数 → 解出的帧丢弃 | **seek 前入队、seek 后才解码**的旧包 | 向后 seek 回跳（55s 的帧出现在 4.8s 位置） |
| `seekDropMs`（时间） | `pts < target - 20ms` → 丢弃 | **seek 后**从关键帧开始解码、但还没到目标的那几帧 | 每次 seek 先闪一下目标前 0.5s 的画面（"花屏感"） |

两者缺一不可：`gen` 只能识别"旧数据"，识别不了"新数据但还没到目标"；`seekDropMs` 只能比较时间，
识别不了"时间看着对、其实是旧位置"（向后 seek 时 55s ≥ 4.8s，屏障会放行）。

**解除屏障的规则**：只有**确认要渲染**的帧（通过 gen、通过 pts、通过落后阈值、没暂停）才清
`seekDropMs`。曾经用"第一帧 pts ≥ target 就清"，结果向后 seek 时旧帧先把屏障清了（bug #3）。

**交付前必须复检**：`syncToClock()` 可能睡几百 ms，这期间可能又发生 seek。等待结束后要再查
一遍 gen / 屏障 / 落后阈值（bug #2）。

### 3.3 三个 bug 的因果（都是 seek 风暴抓出来的）

| # | 症状 | 根因 | 修法 |
|---|---|---|---|
| 1 | 风暴中漂移 50.3s | `seek()` 在 GUI 线程把 audioClock 改成目标，demux 还没 flush，旧帧与新时钟同时存在 | 时钟只在 doSeek 重置 |
| 2 | 55.4s 旧帧渲染在 19.8s 时钟上 | 帧在 `syncToClock` 等时钟时又发生 seek，醒来直接交付 | 交付前复检 gen/屏障/落后 |
| 3 | 无音频时画面 4.8s 按 2.1s 计时 | 屏障被"目标之后的旧帧"提前解除；wall clock 锚点被旧帧占用 | 只由有效帧解屏障/设锚点 |

## 4. 边下边播（GrowingFileIO）

### 4.1 状态机

~~~text
            ┌──────────────┐  文件还不存在 / 长度为 0
            │ 等待文件出现  │◄───────────────┐
            └──────┬───────┘                │ 30ms 后重试（stall=true）
                   │ 文件存在                │
                   ▼                        │
            ┌──────────────┐  pos < size    │
            │  正常读取     │───────────────►│ 返回字节
            └──────┬───────┘
                   │ pos >= size
                   ▼
     complete? ──是──► 返回 AVERROR_EOF（demux 正常收尾，播到结尾）
        │否
        ▼
  等待新块（cond.wait_for 30ms，stall=true）──► abort? ──► 返回 AVERROR_EXIT
~~~

关键点：

- **返回 EOF 会让 demuxer 认为"流结束"**：播放器会走 `ended`，用户看到"播完了"，而实际只下了 4MB。
  所以未完成时**必须阻塞**而不是 EOF。
- 阻塞粒度 30ms：既不会空转烧 CPU，也能让 `close()` 在 30ms 内退出（`abort()` 唤醒 cond）。
- `stall` 回调只在"进入等待/离开等待"时触发一次，避免每个 30ms 都刷 UI。
- `sourceComplete=true` 由 transfer 层在下载完成时设置（`PlayerCore::setSourceComplete`），
  之后 read 才允许返回 EOF。

### 4.2 为什么等首块落盘才 open

`avformat_open_input` 会在**调用线程**里读文件（探针 + moov）。如果在 GUI 线程对一个还没数据的
`.part` 调用，它会阻塞在 GrowingFileIO 的等待里；而下载的 `DownloadDataRs` 也由 GUI 线程的
事件循环分发 → **互等死锁**。

所以 UI 侧规则是：`bytesDone > 0`（首块 4MB 写完）再 `open(part, progressive=true)`。
此时 moov 与首个 mdat 片段都已可读，open 不会等。

### 4.3 probesize / analyze 为什么要限死

FFmpeg 默认 `probesize` 5MB、`analyzeduration` 5s。边下边播时这些数据可能**还没下到**，
open 就会阻塞在"等第 5MB"。当前实现：

```cpp
fmt->probesize = 512 * 1024;              // 512KB，够识别 mp4 + mpeg4/aac
fmt->max_analyze_duration = 2 * AV_TIME_BASE;   // 2s
```

代价是"探测信息可能不全"（例如某些流拿不到 duration/尺寸），收益是**首帧延迟可控**。
实测首帧 188ms（phase-9.md）。

### 4.4 对容器的要求

MP4 的 `moov` 必须在文件前部（faststart）。如果 moov 在尾部（普通 `ffmpeg` 默认输出），
边下边播必须等整个文件下完才能 open —— 这不是播放器能绕过的，属于**素材生产规范**
（`-movflags +faststart`）。

## 5. 渲染接口

~~~cpp
class VideoSurface {                 // ui/VideoSurface.h
public:
    virtual QWidget* widget() = 0;
    virtual void setImage(const QImage& image) = 0;
    virtual void clear() = 0;
    virtual QString backendName() const = 0;   // "gl" / "painter"
};
~~~

| 后端 | 实现 | 适用 |
|---|---|---|
| `GlVideoSurface`（默认） | QOpenGLWidget + 2D 纹理 + 简单 shader，`glViewport` 做 letterbox | 有 GL 的桌面 |
| `PainterVideoSurface` | QWidget + `QPainter::drawImage` + `SmoothPixmapTransform` | 远程桌面、虚拟机、GL 初始化失败 |

选择逻辑：`createVideoSurface(parent, forcePainter)`；`forcePainter` 来自 `--painter`，
否则探测 `QOpenGLContext::create()`，失败自动回退。启动日志会打印 `player surface: gl|painter`。

宽高比统一由纯函数负责（`ui/Letterbox.h`），两个后端共用，避免"换后端画面位置变了"：

```text
imageAspect = image.w / image.h;  targetAspect = target.w / target.h
imageAspect > targetAspect → 宽度撑满，上下黑边（letterbox）
否则                        → 高度撑满，左右黑边（pillarbox）
```

6 个单测覆盖 16:9/4:3/竖屏/同比例/极小目标/非法尺寸。

## 6. 生命周期与线程安全

### 6.1 PacketQueue

- `std::deque<AVPacket*>` + `std::mutex` + `condition_variable`（不用 SDL_mutex，符合 C++11 规范）。
- `put` 用 `av_packet_move_ref` 接管所有权；`get` 再 move 出去；`flush` 逐个 `av_packet_free`。
- `abort()` 置位并 `notify_all`，阻塞中的 `get` 立即返回 false；`reset()` 用于重新打开。
- 音频回调只用**非阻塞** `get`：宁可这一拍静音，也不能卡住声卡线程。

### 6.2 跨线程信号

- worker 直接 `emit`，接收者在 GUI 线程 → Qt 自动 queued。QImage 是注册过的 metatype 且隐式共享，
  跨线程传递安全。
- `frameSync` 每帧一发（25/s），只做数值统计，不进 UI 队列堆积（接收者是轻量 lambda）。
- GUI → worker 全部走原子标志 + 队列，不做 `invokeMethod` 同步调用，避免 GUI 卡在解码线程上。

### 6.3 析构顺序（踩过崩溃）

正确顺序：

~~~text
MainWindow::~MainWindow
  └─ PlayerPane::shutdown()        ← 此时兄弟控件都还活着
       ├─ 若还有 playback 任务 → queue->cancel()（会 emit changed，安全）
       ├─ m_player->close()        ← 停线程/关设备
       └─ disconnect(queue) + blockSignals
  └─ ~QMainWindow → 子控件逐个析构
       └─ ~PlayerPane：只断连接、不再碰 TransferQueue
~~~

**为什么不能反过来**：在 `~PlayerPane` 里 `cancel()`，`changed()` 会同步进到还没销毁的
`TransferPane::refresh()`，而那时 QSplitter 正在删子控件 → Qt 崩在
`QWidgetPrivate::reparentFocusWidgets`（gdb 定位过）。同理，`notice` 信号也不能在析构阶段
抛给半销毁的 MainWindow（Toast 可能已经被 delete）。

`PlayerCore::close()` 内部顺序：

```text
quit = true
→ audioQ.abort() / videoQ.abort() / io->abort()   （唤醒所有阻塞）
→ join(demux) / join(video)                       （等线程真正退出）
→ SDL_CloseAudioDevice                             （会等回调返回）
→ free frames/swr/sws/codecs → avformat_close_input → delete io
```

先 abort 再 join 是关键：demux 可能正阻塞在 GrowingFileIO 的等块里，不 abort 就永远 join 不回来。

## 7. 面试问答（自问自答）

**Q1：为什么边下边播要阻塞读，而不是读到文件尾就返回 EOF？**
EOF 对 demuxer 是"流结束"的语义：它会 flush 解码器、发结束事件，播放器就停在 4MB 处了。
阻塞读让 demuxer 认为"数据只是慢"，解码/同步/时钟全部照常，等下载推进后自然继续。
另外，返回 EOF 后再想继续，只能重新 open + seek，等于重建整条管线。

**Q2：视频落后为什么要丢帧，不能慢放追吗？**
音频由声卡时钟驱动，不会等视频；慢放只会让差距越来越大。丢帧是唯一能收敛的手段。
120ms ≈ 3 帧，低于它靠等待（人眼无感），高于它继续等只会累积延迟。

**Q3：为什么音频做主时钟，而不是视频或系统时钟？**
声卡消费速率由硬件晶振决定，软件无法微调；音频抖动是"听得见"的，视频延迟是"看不见"的。
让视频追音频成本最低。无音频时才退回系统时钟，并用"视频 pts 锚定"的方式让画面自己当基准。

**Q4：音频时钟为什么按"已消费样本数"推进，而不是解码到哪算哪？**
解码通常跑在播放前面（缓冲区），按解码 pts 计时会让时钟超前 1~2 个缓冲，视频就会提前渲染，
表现为"音画不同步但看起来每帧都对"。按已交声卡的样本数推进，误差上限就是设备缓冲（≈23ms）。

**Q5：seek 时为什么要"清队列 + flush 解码器 + 清 PCM"三件事都做？**
只清队列：解码器内部还有 B 帧/预测帧，会吐出 seek 前的画面；只 flush 解码器：队列里的旧包
又会被解出来；不清 PCM：seek 后还会听到最多一帧的旧声音。三件事都做，且要在 audioMutex 里做，
避免和音频回调撞车。

**Q6：时钟基准为什么必须在 demux 线程 flush 之后重置？**
GUI 的 `seek()` 只是"提请求"。真正 seek 完之前，管线里还是旧位置的数据；提前改时钟，
这段时间交付的帧就会"旧画面配新时钟"（实测漂移 50s）。时钟必须和"flush 生效"同一时刻更新。

**Q7：seekGen 和 seekDropMs 为什么都要？只留一个不行吗？**
`seekGen` 认"数据新旧"，`seekDropMs` 认"时间是否到目标"。向后 seek 时旧帧的时间（55s）
大于新目标（4.8s），时间屏障会放行，只能靠代数识别；而从关键帧解码到目标之间的新帧，
时间没到目标，只能靠时间屏障丢弃。两者防的是不同的窗口。

**Q8：为什么要 faststart？**
MP4 的索引（moov）在文件尾部时，播放器必须拿到整个文件才能建立索引。边下边播只能等下载完成，
"首块起播"无从谈起。`-movflags +faststart` 把 moov 挪到前面，打开时只需几百 KB。

**Q9：probesize / analyzeduration 为什么要调小？**
默认值（5MB/5s）在边下边播时可能还没下到，`avformat_open_input` 会一直等数据；而下载响应的
分发也在 GUI 线程 → 死锁。调小后 open 只读已到达的首块，代价是某些元信息可能识别不全。

**Q10：为什么 `#define SDL_MAIN_HANDLED`？**
SDL 为了跨平台会把 `main` 重定义成 `SDL_main` 并要求链接 `SDL2main`。我们的入口是 Qt 的
`main`（QApplication 必须在最前），定义这个宏让 SDL 不再接管入口。

**Q11：为什么 `opened` 信号里的宽高可能是 0×0？**
有些封装（例如 mpeg4 的 mp4v）不在容器头里写宽高，要等第一帧解码才知道。播放器以
`frame->width/height` 为准做转换和 letterbox，`opened` 的宽高只当提示。

**Q12：QImage 每帧拷贝，性能扛得住吗？**
640×360 RGBA 约 900KB/帧，25fps 约 22MB/s，一次拷贝在现代机器上是微秒级。4K/60 会是 2GB/s 量级，
那时需要走硬解纹理（`VideoSurface` 增加纹理重载），但绝不能把 AVFrame 漏进 `ui/`。

**Q13：3 个 worker 会不会太多/太少？**
demux 不能被视频等待拖住（否则音频饿死），音频必须在声卡回调里（否则多一次拷贝和延迟抖动），
视频需要一个独立线程做 pts 节流。GUI 只发命令和收状态。所以 3 个是下限，再加只会多同步点。

**Q14：暂停/恢复为什么不会漂？**
暂停时 `paused=true` 且 `SDL_PauseAudioDevice(1)`：音频回调停、音频时钟停、视频线程空转等待；
恢复时 `play()` 用当前 position 重新锚定系统时钟（无音频时）或继续用音频时钟（有音频时）。
回归实测恢复后 14ms 内，最大 14ms。
