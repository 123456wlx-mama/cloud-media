## 1. 目标与边界

目标：提供一套可压测、可滚动、可追踪、崩溃前能落盘的异步日志，服务端与客户端共用。

必须满足：

- 双缓冲异步：业务线程只负责格式化与入队，落盘在后台线程。
- 分级：TRACE / DEBUG / INFO / WARN / ERROR / FATAL / OFF。
- 滚动：按大小与日期；保留天数可配置。
- 格式固定：时间 | 级别 | tid | 文件:行 | traceId | 消息。
- RAII：析构时 flush 并 join；显式 shutdown 幂等。
- 压测可开关：关闭后不格式化、不入队，避免日志污染性能数据。

不做：远程日志采集、日志检索服务、结构化 JSON、日志加密。需要时在 Phase 6 之后评估。

## 2. 总体架构

~~~mermaid
flowchart LR
    P1[业务线程 1] --> F[front buffer<br/>vector of string]
    P2[业务线程 N] --> F
    F -->|swap| B[back buffer]
    B --> W[后台写线程]
    W --> FILE[server.log]
    W -->|size/date| R[滚动与保留]
    T[条件变量/定时] --> W
~~~

线程模型：

- 业务线程：判断级别 → 格式化整行 → 加锁 push 到 front → 达到批量阈值或定时唤醒。
- 后台线程：等待条件变量 → 交换 front/back → 释放锁 → 写 back → 定期 flush → 检查滚动。
- 锁只保护 front 与 swap，不覆盖文件 IO。
- 只有一个后台写线程，滚动、flush、清理都在该线程内完成，避免多线程写文件。

## 3. LogConfig

| 字段 | 类型 | 默认值 | 校验 | 说明 |
|---|---|---|---|---|
| path | string | logs/server.log | 非空，目录可创建 | 活动日志文件 |
| level | string | info | TRACE~FATAL/OFF | 低于该级别的日志不格式化 |
| max_size_mb | int | 100 | 1~4096 | 单文件大小上限 |
| roll_days | int | 7 | 1~365 | 滚动文件保留天数 |
| async | bool | true | 0/1 | false 为同步模式，仅供基准对比 |
| console | bool | true | 0/1 | 是否同时输出到控制台 |
| flush_interval_ms | int | 1000 | 10~60000 | 定时 flush 间隔 |
| max_pending_mb | int | 64 | 1~1024 | 待写数据上限 |
| fsync_on_fatal | bool | true | 0/1 | FATAL 时是否 fsync |
| max_line_bytes | int | 8192 | 1024~65536 | 单行上限，超出截断并标记 |

初始化失败（目录不可写、文件打不开、参数非法）返回 ErrorCode，不进入半初始化状态。

## 4. 级别与格式

### 4.1 级别

| 级别 | 用途 | 默认 |
|---|---|---|
| TRACE | 逐包/逐帧细节，仅本地调试 | 关闭 |
| DEBUG | 关键分支、状态变化 | Debug 构建可开 |
| INFO | 启动、连接、登录、任务完成 | 开 |
| WARN | 可恢复异常、降级、重试 | 开 |
| ERROR | 请求失败、资源错误 | 开 |
| FATAL | 进程无法继续 | 开，立即 flush |
| OFF | 全部关闭 | 压测时使用 |

级别比较用整数枚举，日志宏先判断 enabled 再构造消息，避免关闭时仍付出字符串拼接成本。

### 4.2 行格式

~~~text
2026-10-18 15:30:00.123 | INFO  | tid=1 | EventLoop.cpp:88 | trace=9f2a1c | accepted fd=12
~~~

| 段 | 规则 |
|---|---|
| 时间 | 本地时间，YYYY-MM-DD HH:MM:SS.mmm |
| 级别 | 5 字符左对齐：TRACE/DEBUG/INFO /WARN /ERROR/FATAL |
| tid | 进程内自增的逻辑线程号，从 1 开始，稳定可读；不直接打印 OS tid |
| 文件:行 | 取 __FILE__ 的 basename + 行号，避免绝对路径泄露 |
| traceId | thread_local；无则为 -；建议 8~16 位十六进制 |
| 消息 | 单行；换行替换为转义 n；超过 max_line_bytes 截断并追加 ...(truncated) |

示例中的 traceId 由请求入口设置；同一请求跨线程时，投递任务必须显式携带 traceId 并在任务开始时 set_trace_id。

### 4.3 traceId 传播

- 每个连接/请求入口生成 traceId（或从上游协议携带）。
- 同线程内自动继承（thread_local）。
- 线程池任务：任务对象保存 traceId，执行前 set_trace_id，执行后恢复/清空。
- 不依赖隐式全局变量；跨进程不传播（v1 不做分布式追踪）。

## 5. 双缓冲与写入路径

### 5.1 数据结构

- front：vector of string，业务线程写入。
- back：vector of string，后台线程消费。
- mutex：保护 front 与 swap。
- condition_variable：通知后台线程。
- atomic bool stop：退出标志。
- atomic uint64 pending_bytes：待写字节数，用于背压。

### 5.2 写入流程

1. 判断 level <= 当前级别；否则直接返回。
2. 格式化整行（时间在业务线程取，保证时间准确）。
3. 加锁，push 到 front，pending_bytes 增加行长度。
4. 若 front 行数 >= 256 或 front 字节数 >= 64KB，notify_one。
5. 解锁返回；不做文件 IO。

### 5.3 后台流程

1. wait_for(flush_interval_ms) 或 wait 直到 notify/stop。
2. 加锁，swap(front, back)，清空 front，解锁。
3. 若 back 为空且未到 flush 时间，继续等待。
4. 逐行写文件；累计写入字节。
5. 满足 flush 间隔或 back 写完时 flush。
6. 检查日期变化与文件大小，必要时滚动。
7. 清空 back，pending_bytes 减去已写字节。

### 5.4 同步模式

async=false 时，业务线程在锁内直接写文件并 flush；仅用于“同步 vs 异步”基准对比，不用于生产。

## 6. 滚动与保留

### 6.1 文件命名

- 活动文件：logs/server.log
- 滚动文件：logs/server.log.YYYYMMDD-HHMMSS.N
- N 从 1 开始；同一秒内重复滚动则递增，避免覆盖。

### 6.2 触发条件

| 条件 | 检查时机 | 动作 |
|---|---|---|
| 大小 | 每批写完后 | 当前文件 >= max_size_mb 时滚动 |
| 日期 | 每批写入前 | 本地日期与文件日期不同则滚动 |
| 手动 | 运维发送信号/调用接口 | 可选，Phase 2 不做 |

滚动步骤：flush → close → rename → 打开新文件 → 写一条 INFO 记录（rolled from/to）。

### 6.3 保留与清理

- 启动时与每次滚动后扫描 logs/server.log.*。
- 解析文件名中的日期；早于 today - roll_days 的文件删除。
- 只删除匹配前缀与格式的文件，忽略其他文件。
- 清理失败只记录 WARN，不影响主流程。

### 6.4 权限

- POSIX：创建文件使用 0600；目录 0700。
- Windows：依赖默认 ACL；不额外放开权限。
- 日志目录不放在 Web 根目录或共享目录。

## 7. 缓冲上限、丢弃与背压

原则：绝不在业务/IO 线程阻塞等磁盘。

| pending 状态 | 策略 |
|---|---|
| < max_pending | 正常入队 |
| >= max_pending | 丢弃 TRACE/DEBUG，计数 dropped_low |
| >= 2 倍 max_pending | 继续丢弃 WARN，计数 dropped_warn；ERROR/FATAL 仍接收 |
| 硬上限 4 倍 max_pending | 只接收 FATAL；计数 dropped_all |

- 丢弃时只增加原子计数，不做同步 IO。
- shutdown 时把 dropped 计数汇总写一行 WARN（若还能写）。
- 压测时直接 level=OFF 或 async=false 对比，不依赖丢弃策略。
- 该策略意味着极端过载下日志可能不完整；这是有意的可用性取舍，写入设计文档并在监控中暴露。

## 8. 生命周期与 RAII

### 8.1 初始化

Logger::init(cfg, err)：

1. 校验配置。
2. 创建目录（若不存在）。
3. 打开活动文件（追加模式）。
4. 启动后台线程。
5. 写一条 INFO：version、pid、log path、level。

重复 init：返回 AlreadyExists 或先 shutdown 再 init；v1 选择“已初始化则返回错误”，避免隐式重启。

### 8.2 关闭

- shutdown()：设置 stop → notify → join → 交换并写完剩余 → flush → close。
- 幂等：多次调用安全。
- 析构函数调用 shutdown，作为兜底；主函数应显式调用，避免静态析构顺序问题。
- shutdown 后的日志：丢弃并写 stderr（若可用），不再入队。
- FATAL：立即 flush；fsync_on_fatal=true 时 fsync；是否 abort 由调用方决定，日志库不擅自终止进程。

### 8.3 异常安全

- 构造/初始化失败不留下半开文件或线程。
- 后台线程捕获所有异常，记录到 stderr 后退出；不让异常穿过线程边界。
- 文件写失败：重试一次；仍失败则写 stderr 并停止后台线程，避免忙等。

## 9. 性能与基准

### 9.1 测量方法

工具：benchmarks/log_bench（Phase 2 实现）。

参数：

- --count 1000000
- --threads 1 / 8
- --sync / --async
- --file build/log_bench.log

指标：elapsed_ms、lines_per_sec、MB/s、dropped、文件大小。

### 9.2 验收

- 1M 行、单线程、异步：无丢失（dropped=0），记录实测行/秒。
- 8 线程 × 125k 行：总行数准确，无数据竞争（TSan 跑一次）。
- 同步 vs 异步：记录两者数字，不承诺固定倍数；异步的目标是降低业务线程阻塞时间。
- 结果写入 docs/benchmark/日志性能.md，注明机器、编译器、构建类型。

## 10. 与 spdlog 的选型对比

| 维度 | 自研 Logger | spdlog |
|---|---|---|
| 依赖 | 无第三方依赖 | 依赖 fmt（或 bundled fmt） |
| C++ 标准 | 纯 C++11 | 1.x 支持 C++11 |
| 异步 | 双缓冲 + 后台线程，自控 | 内置 async logger + 线程池 |
| 滚动 | 自研按大小/日期 + 保留天数 | rotating_file_sink / daily_file_sink |
| 格式化 | 自研固定格式 | fmt 风格，功能强 |
| 编译/体积 | 代码量小，编译快 | header-only 默认，编译时间与体积较大 |
| 成熟度 | 自己维护，需测试 | 成熟、社区广 |
| 可控性/面试叙事 | 完全可控，能讲双缓冲、背压、滚动 | 黑盒较多，面试只能讲选型 |
| 风险 | 自研 bug、边界多 | 版本/依赖管理 |

决策：默认自研。理由是后端岗面试会追问“为什么异步、锁在哪、丢日志怎么办、滚动怎么保证不丢”，自研能给出实现级答案；同时避免在 Phase 2 引入 fmt 版本与编译复杂度。若工期紧张，允许整体替换为 spdlog，但不得两套并存。

## 11. 测试与验收

| 用例 | 期望 |
|---|---|
| 级别过滤 | level=WARN 时 INFO 不落盘，ERROR 落盘 |
| 格式 | 行内包含时间、级别、tid、文件:行、trace、消息 |
| 8 线程 × 1000 行 | shutdown 后正好 8000 行，抽样内容完整 |
| 大小滚动 | max_size 很小时生成多个文件，总行数不丢 |
| 日期滚动 | 注入假时钟跨天，生成新文件（测试用 Clock 接口） |
| flush | 写入后 shutdown，文件非空且无残留 |
| 丢弃策略 | pending 超限时 TRACE 被丢弃，ERROR 保留，计数正确 |
| 同步/异步 | 两种模式总行数一致 |
| 析构 | 不显式 shutdown 也能 flush（best-effort） |
| TSan | 并发写入无数据竞争 |

验收：上述用例全部通过；1M 行基准有数据；GCC 警告选项 -Wall -Wextra 零警告；无裸 new/delete。

| log.level | string | info | 是 | TRACE~FATAL/OFF |
| log.max_size_mb | int | 100 | 否 | 1~4096 |
| log.roll_days | int | 7 | 否 | 1~365 |
| log.async | bool | true | 否 | 0/1/true/false |
| log.flush_interval_ms | int | 1000 | 否 | 10~60000 |
| log.max_pending_mb | int | 64 | 否 | 1~1024 |
| log.fsync_on_fatal | bool | true | 否 | 0/1/true/false |
| mysql.host | string | 127.0.0.1 | 是 | 非空 |
| mysql.port | int | 3306 | 是 | 1~65535 |
| mysql.user | string | 无 | 是 | 非空 |

| redis.db | int | 0 | 否 | 0~15 |
| transfer.download_dir | string | downloads | 否 | 非空 |
| transfer.max_connections_per_file | int | 4 | 否 | 1~8 |
| transfer.max_concurrent_files | int | 2 | 否 | 1~8 |

### 12.3 解析规则

- UTF-8；允许 BOM，解析前跳过。
- 行首尾空白忽略；空行忽略。
- 注释：# 或 ; 开头；不支持行尾注释。
- 段：[section]；key=value；key/value 两侧 trim。
- 值可用单引号或双引号包裹，解析后去掉引号。
- 重复 key：后者覆盖，记录 WARN。
- 缺段/缺 key：必填项报错，错误信息包含 section.key 与行号。
- 不支持嵌套段、数组、变量展开。
- 解析失败 fail fast，不启动半配置服务。

### 12.4 安全

- mysql.password / redis.password 不进入 describe()、不写日志。
- 配置文件权限：POSIX 0600；Windows 依赖 ACL。
- 建议支持环境变量覆盖密码：CM_MYSQL_PASSWORD、CM_REDIS_PASSWORD；配置文件中留空。
- 不在异常信息中回显密码；错误信息只写 key 名。

|---|---|---|---|---|
| 0 | Ok | 成功 | 成功 | — |
| 1001 | InvalidArgument | 通用 | 参数非法 | 否 |
| 1002 | NotFound | 通用 | 资源不存在 | 否 |
| 1003 | AlreadyExists | 通用 | 资源已存在 | 否 |
| 1004 | PermissionDenied | 通用 | 无权限 | 否 |

| 1008 | InternalError | 通用 | 内部错误 | 视情况 |
| 1099 | UnknownError | 通用 | 未知错误（兜底） | 否 |
| 2001 | AuthFailed | 认证 | 账号或密码错误 | 否 |

### 13.2 协议错误码（ERROR_RS 使用）

| 值 | 名称 | 含义 |
|---|---|---|
| 9001 | ERR_BAD_FRAME | 帧头/长度非法 |
| 9002 | ERR_VERSION | 协议版本不支持 |
| 9003 | ERR_UNKNOWN_TYPE | 未知消息类型 |
| 9004 | ERR_PAYLOAD_TOO_LARGE | payload 超过 8MB |
| 9005 | ERR_CRC | CRC 校验失败 |
| 9006 | ERR_HANDSHAKE_REQUIRED | 未完成 HELLO 就发业务消息 |
| 9007 | ERR_DEPRECATED | 已废弃的消息类型（如 10011/10024） |
| 9008 | ERR_TIMEOUT | 握手/心跳超时 |

### 13.3 设计规则

- 使用 enum class，显式赋值；数值一旦发布不得修改。
- 提供 to_string(ErrorCode) 与 is_retryable(ErrorCode)；未知值返回 UnknownError。
- 业务错误与协议错误分号段：1xxx~3xxx 业务，9xxx 协议。
- 模块边界用返回值传递错误，不跨模块抛异常；异常只用于不可恢复的编程错误。
- 错误信息面向用户时用中文文案，面向日志时带错误码与字段名；禁止只回“失败”。
- 协议 ERROR_RS 的 code 使用 9xxx；业务响应中的 code 使用 1xxx~3xxx。
