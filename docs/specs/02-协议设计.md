## 1. 目标与边界

协议 v2 解决旧协议四个问题：无版本、无校验、无序号、裸结构体跨编译器对齐。目标是让 common 层用同一份 Codec 同时服务 Linux 服务端与 Windows 客户端。

边界：

- 只定义帧格式、控制消息、序列化规则与兼容策略；业务消息的 payload 字段表在 Phase 5 的 05-业务设计.md 中冻结。
- 不做加密与压缩；鉴权由登录后的 token 承担，CRC 只做完整性校验。
- 不做协议层重传；TCP 保证可靠，超时与重试由业务层负责。
- 不做 v1 解码；旧客户端兼容策略见第 4 节。

## 2. 帧格式

### 2.1 字段表

| 偏移 | 字段 | 长度 | 类型 | 说明 |
|---|---|---|---|---|
| 0 | MAGIC | 4B | uint32 | 固定 0x434D4456，ASCII 为 CMDV |
| 4 | VERSION | 1B | uint8 | 固定 2 |
| 5 | TYPE | 2B | uint16 | 消息类型，见第 3 节 |
| 7 | LEN | 4B | uint32 | payload 字节数，不含 19B 帧头 |
| 11 | SEQ | 4B | uint32 | 请求/响应关联号；推送为 0 |
| 15 | CRC32 | 4B | uint32 | 校验值，覆盖范围见 2.2 |
| 19 | PAYLOAD | LEN | bytes | 业务数据，字段逐个序列化 |

帧头固定 19 字节。所有整数使用网络字节序（大端）。

### 2.2 CRC32 覆盖范围

CRC32 覆盖从 VERSION 到 PAYLOAD 末尾的连续字节，即偏移 4 到 19+LEN-1：

- 包含：VERSION、TYPE、LEN、SEQ、PAYLOAD
- 不包含：MAGIC、CRC32 自身

算法：标准 CRC-32（多项式 0xEDB88320，初值 0xFFFFFFFF，结果取反），与 zlib/gzip 的 crc32 一致。

### 2.3 长度与边界

| 约束 | 取值 | 处理 |
|---|---|---|
| 帧头长度 | 19B | 固定 |
| 最大 payload | 8MB | LEN 超过 8MB 直接判 BadLength 并断开 |
| 推荐文件块 | 4MB | 与分片上传/下载的 chunk 对齐 |
| 字符串上限 | 64KB | 序列化时校验，超限返回 Error |
| Buffer 上限 | 16MB | 超过上限仍未解出完整帧，判 BadLength 并断开 |

LEN 必须在分配内存前校验，禁止先按 LEN 分配再判断，避免恶意长度导致 OOM。

## 3. 消息类型

### 3.1 号段

| 号段 | 用途 | 说明 |
|---|---|---|
| 10000~10999 | 业务消息 | 保留旧语义，payload 按 v2 重写 |
| 11000~11999 | 控制消息 | HELLO、ERROR、心跳、登出 |
| 12000+ | 预留 | 后续扩展，不得随意占用 |

### 3.2 旧协议号 10000~10029 映射

旧协议号为 4 字节长度 + 裸结构体；v2 只保留“语义映射”，不复用旧结构体布局。

| 旧类型号 | 旧语义 | v2 处理 | 说明 |
|---|---|---|---|

| 10001 | Register RS | 保留 | 错误码统一为 ErrorCode |
| 10002 | Login RQ | 保留 | 增加 client_version/client_id |
| 10003 | Login RS | 保留 | 返回 token、user_id、昵称 |
| 10004 | UploadFile RQ | 保留 | 增加 file_md5、total_size、chunk_size、total_chunks |
| 10005 | UploadFile RS | 保留 | 返回 upload_id、file_id、已存在分片位图 |
| 10006 | FileContent RQ | 保留 | 改为 4MB 分片；payload = 分片头 + 原始字节 |
| 10007 | FileContent RS | 保留 | 返回 seq、offset、校验结果 |
| 10008 | GetFileInfo RQ | 保留 | 增加分页参数（offset/limit） |
| 10009 | GetFileInfo RS | 保留 | 增加 total_count、has_more |
| 10010 | DownloadFile RQ | 保留 | 返回单文件下载元信息与直链 token |
| 10011 | DownloadFolder RQ | 废弃 | v2 不做文件夹打包；客户端多选入队，服务端仅单文件接口（05 Item 19） |
| 10012 | DownloadFile RS | 保留 | 返回文件元信息与分片大小 |
| 10013 | FileHeader RQ | 保留 | 下载文件头，增加 offset |

| 10016 | AddFolder RS | 保留 | 返回新 folder 的 file_id |

被废弃的 10011/10024 在 v2 中收到时返回 ERROR_RS（code=ERR_DEPRECATED），不进入业务分发。

### 3.3 控制消息

| 类型号 | 名称 | 方向 | payload |
|---|---|---|---|
| 11000 | HELLO_REQ | C→S | u16 client_version, u32 client_build, string client_id |
| 11001 | HELLO_RS | S→C | u16 server_version, u32 server_build, u64 server_time_ms |
| 11002 | ERROR_RS | S→C | u32 code, string message |
| 11003 | HEARTBEAT_REQ | C→S | 空或 u64 client_time_ms |
| 11004 | HEARTBEAT_RS | S→C | u64 server_time_ms |
| 11005 | LOGOUT_REQ | C→S | 空 |

11006~11999 预留。控制消息的 SEQ 规则与业务消息一致；ERROR_RS 必须回显触发错误的 SEQ，无法解析 SEQ 时填 0。

## 4. 旧客户端兼容策略

### 4.1 三个候选

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| 双协议并存 | 服务端保留 v1/v2 两套 Codec 与 handler | 旧客户端可继续用 | 两套状态机、两套测试、字段漂移风险；旧协议无版本/CRC，维护成本高 | 不采用 |
| 号段映射 | 把旧类型号映射到 v2 类型号 | 类型表可读，迁移对照方便 | 只解决编号，不解决帧头、字节序、payload 布局；不能单独解码 v1 | 仅作为文档映射，不作为兼容层 |
| **强制升级** | 只接受 VERSION=2；首帧 HELLO 校验；不匹配返回 ERR_VERSION 并断开 | 单 Codec、单状态机、测试矩阵小；错误明确 | 旧客户端不能连 | **采用** |

### 4.2 决策与理由

采用“强制升级 v2”：

1. 客户端与服务端在同一个仓库、同一阶段发布，没有需要长期兼容的线上 v1 客户端。
2. 旧协议是 4 字节长度 + 裸结构体，没有版本与 CRC；要支持 v1 就必须保留旧 Codec、旧分片逻辑和旧错误处理，双份维护，违背“宁可少做三个功能，也要把做的三个讲透”的原则。
3. 号段映射不能解决帧头和 payload 差异，单独使用只是“看起来兼容”，实际无法解码。
4. 明确失败优于静默失败：服务端返回 ERROR_RS（ERR_VERSION）并记录客户端版本，客户端提示“请升级到 v2 客户端”，不会出现“连上了但收不到响应”的静默不兼容。

### 4.3 握手与拒绝流程

~~~mermaid
sequenceDiagram
    participant C as Client
    participant S as Server
    C->>S: HELLO_REQ(version=2, client_id)
    alt version == 2
        S-->>C: HELLO_RS(version=2, server_time)
        Note over C,S: 进入业务消息
    else version != 2
        S-->>C: ERROR_RS(code=ERR_VERSION, message="upgrade to v2")
        S->>S: 记录 client_version/client_id 后关闭连接
    end
~~~

规则：

- 连接建立后 5 秒内必须收到 HELLO_REQ，否则关闭。
- HELLO 之前收到任何业务消息，返回 ERROR_RS（ERR_HANDSHAKE_REQUIRED）并关闭。
- HELLO_RS 之后才允许业务消息。
- 心跳间隔 30 秒；90 秒无任何帧则关闭（服务端 TimerQueue 负责）。
- 旧客户端连接时，服务端只读取 19 字节帧头；若 MAGIC/VERSION 不匹配，最多记录前 32 字节的十六进制摘要（不含 payload），然后关闭。

## 5. Codec 设计

### 5.1 接口

~~~cpp
enum class DecodeStatus {
    Ok,
    NeedMore,
    BadMagic,
    BadVersion,
    BadLength,
    BadCrc,
    UnknownType
};

struct Frame {
    uint16_t type;
    uint32_t seq;
    std::string payload;
};

class Codec {
public:
    static std::string encode(uint16_t type, uint32_t seq,
                              const std::string& payload);
    static DecodeStatus decode(Buffer& in, Frame* out);
};
~~~

接口只依赖 std 与 common/base/Buffer，不依赖 Qt/FFmpeg。

### 5.2 编码流程

1. 校验 payload 长度不超过 8MB；超限返回空串并记录错误。
2. 预留 19 字节帧头。
3. 依次写入 MAGIC、VERSION、TYPE、LEN、SEQ。
4. 追加 payload。
5. 计算 CRC32（覆盖偏移 4 到末尾），回填偏移 15。
6. 返回完整帧字符串。

编码不分配额外的大对象；文件块用 string 移动或直接 append 原始字节。

### 5.3 解码流程

~~~mermaid
flowchart TD
    A[Buffer 可读字节] --> B{>= 19?}
    B -- 否 --> N[NeedMore，不消费]
    B -- 是 --> C{MAGIC 正确?}
    C -- 否 --> E1[BadMagic]
    C -- 是 --> D{VERSION == 2?}
    D -- 否 --> E2[BadVersion]
    D -- 是 --> F{LEN <= 8MB?}
    F -- 否 --> E3[BadLength]
    F -- 是 --> G{可读 >= 19+LEN?}
    G -- 否 --> N
    G -- 是 --> H{CRC 正确?}
    H -- 否 --> E4[BadCrc]
    H -- 是 --> I{类型已知?}
    I -- 否 --> E5[UnknownType]
    I -- 是 --> J[复制 payload，retrieve 整帧，返回 Ok]
~~~

状态语义：

| 状态 | 是否消费 Buffer | 调用方动作 |
|---|---|---|
| Ok | 是，消费 19+LEN | 分发业务/控制消息 |
| NeedMore | 否 | 继续读 socket，等待更多字节 |
| BadMagic / BadVersion | 否 | 记录后关闭连接 |
| BadLength | 否 | 记录后关闭连接，禁止按 LEN 分配 |
| BadCrc | 否 | 记录后关闭连接，不投递业务 |
| UnknownType | 否 | 回 ERROR_RS（ERR_UNKNOWN_TYPE）后关闭；HELLO 前直接关闭 |

错误处理不得打印 payload 内容；只记录 type、len、seq、状态与连接标识。

### 5.4 SEQ 规则

- 每个连接独立维护递增 SEQ，请求从 1 开始；uint32 回绕到 1（跳过 0）。
- 响应必须回显请求 SEQ；推送消息 SEQ=0。
- 服务端每个连接保留最近 64 个已处理 SEQ，重复 SEQ 直接丢弃并记录（TCP 可靠，正常情况下不会出现）。
- 业务层超时重试必须使用新 SEQ，避免和旧响应混淆。

## 6. Buffer 设计（粘包/半包）

### 6.1 结构

~~~text
+----------------+------------------+----------------+------------------+
| 已读区域       | readable 可读区  | writerIndex    | writable 可写区  |
| (readerIndex)  |                  |                |                  |
+----------------+------------------+----------------+------------------+
0                readerIndex        writerIndex      capacity
~~~

字段：vector<char> storage、size_t readerIndex、size_t writerIndex。

### 6.2 接口

| 方法 | 语义 |
|---|---|
| append(const char*, size_t) | 追加数据；空间不足时先 compact，再按 2 倍扩容 |
| append(const std::string&) | 同上 |
| peek() | 返回可读区起始指针；下一次 append/retrieve 后失效 |
| readableBytes() | writerIndex - readerIndex |
| writableBytes() | capacity - writerIndex |
| retrieve(size_t) | readerIndex 前移；超过可读长度则断言/返回错误 |
| retrieveAsString(size_t) | 复制并前移；用于取 payload |
| ensureWritable(size_t) | 保证可写空间；必要时 compact 或扩容 |
| compact() | 把未读数据移到 0，重置索引 |
| reset() | 清空并保留容量 |

### 6.3 粘包/半包处理

- 半包：readableBytes < 19 或 < 19+LEN 时返回 NeedMore，Buffer 原样保留。
- 粘包：一次 read 可能包含多帧；调用方循环 decode，直到 NeedMore。
- 非法长度：LEN > 8MB 或 Buffer 超过 16MB 仍未解出完整帧，直接断开，避免无限增长。
- 扩容上限 16MB；超过后不再扩容，返回错误并关闭连接。
- peek 返回的指针只在当前 decode 调用内有效；复制 payload 后再 retrieve。

## 7. 序列化约定

| 类型 | 编码 | 说明 |
|---|---|---|
| u8/u16/u32/u64 | 大端定长 | 不使用结构体 memcpy |
| string | u32 长度 + UTF-8 字节 | 长度上限 64KB |
| bytes | u32 长度 + 原始字节 | 用于文件块；上限 8MB |
| bool | u8，0/1 | 不接受其他值 |

规则：

- 禁止直接发送 C++ struct；禁止依赖编译器 padding/对齐。
- 字段顺序固定；新增字段只能追加到 payload 末尾，并提升 VERSION 或使用可选扩展区；v2 内不改变已有字段语义。
- 文件块 payload：u32 chunk_index + u32 offset + u32 data_len + raw bytes；data_len 与 LEN 一致校验。
- 业务消息的完整字段表在 Phase 5 冻结；本文只固定原语与控制消息。

## 8. 安全与可观测性

- CRC32 只保证传输完整性，不提供认证；认证由登录 token 承担。
- LEN 上限、Buffer 上限、字符串上限三层防护，避免 OOM。
- 未知类型、坏帧、版本不符都必须显式记录并断开，不得静默丢弃。
- 日志只记录 type、seq、len、状态、连接 id；禁止记录 payload、密码、token。
- 单个连接的错误次数超过阈值（如 10 次/分钟）直接断开，防刷。
- 协议错误码的数值表见 03 第 13.2 节；本文只使用名称，03 定义数值。

## 9. 测试与验收

| 用例 | 期望 |
|---|---|
| 正常帧 encode→decode | Ok，type/seq/payload 一致 |
| 0/1/18/19 字节半包 | NeedMore，Buffer 不变 |
| 19+LEN-1 字节半包 | NeedMore |
| 两帧粘包 | 连续两次 Ok，第二次后 Buffer 为空 |
| 翻转 MAGIC | BadMagic |
| VERSION=1/3 | BadVersion |
| LEN=8MB+1 | BadLength，不分配 |
| 翻转 payload 一个字节 | BadCrc |
| 未知类型 19999 | UnknownType |
| SEQ 回绕 | 从 1 继续，跳过 0 |
| Buffer 扩容/compact | 数据不丢失，索引正确 |
| 随机字节 fuzz | 不崩溃、不越界、状态合法 |

验收：上述用例全部通过；Codec/Buffer 单测 ≥15 例；fuzz 在 Phase 6 补 1M 随机输入无崩溃；协议文档与 message_type.h 的类型表逐项一致。

## 9. Phase 5 实现回填（2026-10-19）

以下是 v2 最终实现，与第 2 节旧表不一致处以本节为准：

| 类型号 | 实现用途 | 说明 |
|---|---|---|
| 10011 | DownloadDataRs | 复用废弃的 DownloadFolderRq 槽位；payload 是**纯 raw 块字节**（无结构体），LEN = 块长度，SEQ 回显 10013 的请求 SEQ |
| 10024 | QuickUploadRs | 复用废弃的 FolderHeaderRq 槽位；秒传预检响应 |
| 10030~10043 | UploadComplete / PlayReport / Recycle / DownloadDone / ShareCancel | Phase 5 新增消息段，详见 06 §3 与 common/protocol/message_type.h |

- **认证消息**：10000/10001 Register、10002/10003 Login 已实现；密码只上行，LoginRs 仅回 code/uid/name，不含 hash/salt。
- **10006 大帧**：payload = task_id + chunk_index + offset + chunk_md5 + u32 data_len + 原始分片字节；
  服务端用 Codec::decodeBulk 解析、业务线程校验 CRC（H2）。
- **10011 下载块**：19 字节帧头后直接跟块字节，不是 10006 那样的「字段 + data_len + bytes」；客户端按 LEN 整块取走。
- **分享码**：6 位，字符表 23456789ABCDEFGHJKMNPQRSTUVWXYZ（去掉 0/O/1/I/L），全大写；s_code 为 CHAR(6)。
- **错误码**：所有业务 RS 首字段固定 u32 code；ERROR_RS 为 u32 code + string message。
- 未知类型（含未注册的旧槽位）回 ERROR_RS 9003 UnknownType，不进入业务分发。
