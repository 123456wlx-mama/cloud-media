## 一、网络（6）

### 1. 为什么自研 Reactor + epoll ET/ONESHOT，而不是 libevent 或 per-connection 线程？

**考点**：IO 模型选型、是否理解事件驱动与线程模型的关系。

**回答要点**

1. 目标场景是"大量长连接 + 小块请求"：实测 8000 条长连接只占 3% CPU、服务端 RSS 41.7MB，事件驱动是合适模型；per-conn 线程在 8000 连接下光栈就不可行。
2. ET 减少重复就绪通知；**ONESHOT 保证同一条连接同一时刻只被一个 IO 线程处理**，重新注册后才可能被别的线程拿到，从模型上消灭"两个线程同时读一个 socket"。
3. 自研的收益是可控：帧解析、sendfile 零拷贝、令牌桶都贴着事件循环做，没有额外抽象层；libevent 不是不能用，是依赖与调优成本和收益不匹配。
4. 反例也想过：EPOLLEXCLUSIVE（多 IO 线程惊群优化）在本项目**没有收益**——8000 连接 CPU 只有 3%，瓶颈根本不在 accept。

**出处**：[04 网络设计](specs/04-网络设计.md) · [压测报告 §5](benchmark/压测报告.md) · [架构总览 §1](架构总览.md)

### 2. 为什么绝不在 IO 线程里做磁盘 / DB / 日志同步写？

**考点**：是否理解"事件循环被阻塞 = 所有连接一起卡"。

**回答要点**

1. IO 线程只做 `read → 解帧 → 投递任务`，任何可能阻塞的操作（MySQL/Redis/文件）都交给 worker 线程池。
2. 日志也不是"同步写盘"：**调用线程只做格式化并入队**，后台线程批量落盘；队列超阈值时丢弃 Debug/Trace，宁可丢日志也不阻塞业务。
3. 一个反例足以说明代价：一次 5ms 的磁盘写，会让这一轮 epoll 上的所有连接多等 5ms；QPS 上千时就是灾难。
4. 定时器同理：限速等待用 `runAfter` 延迟重入，不 `sleep` 工作线程。

**出处**：[04 网络设计](specs/04-网络设计.md) · [03 日志设计](specs/03-日志设计.md) · [日志性能](benchmark/日志性能.md)

### 3. 粘包 / 半包怎么解？CRC 挡住的是什么？

**考点**：二进制协议的基本功。

**回答要点**

1. 帧头定长 19 字节：`magic(4) + version(1) + type(2) + len(4) + seq(4) + crc(4)`；先凑齐头，再按 `len` 收满 payload。
2. 客户端同样有 `FrameAssembler`：一次 read 可能拿到半个帧或几个帧，按状态机切，剩余字节留在 Buffer 里等下一次。
3. CRC32 覆盖 `version..seq` 共 11 字节 + payload；挡的是**传输/内存损坏**（BadCrc 直接断链），不是安全校验。
4. 另外 `kMaxPayload = 8MB` 限制了单帧上限，避免恶意长度把内存撑爆。

**出处**：[02 协议设计](specs/02-协议设计.md) · `common/protocol/include/cm/protocol/frame.h` · `client/netapi/FrameAssembler.cpp`

### 4. 协议 v2 的帧格式是怎么取舍的？

**考点**：协议设计权衡（扩展性/健壮性/可调试性）。

**回答要点**

1. **魔数 0x434D4456（"CMDV"）**：非本协议的连接第一帧就被拒，不用等业务层报错。
2. **版本 1 字节**：协议强制升级，不做 v1 兼容解码；版本不匹配立即失败，避免"半兼容"的灰度地狱。
3. **type 2 字节 + len 4 字节**：10000~11005 的类型号够用；4 字节长度支持 8MB 大帧（上传分片）。
4. **SEQ 4 字节**：客户端每个请求自增，响应按 seq 关联；配合 5s 超时做"请求-响应"配对，异步多路复用。
5. **CRC 只算 11 字节头 + payload**：不覆盖 magic 与 crc 自身，避免"算完 CRC 再改字段"的经典坑（本项目为此返工过两次）。

**出处**：[02 协议设计](specs/02-协议设计.md) · [架构总览 §5](架构总览.md) · `.codebuddy/rules/env-policy.md`（CRC 硬规则）

### 5. 客户端为什么用 QTcpSocket + 独立网络线程？

**考点**：GUI 线程与 IO 的关系。

**回答要点**

1. GUI 线程一旦阻塞（connect/read/DNS），界面直接假死；QTcpSocket 放进 `QThread`，所有调用走 queued connection。
2. 网络线程内维持 `seq → 请求` 表，5s 未响应判超时；收帧后按 type/seq 分发，未匹配的帧丢弃。
3. 断线自动重连：1/2/4/8s 退避，最多 5 次；重连成功后自动用缓存凭据重登，UI 无感。
4. 传输状态机（transfer）只在 GUI 线程读写，网络线程只发信号——单向数据流，界面不自己算进度。

**出处**：[08 界面契约 §1.3](specs/08-界面设计契约.md) · `client/netapi/NetWorker.cpp` · [phase-8 联调记录](plans/phase-8.md)

### 6. 断线重连与断点续传怎么配合？

**考点**：异常路径的完整性，而不是"顺风局"。

**回答要点**

1. 断线时在途请求统一走 `requestAborted`（不是失败），任务转 **Paused** 并保留 `.part` / `.part.state`。
2. 重连 → 自动重登 → 用户点继续：下载先发 `DownloadStatRq` 比对 size + md5，一致才按 bitmap 从第一个缺块续；不一致提示"文件已变更"整文件重下。
3. 上传侧看服务端 `t_chunk.bitmap`（ContinueUploadRq），只补缺片；Complete 返回 `badIndexes` 时也只重传坏片。
4. 实测：20MB 文件下到 12MB 断线，重连后续传"本次只取 2 块"，落盘 20971520 字节。

**出处**：[phase-8 P8-2 记录](plans/phase-8.md) · [06 业务设计](specs/06-业务设计.md) · [05 存储设计](specs/05-存储设计.md)

## 二、存储（5）

### 7. 内容寻址 `blobs/aa/bb/md5` + 引用计数，为什么省空间？

**考点**：存储布局与去重。

**回答要点**

1. 文件内容只按 MD5 存一份：`data/blobs/aa/bb/{md5}`，两级目录防止单目录几十万文件。
2. `t_file` 对 MD5 唯一，`f_ref_count` 记录"被多少个用户节点引用"；`t_user_file` 才是用户看到的名字/目录。
3. 同一份内容被 10 个用户各存一份名字，磁盘只有 1 份；删一个用户节点只减引用，不动物理文件。
4. 写路径也做了收敛：merge 直接写 blobs 路径（同目录 rename），把"tmp→blob 二次写"消灭，写放大 2.0×→1.0×。

**出处**：[05 存储设计](specs/05-存储设计.md) · [压测报告 §4 O1](benchmark/压测报告.md)

---

### 8. 秒传的原理与幂等键是什么？

**考点**：去重、幂等、跨进程一致性。

**回答要点**

1. `UploadInitRq` 带 `md5 + size`；服务端查 `t_file`（唯一 MD5），命中就只建 `t_user_file` 并返回 `result=1`，**0 字节传输**。
2. 幂等键是 `(uid, reqId)`：同一请求重发返回同一个 task，不会重复建任务；Redis 键 `cm:v1:upload:req:{uid}:{reqId}`。
3. 踩过的坑：reqId 早期直接用任务号（每次启动从 1 开始），会撞上历史请求、复用已完成的 taskId，分片上报直接 3005；改成毫秒时间戳后消失。
4. 秒传命中必须在 UI 显式提示"已秒传 · 0 字节"，否则用户以为没上传。

**出处**：[06 业务设计](specs/06-业务设计.md) · [05 存储设计](specs/05-存储设计.md) · `client/transfer/TransferQueue.cpp`

### 9. 断点续传的 bitmap 两端怎么对账？

**考点**：状态落在哪里、谁说了算。

**回答要点**

1. 服务端：`t_chunk.bitmap` 记录每个 4MB 分片是否已收（LSB-first，1 bit/片）；客户端：`.part.state` 文本记录 `size/md5/block_size/block_count/bitmap`。
2. 上传续传以**服务端**为准（ContinueUploadRq 拿 bitmap）；下载续传以**本地**为准，但必须先 `DownloadStatRq` 校验远端 size/md5 没变。
3. 两侧 bitmap 同构（LSB-first），可以逐字节比对；差异只可能是"客户端多记了未落盘的块"，所以客户端写完块才置位。
4. 这样断线/重启都能从第一个缺块继续，不用重传整文件。

**出处**：[05 存储设计](specs/05-存储设计.md) · [06 业务设计](specs/06-业务设计.md) · [phase-8 P8-2](plans/phase-8.md)

### 10. 回收站为什么用"哨兵时间"做软删？

**考点**：软删的建模方式与索引友好度。

**回答要点**

1. `t_user_file.uf_deleted_at` 用 **1970-01-01 00:00:00** 表示"未删除"（哨兵），删除写 `NOW(6)`，恢复写回哨兵。
2. 好处：所有查询都能走同一个索引条件 `uf_deleted_at = 哨兵`，不需要 `IS NULL`（NULL 在唯一索引/统计里语义麻烦）。
3. 回收站列表就是 `uf_deleted_at <> 哨兵` 按删除时间倒序，天然分页。
4. 彻底删除（PurgeRq）才删行并 `f_ref_count--`；不做保留期与定时物理清理（需求冻结）。

**出处**：[05 存储设计](specs/05-存储设计.md) · [06 业务设计](specs/06-业务设计.md) · `server/db/file_dao.h`

### 11. GC 怎么保证不误删还在用的 blob？

**考点**：删除策略、时间宽限、对账。

**回答要点**

1. 只清 `f_state=2 AND f_ref_count=0` 的 blob，且必须同时满足三个"没人用"：没有活跃用户节点、没有未过期未取消的分享、孤儿时间超过宽限。
2. 宽限 **24 小时**，基准列用 `f_updated_at`（引用数归零那一刻自动刷新），而不是 `f_created_at`——否则"刚变成孤儿的老文件"会被立刻删。
3. 时间比较用 **数据库时钟** `DATE_SUB(NOW(6), INTERVAL ? SECOND)`，避免应用与 DB 时区/时钟偏差。
4. 每轮最多清 **2GB**（至少清 1 个），防止一次 GC 把磁盘 IO 打满；单测用可注入参数覆盖小阈值。

**出处**：[05 存储设计](specs/05-存储设计.md) · `server/logic/jobs/orphan_gc_job.h` · `server/db/file_dao.cpp`（listOrphanBlobs）

## 三、并发（5）

### 12. 线程池模型与任务边界是怎么划的？

**考点**：为什么是"IO 线程 + worker 线程"两段式。

**回答要点**

1. IO 线程（`io_threads`）负责 `epoll_wait`、read、解帧；worker 线程（`worker_threads`）跑业务 handler（DB/磁盘）。
2. 任务粒度是**一个完整请求**（一帧），不是"一次 read"：避免半帧进业务。
3. 同一连接不会并发：EPOLLIN|EPOLLONESHOT，处理期间不重新注册，天然串行。
4. Docker 里为了 2C4G 配成 `io_threads=2 / worker_threads=4`；默认是 4/8，按机器调。

**出处**：[04 网络设计](specs/04-网络设计.md) · `docker/server.conf`

---

### 13. 令牌桶限速 + 流上限，为什么还需要全局背压？

**考点**：公平性 vs 稳定性。

**回答要点**

1. 限速解决"单个用户不能占满带宽"：连接级 2MB/s（桶容量 4MB）、用户级 8MB/s（容量 16MB）。
2. 流上限解决"单个用户不能占满连接"：全局 512 条下载流、每用户 8 条，超过回 3006。
3. 令牌不足但 ≤2s 能补上时，用 `runAfter` 延迟重入，不 sleep 工作线程；>2s 直接 3006。
4. 还需要全局背压是因为**内存**：4MB 分片 × 64 在途 ≈ 256MB，2C4G 上不设上限会 OOM——这是压测里的拐点来源。

**出处**：[06 业务设计](specs/06-业务设计.md) · [压测报告 §1/§3](benchmark/压测报告.md) · `server/logic/rate_limiter.h`

---

### 14. 压测里为什么 64 在途是拐点？

**考点**：能否把压测现象解释成排队论/内存约束，而不是"调参玄学"。

**回答要点**

1. 在途上限 64 ≈ 64 × 4MB ≈ 256MB 缓冲，是 2C4G 机器在"吞吐"和"不 OOM"之间的经验值；再往上 P99 先抬头。
2. 10MB 上传的 P99 不是单请求慢，而是**排队**：64 在途 × 10MB ÷ 42MB/s ≈ 7.6s，与实测 P50 7.72s 吻合（Little's Law）。
3. 优化后 86.7MB/s、P99 6.65s，说明拐点更多来自"写放大/哈希扫描"，不是线程数。
4. 面试可补一句：真正的全局背压（发送队列按字节阻塞）目前还没做，是本项目已知限制。

**出处**：[压测报告 §1/§3](benchmark/压测报告.md) · [09 播放器设计 §1 末尾](specs/09-播放器设计.md)（队列无反压的说明）

### 15. 锁粒度怎么控制？

**考点**：临界区里到底放了什么。

**回答要点**

1. `TokenBucket` 本身**无锁**：每条连接的桶只在该连接的 IO 线程内更新，不存在竞争。
2. 跨连接共享的是"用户级桶 + 流计数"，放在 `DownloadLimits` 的一把 mutex 下；临界区只做加减和 map 查找，**不碰 IO、不写日志**。
3. 队列用 `std::mutex + condition_variable`，但音频回调只用非阻塞 `get`，绝不把声卡线程挂在锁上。
4. 原则：锁只保护数据结构，不保护动作；能算完再出锁，就不要在锁里做系统调用。

**出处**：`server/logic/rate_limiter.h` · `server/logic/download_limits.h` · [09 播放器设计 §6](specs/09-播放器设计.md)

### 16. 惊群与 EPOLLEXCLUSIVE：为什么本项目不用？

**考点**：是否会"为了用而用"高级特性。

**回答要点**

1. 实测 8000 连接 CPU 只有 3%，accept 侧不是热点；火焰图里 `EpollPoller` 占比 0.03%~0.62%。
2. connect storm 的 P90 1s 来自**客户端 TIME_WAIT/端口回收**与 accept 循环，不是内核惊群；调大 `somaxconn` 后 P99 反而更差（排队更久），已回退。
3. EPOLLEXCLUSIVE 只对"多 IO 线程同时被唤醒抢 accept"有意义；本场景没有这个瓶颈，做了也不会提升上传/列表吞吐。
4. 结论写进了压测报告："不要用 EPOLLEXCLUSIVE 去解 TIME_WAIT"。

**出处**：[压测报告 §5](benchmark/压测报告.md) · [phase7_optimize O3](benchmark/phase7_optimize.md)

## 四、缓存（3）

### 17. Redis 里到底存了什么？

**考点**：缓存边界——什么该进、什么不该进。

**回答要点**

1. 会话 `cm:v1:sess:{token}`；文件索引 `cm:v1:file:md5:{md5}` / `file:id`（秒传与下载元信息）。
2. 分享：`share:{code}`（5min ±10% 抖动）、`share:miss:{code}`（60s 防穿透）、`share:req:{uid}:{reqId}`（创建幂等）、`share:ticket:{token}`、`share:fail:{code}:{ip}`（提取码失败计数）。
3. 限流：`rate:*` 固定窗口计数；上传幂等：`upload:req:{uid}:{reqId}`；上传 bitmap：`upload:bitmap:{taskId}`。
4. **不缓存目录列表**：一次上传/删除/分享会影响多个列表键，失效面大，查询本身走索引 <5ms——这是刻意不做。

**出处**：[05 存储设计 §缓存](specs/05-存储设计.md) · `server/cache/cache_store.h`

---

### 18. Redis 挂了怎么降级？

**考点**：不同数据的一致性要求不同，降级策略要分开。

**回答要点**

1. **会话/鉴权 fail-closed**：Redis 不可用时拒绝（返回 4008 一类），安全优先，不能"降级成放行"。
2. **分享元信息 fail-open**：缓存 miss/错误就回源 MySQL，一致性优先；只是慢一点。
3. **秒传**：Redis 索引 miss 就查 `t_file`（MySQL 才是权威），不影响正确性。
4. **带提取码的分享**：Redis 挂时无法做失败计数/锁定，直接 4008 拒绝（fail-closed），避免被暴力试码。

**出处**：[06 业务设计](specs/06-业务设计.md) · `server/logic/share_service.h`（注释写明 fail-closed/fail-open） · [05 存储设计](specs/05-存储设计.md)

---

### 19. 分享码 / 限流 key 是怎么设计的？

**考点**：key 设计与误输入友好度。

**回答要点**

1. 分享码：**6 位、31 字符表**（去掉易混的 0/O/1/I/L），统一大写，生成用拒绝采样保证均匀；碰撞重试 5 次。
2. 所有 key 统一前缀 `cm:v1:`，按域分段（sess/file/share/rate/upload）；`isSafeKey` 校验拼接值，防 key 注入。
3. 幂等键一律 `(uid, reqId)` 组合，和业务对象解耦；ticket 用 hex 串，长度受限。
4. 限流 key 按 `(ip, 时间窗)` 或 `(uid, 窗口)` 固定窗口计数，窗口过期自动淘汰。

**出处**：[06 业务设计](specs/06-业务设计.md) · `server/logic/share_service.cpp` · `server/cache/cache_store.cpp`

## 五、日志（2）

### 20. 异步日志是怎么做的？

**考点**：日志不能成为业务线程的负担。

**回答要点**

1. **调用线程只做格式化**（带上时间/线程 id/traceId/文件行号），然后把整行字符串入队；后台线程只做 write。
2. 批量策略：队列 ≥256 条或 ≥64KB 唤醒一次；定时 flush；文件按大小/天数滚动。
3. 队列有上限：超过阈值先丢 Debug/Trace，超过 4× 连普通级别也丢，只有 Fatal 必留——**宁可丢日志，不阻塞业务**。
4. 因为格式化在调用线程完成，traceId（thread_local）不会在落盘线程里丢。

**出处**：[03 日志设计](specs/03-日志设计.md) · `common/log/logger.cpp` · [日志性能](benchmark/日志性能.md)

### 21. traceId 怎么跨任务传递？

**考点**：thread_local 的边界。

**回答要点**

1. `Logger::setTraceId/traceId` 用 `thread_local char[128]`，每条日志格式里输出 `trace=-` 或具体值。
2. 因为格式化发生在**调用线程**，同一线程内的日志天然带 trace；跨线程（IO → worker）必须**显式把 trace 字符串放进任务参数**，thread_local 不会跟着任务走。
3. 现状：API 与单测齐备，落盘格式已带 trace 字段；生产调用点还没有全面铺开（属于"已留好接口，未全量接线"）。
4. 如果面试官追问"怎么做到全链路"，回答：在连接 dispatch 处生成 `uid-seq-时间` 作为 trace，随任务结构体传给 worker，worker 入口 setTraceId、出口清空。

**出处**：[03 日志设计](specs/03-日志设计.md) · `common/log/logger.cpp` · `common/tests/test_logger.cpp`

## 六、音视频（5）

### 22. 播放器的三线程模型是什么？

**考点**：为什么不能用 1 个线程或每帧开线程。

**回答要点**

1. **demux**：`av_read_frame` 按 stream 分发到 videoQ/audioQ，seek 也在这一线程做。
2. **video**：解码 + 按 pts 与主时钟差节流 + sws 转 RGBA → `frameReady(QImage)`。
3. **SDL 音频回调**：解码音频、swr 转 S16、混音量、推进音频时钟；回调里只做非阻塞取包。
4. GUI 只发命令和收状态。1 个线程会让"视频等同步"卡住 demux（音频饿死）；再多一个只是多一次拷贝和同步点。

**出处**：[09 播放器设计 §1](specs/09-播放器设计.md)

---

### 23. 音画同步为什么以音频为主时钟？落后为什么丢帧不慢放？

**考点**：同步的物理约束。

**回答要点**

1. 声卡消费速率由晶振决定，软件改不了；音频抖动"听得见"，视频延迟"看不见"——所以让视频追音频。
2. 时钟 = 当前音频帧 pts + 已交给声卡的样本数/44100，**只增不减**，误差上限就是设备缓冲（≈23ms）。
3. 视频 pts 比时钟早 ≤8ms 直接渲染；早更多就每 5ms 睡一次等；**落后 >120ms 丢帧**。
4. 慢放会让视频永远追不上（音频不会等），差距越滚越大；丢帧是唯一能收敛的手段。实测 seek 风暴最大漂移 109ms（≤丢帧阈值）。

**出处**：[09 播放器设计 §2](specs/09-播放器设计.md) · [phase-9 回归数据](plans/phase-9.md)

---

### 24. seek 为什么会花屏？双屏障各防什么？

**考点**：异步 seek 的竞态。

**回答要点**

1. seek 要做四件事：`av_seek_frame` → 清包队列 → flush 解码器 + 清 PCM 缓冲 → **在 flush 之后**重置时钟基准。
2. `seekGen`（代数）防"seek 前入队、seek 后才解码"的旧包；`seekDropMs` 防"seek 后从关键帧解码、但还没到目标"的帧。
3. 只留一个不够：向后 seek 时旧帧的 pts（55s）大于新目标（4.8s），时间屏障会放行；而关键帧到目标之间的新帧时间没到，只能靠时间屏障。
4. 交付前必须再查一次（等时钟期间可能又发生 seek）；实测修完漂移从 50.3s 降到 109ms。

**出处**：[09 播放器设计 §3](specs/09-播放器设计.md) · [phase-9 三个 bug](plans/phase-9.md)

---

### 25. 边下边播为什么阻塞读而不是 EOF？faststart 是干什么的？

**考点**：把"文件还没写完"建模成"数据慢"而不是"流结束"。

**回答要点**

1. 对 demuxer 来说 EOF = 流结束，播放器会停在 4MB 处；阻塞读让"数据慢"成为唯一语义，下载推进后自然继续。
2. 下载完成由 transfer 层置 `sourceComplete`，之后 read 才返回真正的 EOF → 自然播到结尾。
3. MP4 的 moov 必须在文件前部（`-movflags +faststart`），否则必须等整个文件下完才能 open。
4. 另外两处配套：首块落盘后才 open（否则 GUI 线程与下载响应互等）、`probesize=512KB` / `max_analyze_duration=2s` 防止 open 等未下载的数据。

**出处**：[09 播放器设计 §4](specs/09-播放器设计.md) · [phase-8 P8-4 记录](plans/phase-8.md)

---

### 26. 下载的 sendfile 零拷贝是怎么做的？

**考点**：Linux IO 路径与收益。

**回答要点**

1. 4MB 块直接从文件 fd `sendfile` 到 socket，数据不进用户态；对比 read+write 少两次拷贝、少一次上下文切换。
2. 实测下载裸能力 **522MB/s、CPU 15%**；c=1000 掉到 407MB/s 是 1000 条连接的调度开销，不是拷贝问题。
3. 零拷贝与限速正交：令牌桶在提交 sendfile 之前扣，超限回 3006 或 `runAfter` 重试。
4. 编译期开关 `CM_DOWNLOAD_ZEROCOPY`，关闭时走 4MB 缓冲路径，协议不变。

**出处**：[压测报告 §3](benchmark/压测报告.md) · [06 业务设计](specs/06-业务设计.md) · `server/logic/sendfile_block_sender.cpp`

## 七、C++11（2）

### 27. 为什么死守纯 C++11？

**考点**：工程约束优先于语法糖。

**回答要点**

1. 目标环境是 Ubuntu 16.04 + **g++ 5.4 + cmake 3.5**（面试可补：本机新工具链只是开发便利）；C++14/17 特性在那边编不过。
2. 红线清单：`std::make_unique`、`std::optional`、`std::string_view`、`std::filesystem`、泛型 lambda、`std::variant` 全部禁用。
3. CI 有 `scripts/check_cpp11.sh` 做 grep 级检查，C++11 标准在 CMake 里显式 `-std=c++11`。
4. 代价是写法啰嗦（`unique_ptr<T>(new T)`），收益是"到哪台机器都能编"，对交付更重要。

**出处**：[cpp11 规范](../.codebuddy/rules/cpp11-style.md) · [phase6 C++11 检查](benchmark/phase6_cpp11_check.md) · [架构总览 §5](架构总览.md)

### 28. RAII / move / 智能指针在项目里怎么落地？

**考点**：不是背概念，而是看代码里怎么用。

**回答要点**

1. `unique_ptr` 管 `MYSQL*` / `AVFrame` / `AVCodecContext` / `AVIOContext`：连接池借出即包装，析构自动归还或释放。
2. `Buffer` 支持 move：4MB 分片在"网络→队列→业务"之间移动而不是拷贝；`emplace_back` 构造任务。
3. 锁一律 `std::lock_guard`/`unique_lock`，没有手工 lock/unlock 配对；条件变量用谓词版本防虚假唤醒。
4. 错误用 `ErrorCode` 返回值而不是异常（服务端不想为异常付出栈展开成本）；构造失败用工厂/`bool init()`。

### 30. 压测怎么把上传从 35.3 优化到 86.7MB/s（2.46×）？

**考点**：有没有"测量→定位→改→再测"的闭环。

**回答要点**

1. 先做基线：10MB×100 并发、64 在途，35.3MB/s、P99 11.59s；perf 火焰图显示 CRC 回读 16.11% + 帧 CRC 12.84% + MD5 是热点。
2. **O7-c**：block CRC sidecar 懒生成，不再上传后回读整个 blob 算 CRC；**O7-a**：收片不再重算分片 MD5（帧 CRC + merge 已覆盖）→ 50.3MB/s。
3. **O1**：merge 直接写 blobs 路径（同目录 rename），消灭 tmp→blob 二次写，写放大 2.0×→1.0× → **86.7MB/s、P99 6.65s**。
4. 反直觉结论也留了：O3（somaxconn/EPOLLEXCLUSIVE）无收益且让 P99 更差，已回退；瓶颈从来不在连接层。

**出处**：[压测报告 §4](benchmark/压测报告.md) · [phase7 优化记录](benchmark/phase7_optimize.md) · [phase7 火焰图](benchmark/phase7_flamegraph.md)

## 附：抽查自述（3 条最没把握的）

> 规则：挑 3 条自己最虚的，用 1 分钟口头复述，并标出会卡壳的位置。下面是自评。

### A. 第 11 条「GC 不误删」

**60 秒复述**：GC 只清三种条件同时满足的 blob：`f_state=2`、`f_ref_count=0`、以及"没人引用"——具体是既没有活跃用户节点、也没有未过期的分享。宽限期 24 小时，基准列用 `f_updated_at`（引用数归零那一刻），不是创建时间；时间比较用数据库时钟 `NOW(6)` 避免时钟偏差。每轮最多清 2GB，至少清一个，防止 GC 把磁盘 IO 打满。

**卡壳点**：① 没亲手跑过 GC 任务，实际调度周期（cron/定时器）没看过；② `f_state=2` 的业务含义（是"已合并完成"还是"待清理"）需要回代码确认；③ "对账"是否额外扫描 `data/blobs` 目录来发现"库里有、盘上没有"的反向孤儿，目前只看了 SQL 侧。

### B. 第 19 条「分享码 / 限流 key 设计」

**60 秒复述**：分享码 6 位、31 字符表（去 0/O/1/I/L），拒绝采样保证均匀，碰撞重试 5 次；key 统一 `cm:v1:` 前缀按域分段，幂等键用 `(uid, reqId)`；限流按 IP/用户 + 时间窗计数。

**卡壳点**：① 拒绝采样的具体循环与最大尝试次数（只记得"重试 5 次"是创建碰撞，不是采样）；② 各 key 的 TTL 具体值（share 5min±10%、miss 60s 记得，upload bitmap 的 TTL 没核对）；③ `isSafeKey` 的字符白名单细节。

### C. 第 21 条「traceId 跨任务传递」

**60 秒复述**：trace 是 thread_local 的 128 字节缓冲，日志格式化在调用线程完成，所以同线程日志天然带 trace；跨线程必须把 trace 字符串随任务显式传过去，worker 入口 set、出口清。

**卡壳点**：① 生产代码里 `setTraceId` 的调用点还没铺开（目前只有 API 和单测）——被追问"那你们线上怎么排查"要如实说"靠 uid/seq/时间戳，trace 接线是待办"；② IO 线程 → worker 的任务结构体现在有没有 trace 字段，没核对；③ 128 字节截断策略（超长直接截断）是否符合预期。
